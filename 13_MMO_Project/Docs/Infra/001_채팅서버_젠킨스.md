# 채팅 서버 Jenkins 잡

Jenkins의 `ChatServer` 폴더에 있는 5개 잡은 `windows-build-server-01`에서 실행한다.

| 잡 / 스크립트 | 역할 |
|---|---|
| [`Build_ChatServer_ALL`](../../Infra/Jenkins/ChatServer/Build_ChatServer_ALL.Jenkinsfile) | 작업 저장소를 `git pull --ff-only`로 갱신하고 `Chatting.sln` 전체를 `Release x64`로 빌드한다. |
| [`Run_ChatServer`](../../Infra/Jenkins/ChatServer/Run_ChatServer.Jenkinsfile) | 빌드된 서버와 설정을 실행별 폴더에 복사해 기동한다. 포트 리슨을 확인하면 잡만 끝나고 서버는 계속 실행된다. |
| [`Run_ChatDummy`](../../Infra/Jenkins/ChatServer/Run_ChatDummy.Jenkinsfile) | 지정 포트에 채팅 서버가 리슨 중인지 확인하고, 빌드된 더미를 실행한다. 실행 결과 `RunSummary.json`을 Jenkins 아티팩트에 보관한다. |
| [`Stop_ChatServer`](../../Infra/Jenkins/ChatServer/Stop_ChatServer.Jenkinsfile) | Jenkins가 띄운 서버에 정상 종료를 요청하고, 응답이 없으면 해당 프로세스만 강제 종료한다. |
| [`Stop_ChatDummy`](../../Infra/Jenkins/ChatServer/Stop_ChatDummy.Jenkinsfile) | Jenkins 실행 폴더에 남아 있는 더미 프로세스만 종료한다. |

보통 `Build_ChatServer_ALL` → `Run_ChatServer` → `Run_ChatDummy` 순서로 실행한다. 두 실행 잡에는 같은 포트를 지정한다. 빌드 잡과 실행 잡 두 개는 성공·실패 결과를 Slack `#jenkins-build-alert`로 보낸다.

`Run_ChatServer`의 메트릭 파라미터와 Grafana 조회 방법은 [채팅 서버 모니터링 연동](002_채팅서버_모니터링.md)을 참고한다.

## Git 연동

5개 잡 모두 Jenkins의 `Configure → Pipeline → Definition`을 `Pipeline script from SCM`으로 설정했다.

| 항목 | 설정값 |
|---|---|
| SCM | `Git` |
| Repository URL | `https://github.com/MyungHyun-Ahn/Portfolio.git` |
| Credentials | `- none -` |
| Branch Specifier | `*/main` |
| Script Path | `13_MMO_Project/Infra/Jenkins/ChatServer/<잡 이름>.Jenkinsfile` (저장소 루트 기준, 위 표의 파일과 1:1 대응) |
| Lightweight checkout | 활성화 |

잡 실행 시 Jenkins가 `main`의 Jenkinsfile을 읽는다. 실행 로직을 바꿀 때는 Jenkins UI 대신 저장소의 Jenkinsfile을 수정해 `main`에 반영한다. Git 연동은 스크립트 출처만 바꾼 것이며, 푸시 시 자동 실행은 설정하지 않았다. `Build_ChatServer_ALL` 내부의 `git pull --ff-only`는 Windows 빌드 작업 저장소를 갱신하는 별도 단계다.

SCM 전환 후 5개 잡 모두 Git에서 Jenkinsfile을 불러와 실행하는 것을 사용자가 확인했다. 스크립트 로드는 해당 빌드의 콘솔에서 `Obtained ... from git` 메시지로 확인할 수 있다. 노드 설정과 인증 정보는 Jenkins에서 관리한다.

## 더미 실행 시간과 Jenkins 타임아웃

- `RUN_DURATION_MS`는 더미의 `main()` 진입부터 새 작업을 중단할 때까지의 시간(ms)이다. 폼에 표시되는 ‘모든 더미가 Ready가 된 뒤’는 이전 동작 설명이다.
- `Run_ChatDummy`는 더미 프로세스가 종료된 뒤 생성된 `RunSummary.json`을 보관하고 끝난다. 정상 실행에서는 설정 시간이 지난 뒤 진행 중인 요청을 정리하므로 잡 완료까지 시간이 더 걸릴 수 있다. 더미가 오류로 먼저 종료되면 설정 시간까지 기다리지 않는다.
- Jenkins 타임아웃은 `RUN_DURATION_MS`를 초로 올림한 값에 300초(5분)를 더해 계산한다. 노드 할당 후 시작되며, 실행 준비부터 결과 보관까지 적용된다.

| `RUN_DURATION_MS` | 더미 실행 시간 | Jenkins 타임아웃 |
|---|---:|---:|
| `360000` | 6분 | 11분 |
| `3600000` | 1시간 | 65분 |

`Run_ChatDummy #18`은 `360000`을 입력한 실행이다. 콘솔의 `Timeout set to expire in 11 min`은 중단 한도를 설정했다는 뜻이며, 실제 결과는 `SUCCESS`였다.
