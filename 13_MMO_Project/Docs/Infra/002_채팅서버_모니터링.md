# 채팅 서버 모니터링 연동

원격 Windows 노드의 ChatServer 지표와 원본 로그를 모니터링 호스트 `myoong`의 Grafana에서 조회한다. Jenkins 잡은 [채팅 서버 Jenkins 문서](001_채팅서버_젠킨스.md)를 따른다.

## 현재 구조

```text
지표 수집: myoong의 Prometheus → Tailscale → Windows의 ChatServer /metrics (:9464)
로그 전송: Windows의 ChatServer .log → Alloy → HTTPS :8443 → Serve → Caddy → Loki
사용자 조회: 브라우저 → HTTPS :443 → Serve → Grafana → Prometheus / Loki (Compose 내부)
```

| 구분 | 현재 구성 |
|---|---|
| 원격 Windows 노드 | Jenkins 에이전트, ChatServer, Alloy 서비스. `Run_ChatServer`가 실행마다 `server-<빌드 번호>` 폴더를 만든다. |
| 모니터링 호스트 | `portfolio-monitoring` Compose 프로젝트로 Prometheus, Grafana, Loki, Caddy를 실행한다. Prometheus·Grafana·Loki 데이터는 각각 Docker 볼륨에 저장한다. [Loki](../../Infra/Monitoring/loki/loki.yml)는 단일 인스턴스이며 로그를 로컬 파일시스템에 저장한다. |
| 사용자 접속 | Grafana는 호스트의 `127.0.0.1:3000` 또는 Tailscale Serve의 HTTPS `443`으로 접속한다. Prometheus UI는 호스트의 `127.0.0.1:9090`에서 확인한다. |
| 로그 수신 | Serve `8443` → `127.0.0.1:3101`의 Caddy → `loki:3100`. Caddy는 지정된 Jenkins 노드 주소의 `POST /loki/api/v1/push`만 전달한다. Loki `3100`은 호스트에 공개하지 않으며 Funnel은 사용하지 않는다. |

## 1. 모니터링 호스트 기동

`13_MMO_Project` 디렉터리에서 실행한다. 이미지 버전, 포트, 볼륨은 [Compose 설정](../../Infra/Monitoring/compose.yml)을 기준으로 한다.

```powershell
docker compose -f Infra/Monitoring/compose.yml config --quiet
docker compose -f Infra/Monitoring/compose.yml up -d
docker compose -f Infra/Monitoring/compose.yml ps
```

Grafana는 [데이터 소스 설정](../../Infra/Monitoring/grafana/datasources.yml)에서 `http://prometheus:9090`과 `http://loki:3100`을 자동으로 등록한다. [대시보드 설정](../../Infra/Monitoring/grafana/dashboards.yml)은 같은 디렉터리의 `dashboards/` 아래 JSON을 읽으므로 UI에서 데이터 소스나 대시보드를 다시 만들 필요가 없다.

원격 Windows 노드와 모니터링 호스트는 같은 tailnet에 연결한다. 새 모니터링 호스트에 복원할 때만 아래 [Serve 설정](https://tailscale.com/docs/reference/tailscale-cli/serve)을 추가한다. 기존 호스트에서는 먼저 `tailscale serve status`로 등록 상태를 확인한다. 신규 Grafana는 원격에 열기 전에 로컬에서 관리자 비밀번호를 변경한다.

```powershell
tailscale serve --bg --https=443 http://127.0.0.1:3000
tailscale serve --bg --https=8443 http://127.0.0.1:3101
tailscale serve status
```

## 2. Prometheus 지표 연동

1. Jenkins `Run_ChatServer`에서 `METRICS_PORT=9464`, `METRICS_BIND_ADDRESS=100.95.10.123`으로 서버를 기동한다. 주소는 Jenkins 컨트롤러가 아니라 **ChatServer가 실행되는 Windows 노드의 Tailscale IPv4**다. `METRICS_PORT=0`이면 exporter가 꺼진다.
2. [Prometheus 설정](../../Infra/Monitoring/prometheus.yml)의 `chat_server` 대상에 같은 주소와 포트를 지정한다. 현재 `/metrics`를 5초마다 읽고, 요청 제한 시간은 3초다. 실행 중인 Prometheus의 설정을 수정했다면 아래 명령으로 검사한 뒤 Prometheus에 다시 로드한다.
3. 모니터링 호스트의 Prometheus **Status → Targets**에서 `chat_server`가 `UP`인지 확인한다. Grafana **Dashboards → ChatServer - Prometheus**에서 활성 세션이나 실제 콘텐츠 FPS가 조회되는지 확인한다.

```powershell
docker compose -f Infra/Monitoring/compose.yml exec -T prometheus promtool check config /etc/prometheus/prometheus.yml
# 검사가 통과한 뒤에만 실행한다.
docker compose -f Infra/Monitoring/compose.yml kill -s SIGHUP prometheus
```

`SIGHUP`은 [Prometheus 설정 재로드](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)에 사용한다.

## 3. Alloy → Loki 로그 연동

`windows-build-server-01`의 관리자 PowerShell에서 실행한다. Alloy가 없다면 `winget install GrafanaLabs.Alloy`로 설치한다. 기본 설정 파일은 `%ProgramFiles%\GrafanaLabs\Alloy\config.alloy`다. 기존 Alloy가 다른 로그도 수집한다면 설정 전체를 덮어쓰지 말고 필요한 블록만 병합한다. Windows 설치·서비스 설정은 [Grafana Alloy 설치 안내](https://grafana.com/docs/alloy/latest/set-up/install/windows/)와 [Windows 설정 안내](https://grafana.com/docs/alloy/latest/configure/windows/)를 참고한다.

아래에서 `$repo`는 원격 노드에 있는 `13_MMO_Project`의 실제 경로로, `$monitoringHost`는 모니터링 호스트의 `tailscale serve status`에 표시되는 호스트명으로 바꾼다. 노드가 바뀌면 [Caddy 수신 설정](../../Infra/Monitoring/loki/Caddyfile)의 허용 IPv4/IPv6도 해당 노드에 맞춘다.

```powershell
$repo = '<13_MMO_Project 경로>'
$monitoringHost = '<모니터링 호스트의 tailnet 호스트명>'
$alloyDir = Join-Path $env:ProgramFiles 'GrafanaLabs\Alloy'
$source = Join-Path $repo 'Infra\Monitoring\alloy\config.alloy'
$target = Join-Path $alloyDir 'config.alloy'
$key = 'HKLM:\SOFTWARE\GrafanaLabs\Alloy'

$env:CHATSERVER_LOG_GLOB = 'C:/JenkinsAgent/workspace/ChatServer/Run_ChatServer/server-*/LogFile/run-*/*-ChatServer.log'
$env:LOKI_PUSH_URL = "https://${monitoringHost}:8443/loki/api/v1/push"

& (Join-Path $alloyDir 'alloy-windows-amd64.exe') validate $source
if ($LASTEXITCODE -ne 0) { throw 'Alloy 설정 검증 실패' }

# 이 Alloy가 ChatServer 로그만 수집할 경우에만 전체 파일을 교체한다.
Copy-Item -LiteralPath $target -Destination "$target.bak" -ErrorAction Stop
Copy-Item -LiteralPath $source -Destination $target -Force -ErrorAction Stop

$existing = (Get-Item -LiteralPath $key -ErrorAction Stop).GetValue('Environment')
[string[]]$updated = @(
    $existing | Where-Object { $_ -and $_ -notmatch '^(CHATSERVER_LOG_GLOB|LOKI_PUSH_URL)=' }
) + @("CHATSERVER_LOG_GLOB=$env:CHATSERVER_LOG_GLOB", "LOKI_PUSH_URL=$env:LOKI_PUSH_URL")
New-ItemProperty -LiteralPath $key -Name Environment `
    -PropertyType MultiString -Value $updated -Force -ErrorAction Stop | Out-Null

Restart-Service -Name Alloy -ErrorAction Stop
Get-Service -Name Alloy
```

`$env:`는 검증과 서비스에 넘길 값 구성에 사용한다. 서비스 자체는 레지스트리의 `Environment` 값을 읽는다. `server-*`를 사용하므로 Jenkins 빌드 번호가 바뀔 때마다 설정하거나 Alloy를 재시작할 필요는 없다. [수집 템플릿](../../Infra/Monitoring/alloy/config.alloy)은 [`tail_from_end = true`](https://grafana.com/docs/alloy/latest/reference/components/loki/loki.source.file/)로 설정되어 있어 읽기 위치가 없는 파일의 기존 줄은 건너뛴다. 새 파일을 발견한 뒤 기록된 로그로 수집을 확인한다.

## 4. 조회 및 장애 확인

- **로그 조회:** Grafana **Dashboards → ChatServer 로그**를 열면 `{service="chatserver"}`가 자동 실행된다. 최근 1시간의 로그를 최신순으로 최대 500줄 표시하며, 10초마다 새로고침한다.
- **메트릭이 안 보일 때:** Prometheus의 `chat_server` 대상부터 확인한다. `DOWN`이면 Server 기동 시 출력한 `/metrics` 주소, 노드 간 접속, Jenkins의 bind 주소와 scrape 대상 일치 여부를 확인한다.
- **로그가 안 보일 때:** 원격 원본 파일의 새 줄, Alloy 서비스 상태와 Windows 응용 프로그램 이벤트 로그, Serve `8443`, Caddy의 허용 노드 주소를 순서대로 확인한다. Loki 준비 상태는 아래 명령으로 볼 수 있지만, 수집 성공은 Grafana에서 같은 실행의 실제 로그를 확인해야 판단할 수 있다. 장애 확인을 위해 끝난 부하 테스트를 다시 돌릴 필요는 없다.

```powershell
docker compose -f Infra/Monitoring/compose.yml exec -T grafana wget -qO- http://loki:3100/ready
```
