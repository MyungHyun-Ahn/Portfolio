# 채팅 패킷 송수신 흐름

현재 `Tests/Chatting`의 콘솔 클라이언트와 IOCP 채팅 서버를 기준으로 한다. 기존 구조처럼 네트워크 계층이 패킷을 송수신하고, 서버 콘텐츠 계층이 로그인·섹터·채팅을 처리한다. Packet Generator는 기존 수동 패킷 작성과 분기 코드만 대체한다. 생성 방법은 [Packet Generator 사용법](../../Tools/PacketGenerator/README.md)을 참고한다.

## 접속부터 채팅 가능 상태까지

클라이언트 `Main()`은 설정을 읽고 서버에 접속을 요청한다. 앱 스레드의 `Tick()`이 현재 `SessionId`로 `TryPopEvent()`를 호출해 `Connected`를 받으면 `onConnect()`가 공통 `ReqLogin()`을 호출한다. `ReqLogin()`은 생성 `SendReqLogin()`의 접수 성공 후 기대 계정을 기록한다. 공통 `HandleResLogin()`은 응답을 검증하고 로그인 승인 상태를 확정한다. 그 뒤 콘솔의 `onLoginAccepted()`가 설정 좌표로 공통 `ReqSectorMove()`를 호출한다. `ReqSectorMove()`는 생성 `SendReqSectorMove()`의 접수 성공 후 기대 좌표를 기록한다. 공통 `HandleResSectorMove()`가 응답을 접수된 요청 계정·좌표와 대조하고 섹터를 확정하면 `IsChatReady()`가 참이 된다. 이후 클라이언트가 보내는 `HeartbeatNoti`는 응답 없이 서버의 마지막 수신 시각을 갱신한다.

## 공통 클라이언트 코드와 앱별 콜백

`CChatNetClient`는 `CClient`를 공개 상속하고 `IClientPacketHandler`를 비공개 상속한다. 콘솔처럼 이 클래스를 직접 상속하면 `Tick()` → `onRecv()` → `DispatchClientPacket()` → `Handle*()` 수신 경로와 `protected ReqLogin()`·`ReqSectorMove()`를 재사용한다. 앱은 요청 시점과 인자를 정하고, 공통 핸들러는 응답을 검증해 상태를 확정한다.

공통 핸들러가 호출하는 `on~()`은 검증과 상태 갱신 이후 실행하는 앱별 콜백이다. 콘솔은 출력을, 더미는 echo 대조와 통계를 여기에 둔다. 향후 언리얼 클라이언트는 콜백 시그니처에 공통 패킷 타입을 유지하고, 언리얼 모듈의 override 내부에서만 `FString`·`FText` 등으로 변환한다. 콜백은 `Tick()` 호출 스레드에서 실행된다. 게임 스레드 밖에서 `Tick()`을 호출한다면 UI 갱신에 필요한 값만 복사해 게임 스레드로 넘긴다. 콜백의 패킷 참조는 호출 이후 보관하지 않는다. 언리얼 연동은 아직 검증하지 않았다.

## 채팅 한 줄의 왕복

1. **클라이언트 송신.** 콘솔 입력 루프가 준비 상태와 메시지 길이를 확인하고, 생성된 `CChatNetClient::SendReqMessage()`에 계정 번호와 메시지를 넘긴다. 생성 함수는 `SReqMessage`를 채우고 `MakePacketReqMessage()`로 힙 버퍼에 패킷 ID와 본문을 쓴다. `CClient`의 `sendPacket()`이 공유 버퍼를 현재 세션의 `CClientManager::SendPacket()`에 넘긴다. 세션이 Net 헤더를 준비하고 송신 큐와 실제 I/O를 관리한다.
2. **서버 수신 → 콘텐츠.** `CSession::PostRecv()`는 TLS 풀에서 빌린 `CRecvBuffer` 페이지에 `WSARecv()`를 건다. `RecvCompleted()`는 헤더와 길이를 검사하고 `Net` 모드에서는 복호화·체크섬까지 확인한다. 한 페이지 안의 프레임은 복사 없이 `CSerializableBufferView`로 만들고, 완료 사이에 걸친 프레임만 세션의 `m_pDelayedBuffer`에 이어 붙인다. 검증된 View는 세션의 `m_recvMsgQueue`를 거쳐 콘텐츠 스레드의 `CChatContents::OnRecv()`로 전달된다. **IOCP 수신 완료 처리에서 채팅 Handle을 바로 실행하지 않는다.**
3. **분기 → 수동 Handle.** `CChatContents::OnRecv()`가 패킷 ID를 한 번 읽고 `DispatchServerPacket()`에 넘긴다. 디스패처는 `message >> packet`으로 본문을 읽고, 잘리거나 후행 바이트가 남으면 Handle을 호출하지 않는다. 정상 본문의 로그인 상태·계정·섹터·크기 검사는 수동 `CProcessPacket::HandleReqMessage()`가 담당한다. 서버 수신이 `Failed`를 반환하면 `CBaseContents`가 연결을 끊는다.
4. **서버 응답과 주변 전파.** `HandleReqMessage()`는 `ResMessage(6)`와 `MessageNoti(8)`를 별도 버퍼로 만든 뒤, 응답은 송신자에게만 제출한다. `SendSector()`는 알림 헤더를 한 번 준비하고 양축 ±1 범위에서 송신자를 제외한 세션에 같은 알림 버퍼를 전파한다. `CServer::SendPacket()`은 큐 등록 뒤 `PostSend()`를 시도한다. 이미 송신 중이면 큐에 남고, 완료 경로에서 이어 보낸다.
5. **클라이언트 수신 → 콘솔.** 클라이언트 세션이 완성된 패킷을 매니저가 관리하는 연결별 Mailbox에 넣는다. 콘솔 스레드가 라이브러리의 `CClient::Tick()`을 호출하면, `Tick()`이 현재 ID로 `TryPopEvent()`를 호출한 뒤 `CChatNetClient::onRecv()`를 실행한다. `DispatchClientPacket()`은 `ResMessage`를 `HandleResMessage()`로, `MessageNoti`를 `HandleMessageNoti()`로 전달한다. 둘 다 Ready 및 본문을 검사하며, 응답은 자기 계정, 알림은 다른 양수 계정만 받는다. 콘솔은 두 콜백에서 같은 형식으로 닉네임과 메시지를 `CLogger`에 출력한다.

## 버퍼 수명과 전송 형식

| 구간 | 누가 버퍼를 유지하고 반환하는가 |
|---|---|
| 클라이언트 송신 | `SendPacket()`에 넘긴 공유 참조는 접수 시 큐에서 진행 중 I/O로 이동한다. 완료 또는 종료 정리 후 마지막 참조가 사라지면 힙 버퍼가 해제된다. 큐 등록 전 실패에는 큐 참조가 없다. |
| 클라이언트 수신 | Mailbox 이벤트가 버퍼의 공유 참조를 보유한다. 앱이 이벤트를 처리하거나 매니저가 파괴되어 마지막 참조가 사라지면 반환된다. |
| 서버 응답·공유 알림 | `MakePacket()`은 구조체의 `kPacketType`을 한 번 기록하고 자동 반환되는 `SendPacketPtr`를 돌려준다. 응답은 `SendPacket(sessionId, spPacket)`으로 제출하고, 알림은 `SendSector()`가 프레이밍을 한 번 한 뒤 공유한다. 큐가 각자의 참조를 유지하므로 콘텐츠는 수동으로 참조를 관리하지 않는다. 두 버퍼 중 하나라도 준비하지 못하면 어느 쪽도 제출하지 않는다. |
| 서버 수신 | 큐에서 꺼낸 View는 `OnRecv()` 호출 동안만 빌려준다. 테스트 채팅 콘텐츠만 기존 생성 디스패처를 유지하기 위해 `Dequeue()`로 본문을 기존 풀 직렬화 버퍼에 복사한다. Handle은 역직렬화된 구조체만 받는다. `CBaseContents`가 호출 뒤 View를 반환하고, 세션 종료 시 큐에 남은 View도 반환한다. 수신 완료 처리와 그 페이지를 참조하는 마지막 View가 모두 끝난 뒤에만 페이지가 풀로 돌아간다. |

패킷 하나는 고정 크기 버퍼 하나에 맞춰 작성한다. 공간이 부족한 필드는 쓰거나 커서를 옮기지 않고 실패로 기록한다. 패킷 생성에 실패하면 빈 핸들을 돌려준다. 이때 클라이언트 버퍼는 공유 참조로 해제되고 서버 버퍼는 풀에 반환된다. 여러 송신 버퍼를 한 번에 보내는 것과 개별 버퍼의 크기 제한은 별개이며, 버퍼를 늘리거나 패킷을 분할하지 않는다.

생성된 구조체는 패킷 본문만 직렬화하고, 패킷 ID는 빌더와 디스패치 경계에서 한 번씩 처리한다. 두 모드 모두 5바이트 `SPacketHeader`를 사용한다. 채팅 서버·콘솔·더미의 설정에서 `PACKET_MODE = Net;`이 기본이다. 양쪽을 `Lan`으로 맞추면 암호화·복호화와 체크섬만 건너뛰고 헤더 코드·길이·프레임 경계 검증은 유지한다. `Lan`은 신뢰하는 내부 연결용이며 기존 2바이트 LAN 프레임과 호환되지 않는다. `ResMessage`와 `MessageNoti`의 본문은 계정·ID·닉네임·메시지 순서로 동일하다. `ReqLogin`과 두 채팅 패킷의 ID·닉네임은 `std::wstring`이며 채팅 본문과 같은 `[uint32 UTF-16 코드 단위 수][UTF-16LE 데이터]` 형식이다. 종결 널과 패딩은 보내지 않는다. 앱은 ID·닉네임 각각 1~19코드 단위만 허용하고 포함된 널을 거부한다. `ReqLogin`의 64바이트 세션 키, 기존 패킷 ID와 Net 헤더는 그대로다. 기존 바이너리는 채팅 알림 분리와 호환되지 않으므로 서버·클라이언트를 함께 교체해야 한다.

### Net 모드의 체크섬 처리

- **송신:** `PreparePacket()`은 평문 본문 전체의 체크섬을 먼저 계산한 뒤, 체크섬 필드부터 본문 끝까지 인코딩한다. 다음 바이트의 인코딩이 이전 바이트의 상태에 의존하므로, 본문을 먼저 인코딩한 뒤 체크섬만 채울 수 없다.
- **수신:** 서버와 클라이언트 모두 `DecodeAndValidateChecksum()`으로 체크섬 필드를 먼저 복호화하고, 뒤따르는 본문은 복호화하면서 합산한다. 합계에는 체크섬 필드 자체를 넣지 않는다. 불일치하면 수신 큐나 메일박스에 등록하지 않고 연결을 종료한다. `Lan`에서는 이 처리를 건너뛴다.
- 기존 `Decoding()`은 비교·검증 테스트에만 사용한다. 검증 결과와 측정 범위는 [서버 패킷 경로 개선 계획](../Plan/Server/007_서버_패킷_경로_개선_계획.md#1-net-수신-복호화와-체크섬-통합)에 기록한다.
