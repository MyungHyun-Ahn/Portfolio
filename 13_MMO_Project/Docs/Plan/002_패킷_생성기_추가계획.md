## 제안: Python 유지, 입력만 YAML로 전환

| 선택 | 판단 |
|---|---|
| **Python + Jinja2 + YAML (권장)** | 기존 생성기의 렌더링 방식은 살리고 TXT 파서와 채팅용 템플릿만 교체한다. Python·Jinja2·YAML 파서는 생성기 실행 환경에만 필요하다. |
| Python + 기존 TXT | 초기 변경은 적지만 방향, 고정 배열 크기, 가변 필드의 길이 참조와 단위를 표현하려면 결국 자체 문법을 늘려야 한다. 기존 TXT는 참고로 남기고 새 프로젝트에서는 두 입력 형식을 함께 지원하지 않는다. |
| C# + YAML | .NET CLI 도구를 한 언어로 묶어 관리하기로 할 때 검토한다. YAML 입력은 가능하지만 기존 Python 로더·검증·렌더링 연결을 다시 작성하고 템플릿 재사용 방식도 결정해야 한다. C# 패킷 코드가 필요해지는 것만으로 생성기를 C#으로 바꿀 필요는 없다. |

YAML 파서 후보는 PyYAML이다. 일반 데이터만 읽는 로더를 사용하고, 중복 키와 허용하지 않는 문법은 별도로 거부한다. Jinja2 템플릿에는 검증 로직을 넣지 않는다. Python과 YAML은 생성 과정에서만 사용하며, 실행 중인 서버·클라이언트의 기존 UTF-16LE `.conf` 및 `CFileLoader`는 변경하지 않는다.

## YAML 스키마와 보존할 전송 계약

- **파일 단위:** `Common/Packet/Schema/<콘텐츠>/<패킷명>.yaml` 하나에서 `Common/Packet/Struct/<콘텐츠>/<패킷명>.g.h` 하나를 만든다. 허용 조합은 `Req + Res`, `Req + Res + Noti`, `Noti` 단독이다. `Req`나 `Res` 중 하나라도 있으면 둘 다 필요하다. `Req`는 클라이언트→서버, `Res`는 서버→클라이언트다. `Noti`는 응답 없는 단방향 패킷이며, 송신 방향을 YAML의 `direction`에 `client_to_server` 또는 `server_to_client`로 명시한다.
- **기존 채팅 이관:** `ReqMessage(5)`·`ResMessage(6)`를 `Chatting.g.h`의 `Req`·`Res` 쌍으로 매핑한다. 기존 `ResMessage`는 주변에 전파되지만 이번에는 ID·필드·전파 대상만 그대로 보존하고 별도 `Noti`는 만들지 않는다. 기존 열거값 이름과 새 구조체 이름은 별개다.
- **하트비트 이관:** 기존 `ReqHeartbeat(7)`을 `HeartbeatNoti(7)`로 바꾸고 `Schema/System/Heartbeat.yaml`에 `kind: noti`, `direction: client_to_server`로 단독 정의한다. `Struct/System/Heartbeat.g.h`에는 `SHeartbeatNoti`만 생성한다. ID 7, `WORD` 타입 + `INT64` 계정 번호, 클라이언트→서버 방향과 무응답 동작은 그대로 유지한다.
- `packets`와 `fields`는 순서가 있는 목록으로 둔다. 각 패킷의 `id`는 명시하고 선언 순서로 자동 부여하지 않는다. `ChatServer = 0`은 현재 열거형 호환용으로 남기되 송신 코드는 만들지 않는다. 실제 패킷 ID는 1~7을 유지한다.
- 처음부터 `int8`, `int16`, `int32`, `int64`, `uint8`, `uint16`, `uint32`, `uint64`를 모두 지원한다. 고정 바이트 배열과 고정·가변 UTF-16도 지원한다. 정수는 선언된 폭으로 리틀 엔디언 직렬화한다. 구조체 전체나 포인터를 복사하지 않는다.
- 고정 UTF-16 필드는 **코드 단위 수**를 선언한다. 기존 이름 필드는 각각 20코드 단위(40바이트, 널·패딩 포함), 세션 키 필드는 64바이트다. 문자열 값과 테스트용 키 값 자체는 스키마에 넣지 않는다.
- **가변 필드 제안:** YAML에는 문자열 필드 자체만 선언한다. 직렬화기가 필드 바로 앞에 리틀 엔디언 `uint32` 개수를 쓴다. UTF-16 문자열은 코드 단위 수 뒤에 코드 단위당 2바이트를 쓰고, 끝에 널을 추가하지 않는다. 가변 배열은 원소 수 뒤에 원소를 순서대로 쓴다(일반 가변 배열 지원은 후속). 고정 길이 이름·키·배열에는 접두부를 붙이지 않는다. 이 개수는 Net 헤더의 전체 패킷 길이와 별개다.
- 수신 시 `count <= remainingBytes / 2`를 확인한 뒤 UTF-16 바이트 수를 계산하고 할당·복사한다. 빈 메시지 금지와 최대 512바이트(256코드 단위)는 YAML이 아니라 채팅 송신·Handle의 정책으로 유지한다.
- **기존 코드 비교:** 05번 채팅 서버 `CProcessPacket.cpp:186–200`은 `WORD`로 UTF-16 바이트 수를 읽는다. 별도 `C:/Portfolio/MMO_Portfolio`의 `Tests/NetworkTests/Headless/Packet/FPacketWriter.cs`·`FPacketReader.cs`에도 4바이트 길이 접두부가 있지만, 문자열은 UTF-8 바이트 수를 기록하므로 여기서 제안한 UTF-16 코드 단위 수와 다르다.

```yaml
# Common/Packet/Schema/Chatting/Chatting.yaml
packets:
  - name: ReqMessage
    kind: req
    id: 5
    fields:
      - {name: account_no, type: int64}
      - {name: message, type: utf16}
  - name: ResMessage
    kind: res
    id: 6
    fields:
      - {name: account_no, type: int64}
      - {name: id, type: utf16_fixed, code_units: 20}
      - {name: nickname, type: utf16_fixed, code_units: 20}
      - {name: message, type: utf16}
```

| 패킷 | ID | `WORD` 타입을 포함한 바이트 수, Net 헤더 제외 |
|---|---:|---:|
| `ReqLogin` | 1 | 154 |
| `ResLogin` | 2 | 11 |
| `ReqSectorMove` / `ResSectorMove` | 3 / 4 | 각각 14 |
| `ReqMessage` | 5 | 기존: 12 + 메시지 바이트 수 / 제안: 14 + 메시지 바이트 수 |
| `ResMessage` | 6 | 기존: 92 + 메시지 바이트 수 / 제안: 94 + 메시지 바이트 수 |
| `HeartbeatNoti` (기존 `ReqHeartbeat`) | 7 | 10 (`WORD` 타입 + `INT64` 계정 번호) |

생성기는 **Net 헤더의 코드·길이·인코딩·체크섬을 만들지 않는다.** 현재 `NetworkLib` 경로와 풀 버퍼 할당·반환 및 참조 수명 계약을 유지한다.

4바이트 제안을 적용하면 두 메시지의 접두부가 `uint16` 바이트 수에서 `uint32` 코드 단위 수로 바뀌므로 신·구 클라이언트와 서버를 섞어 쓸 수 없다. 패킷 ID·문자열 인코딩·나머지 패킷의 본문 바이트는 유지한다.

## 구조체 직렬화와 ISerializable

- 생성된 구조체는 `MHLib::serialization::ISerializable<false>`를 구현한다. `Serialize`·`Deserialize`는 `CSerializableBuffer<FALSE>&`를 직접 받고 자기 필드만 `<<`·`>>`로 쓴다. 기본형은 버퍼가 직접 복사하고, `ISerializable` 객체용 연산자는 같은 버퍼로 객체의 `Serialize`·`Deserialize`를 호출한다. 별도 코덱이나 채팅 버퍼 어댑터는 두지 않는다.
- `MakePacket`은 풀에서 할당한 버퍼에 `*pBuffer << packetId << packet`으로 ID와 본문을 쓴다. 수신 측은 ID를 한 번만 읽고 `message >> packet`으로 본문을 읽는다. 구조체 메모리를 통째로 복사하지 않는다. 기본형과 UTF-16 필드는 리틀 엔디언 환경을 컴파일 시 확인하고 기존 패킷과 같은 바이트를 쓴다.
- 버퍼 한 개에는 정상 패킷 한 개가 들어간다. 여러 송신 버퍼를 모아 보내므로 패킷 버퍼의 `resize`는 구현하지 않는다. 필드가 남은 공간을 넘으면 커서를 옮기지 않고 실패 상태로 표시하고, 뒤 연산도 수행하지 않는다. 송신 빌더는 실패한 버퍼를 풀에 반환하고, 수신 측은 실패 또는 후행 바이트가 있는 패킷을 Handle 전에 거부한다. 연결 종료는 버퍼가 아니라 기존 수신 경로가 처리한다.
- **기존 도구에서 확인한 범위:** `PacketList.txt`에 실제 쓰인 타입은 `CHAR`, `BYTE`, `USHORT`, `INT`, `DWORD`다. `CodeGenerator.py`는 타입 문자열을 검증하지 않고 템플릿에 넘기며, `templates/CGenPacket.cpp`는 필드를 `<<`로 잇는다. 당시 버퍼에는 이들에 대응하는 스칼라 외에 `short`, `long`, `float`, `__int64`, `double` 등의 연산자도 있지만, 그것이 생성기의 배열·문자열·중첩 객체 지원을 뜻하지는 않는다. 기존 도구에 `ISerializable` 계약이나 필드별 역직렬화 생성은 없다.
- **정수 매핑:** YAML 정수 타입은 같은 폭과 부호의 C++ 고정 폭 정수(`int8` → `std::int8_t`, `uint64` → `std::uint64_t` 등)로 매핑한다. 가변 필드의 `uint32` 접두부는 버퍼의 문자열 연산자가 처리하며 YAML에서 별도 필드로 선언하지 않는다.
- **중첩 타입은 확장 지점만:** 이후 패킷에 넣을 `GameData` 타입은 YAML에 구체 타입을 명시하고, 허용 목록의 타입만 `ISerializable`을 구현하는지 컴파일에서 확인한 뒤 그 객체의 두 메서드에 위임하는 방향을 권장한다. `ISerializable` 상속만으로 YAML에서 임의 타입을 선택·생성하거나 메모리 배치를 전송하지 않는다. 이번에는 GameData 연동, 범용 객체/컨테이너 스키마, 런타임 타입 등록을 구현하지 않는다. 인터페이스의 합성 가능성은 작은 테스트용 중첩 타입으로 확인한다.

## 파일 배치

아래는 구현된 YAML·생성 헤더·도구 프로젝트 배치다. `BattlePass`와 `Gacha`는 향후 콘텐츠 예시다.

```text
13_MMO_Project/

    Packet/
      Schema/
        Chatting/               # Login.yaml, SectorMove.yaml, Chatting.yaml
        System/                 # Heartbeat.yaml
        BattlePass/             # 향후 예시
        Gacha/                  # 향후 예시
      Struct/                   # 패킷 구조체를 여기에 등록
        Chatting/
          Login.g.h             # Req + Res
          SectorMove.g.h        # Req + Res
          Chatting.g.h          # Req + Res (Noti 없음)
          ChattingPacketAll.g.h # Chatting Packet Include 모음
        System/
          Heartbeat.g.h         # 클라이언트→서버 Noti 단독
          SystemPacketAll.g.h   # System Packet Include 모음
        PacketTypes.g.h         # 공용 패킷 ID
        IncludePacketAll.g.h    # 모든 콘텐츠의 패킷 Include 모음
  Tests/Chatting/
    Client/Generated/PacketHandler/ # 클라이언트 송신 빌더·수신 디스패처·Handle 선언
    Server/Generated/PacketHandler/ # 서버 송신 빌더·수신 디스패처·Handle 선언
  Tools/
    PacketGenerator/        # Python, GeneratePackets.bat, 템플릿, Generate.vcxproj
```

- `Common`은 서버·클라이언트가 함께 참조하는 영역이다. `Struct`에 기능별 구조체와 `Serialize`·`Deserialize`, 공용 `PacketTypes.g.h`를 생성한다. 기존 `Tests/Chatting/Common`의 콘솔·설정 코드는 이관하지 않는다.
- 각 `<콘텐츠>PacketAll.g.h`는 해당 콘텐츠의 구조체 헤더만 모으고, `IncludePacketAll.g.h`는 전체 콘텐츠 집계 헤더와 공용 패킷 ID 헤더를 모은다. `#include`가 있는 생성 헤더는 이 집계용 헤더로 한정한다. 구조체 헤더에는 `#include`를 넣지 않고, 생성 헤더를 PCH에 넣지 않는다. 소비 `.cpp`에서 자체 PCH와 `ISerializable` 등 선행 정의를 공급한 뒤 집계 헤더를 포함한다.
- 스키마가 번호·필드 순서·타입·길이의 단일 원본이다. `CommonProtocol.h`의 채팅 상수는 유지하고, `EPacketType`은 `PacketTypes.g.h`에만 정의한다. 각 실행 프로젝트는 공용 출력과 자기 `Generated/PacketHandler`의 송신 빌더·수신 디스패처·Handle 선언만 참조한다. 생성 `.cpp`는 소비 프로젝트의 `pch.h`를 첫 include로 둔다.

## 서버·클라이언트 Handle 연결

공용 구조체는 직렬화·역직렬화를 담당한다. 각 프로젝트에 생성된 송신 빌더는 자기 송신 방향의 패킷을 `Serialize`하고, 수신 디스패처는 자기 수신 방향의 패킷을 `Deserialize`한 뒤 수동 Handle을 호출한다.

1. **서버:** `CBaseContents` 수신 큐 → `CChatContents::OnRecv` → 서버 디스패처 → `CProcessPacket`의 `HandleReqLogin`, `HandleReqSectorMove`, `HandleReqMessage`, `HandleHeartbeatNoti`. 디스패처는 공용 구조체의 `Deserialize`를 호출하고 `sessionId`와 파싱 결과를 넘긴다. 로그인·섹터·배포·하트비트 갱신 로직과 수신 결과 매핑은 유지한다.
2. **클라이언트:** `NetworkLib::CNetClient` → `CConsoleChatClient::OnRecv` → 클라이언트 디스패처 → `HandleResLogin`, `HandleResSectorMove`, `HandleResMessage`. 로그인 상태·계정 및 섹터 일치·후속 송신·채팅 출력과 기존 `bool` 결과 전달은 유지한다.
3. **Handle 선언 생성:** 각 프로젝트의 `Generated/PacketHandler`에 타입이 명시된 Handle 인터페이스를 생성하고, 기존 `CProcessPacket`과 `CConsoleChatClient`가 수동 파일에서 구현한다. 디스패처는 인터페이스에만 의존하고, 콘솔/서버 콘텐츠 구현을 포함하거나 전역 등록을 사용하지 않는다. 새 수신 패킷을 추가해 Handle 구현이 빠지면 빌드에서 드러나게 한다.
4. **파싱과 수명:** 서버는 `CChatContents::OnRecv`에서 `WORD` 타입을 한 번 읽고 타입과 남은 본문을 디스패처로 전달한다. 클라이언트는 디스패처에서 타입을 한 번 읽는다. 송신과 수신 연결은 패킷의 실제 방향을 따른다. 모르는 ID, 반대 방향, 잘림·후행 바이트, 길이 제약 불일치 등 기존 형식 오류는 Handle 전에 거부한다. 이름의 널 검사 등은 해당 패킷의 기존 조건을 유지한다. 파싱 결과는 동기 Handle 호출에서만 참조하고 원본 수신 버퍼는 저장하거나 해제하지 않는다. 수신 큐, 실행 스레드, `CLogger`, Net 프레이밍과 풀 수명은 변경하지 않는다.

## 생성기 출력 인자와 BAT

`GeneratePackets.py`는 스키마 입력과 **공용·클라이언트·서버 출력 경로 3개**를 이름 있는 인자로 받는다. 도구 본체에 채팅 프로젝트 경로를 넣지 않고, 채팅용 수동 생성 경로는 BAT에 둔다.

| 인자 | 현재 프로젝트 경로 |
|---|---|
| `--schema-dir` | `Common/Packet/Schema` |
| `--common-out` | `Common/Packet/Struct` |
| `--client-out` | `Tests/Chatting/Client/Generated/PacketHandler` |
| `--server-out` | `Tests/Chatting/Server/Generated/PacketHandler` |

- `Tools/PacketGenerator/GeneratePackets.bat`에는 현재 채팅용 경로와 Python 호출만 둔다. BAT 위치(`%~dp0`) 기준으로 경로를 계산하고 공백이 있는 경로도 인용한다. `start` 없이 한 번만 동기 실행하며 Python의 종료 코드를 그대로 반환한다. 검증·렌더링·파일 복사/정리는 BAT에 넣지 않는다. 다른 출력 경로를 쓰는 호출자는 Python CLI에 직접 전달할 수 있다.
- 세 출력 루트는 서로 또는 스키마 입력과 겹치지 않게 한다. 공용 출력은 `Struct` 안의 지정된 루트·콘텐츠별 `.g.h`에 한정한다. `Schema`와 수동 파일은 덮어쓰거나 지우지 않는다. 세 묶음 모두 검증·렌더링에 성공한 뒤 반영하고, 성공 기록은 모두 반영된 뒤에만 갱신한다.

## Generate 프로젝트와 수동 생성

- `Generate`는 `Tests/Chatting/Chatting.sln`에 남겨 두되 기본 솔루션 빌드에서는 제외한다. `Generate.vcxproj`에는 `GeneratePackets.bat`만 등록하며, 단독 빌드도 BAT를 호출하지 않는다. `ChatServer`와 `ChatClient`에서도 `Generate` 프로젝트를 참조하지 않는다.
- YAML·템플릿 변경을 적용하거나 산출물을 복구할 때는 `Tools/PacketGenerator/GeneratePackets.bat`를 직접 실행한다. Python과 `requirements.txt`의 의존성은 이때만 필요하다. 수동 생성에 실패하면 입력 오류를 확인하고 수정한 뒤 다시 생성한다. 일반 빌드는 YAML 변경을 확인하거나 산출물을 갱신하지 않는다.
- 서버·클라이언트는 기존 생성 C++ 파일을 그대로 컴파일한다. 각 프로젝트와 필터에는 자기 `Generated/PacketHandler` 파일을 유지한다. 정상 빌드에 필요한 생성물은 `.packet-generator.json`과 함께 소스와 같이 관리하며 손으로 수정하지 않는다. 출력이 동일하면 BAT 실행 시에도 파일을 다시 쓰지 않는다.

## 진행 순서와 확인 기준

1. **기준 고정:** 실제 `CGenPacket`, `CConsoleChatClient`, `CProcessPacket`을 대조해 패킷별 필드 순서·길이·기존 API를 확정한다. 생성 코드가 없는 현재 상태에서 비교할 본문 바이트를 확보한다. Net 헤더나 난수 키는 본문 비교에서 제외한다.
2. **`Login.yaml` 한 기능으로 연결:** `Login.g.h`의 구조체를 `ISerializable`과 버퍼 연산자로 연결한다. 생성 송신 바이트를 기존 154·11바이트와 비교하고 구조체 역직렬화 결과도 검증한다. 서버 `HandleReqLogin`에 `sessionId`가 전달되고, 응답을 받은 클라이언트 `HandleResLogin`에서 기존 섹터 요청이 이어지는지 확인한다.
3. **나머지 패킷 지원:** 채팅·섹터·하트비트로 확대한다. Req/Res 짝 누락, Noti 방향 누락·오류, 중복 ID·이름·종류, 출력 이름 충돌, 잘못된 타입·고정 길이, 알 수 없는 키는 출력 전에 거부한다. 허용된 세 조합과 Noti 방향에 맞는 Handle 선언을 확인한다. `Chatting`·`System` 집계 헤더에는 각 콘텐츠의 구조체만, 전체 집계 헤더에는 두 콘텐츠와 공용 ID가 포함되는지 확인한다. YAML 앵커·별칭·사용자 태그는 지원하지 않는다. 지정 경로 외 쓰기 금지, 재생성 동일성, 잘못된 입력에서 기존 결과 보존을 확인한다.
4. **실제 프로젝트 연결:** BAT 수동 호출로 스키마 변경과 산출물 누락을 반영할 수 있는지 확인한다. `Generate` 단독 빌드와 x64 Debug 채팅 빌드는 BAT를 호출하지 않아야 한다.
5. **최종 확인:** 채팅에서 쓰지 않는 타입까지 포함해 정수 8종의 생성 코드를 컴파일하고, 각 타입의 최솟값·최댓값·0을 직렬화해 예상 리틀 엔디언 바이트와 비교한 뒤 역직렬화 결과를 확인한다. 로그인·섹터·하트비트는 기존 본문과 바이트를 비교한다. 메시지에 새 형식을 적용하면 `uint32` 접두부와 동일한 UTF-16 내용, 1·256코드 단위 경계, 한글·이모지, 잘린 접두부·본문, 남은 바이트를 넘는 개수와 후행 바이트를 검증한다. 빈 메시지와 256코드 단위 초과는 채팅 정책에서 거부되는지 확인한다. 실제 로컬 클라이언트 두 개로 로그인 → 섹터 진입 → 양방향 채팅 및 기존 무응답 하트비트를 확인한다.

## 구현 및 검증 결과

- `.packet-generator.json`은 각 출력 루트에서 생성 파일의 소유 목록과 해시를 기록한다. 미관리 파일 또는 수동으로 변경한 생성 파일과 충돌하면 생성을 중단한다.
- `Tests/PacketGenerator`의 Python 테스트 12개와 `SerializableBufferTests.cpp`가 통과했다. 기본형 8종, 중첩 객체, 고정 배열, UTF-16 길이 경계, 정확히 맞는 쓰기, 실패 시 커서 유지와 풀 재할당 초기화를 확인했다.
- 직접 버퍼 방식으로 전환한 뒤 생성 송신 코드에서 `ResLogin`과 한글·이모지 `ReqMessage`를 예상 바이트와 비교했다. 서버 디스패처가 정상 요청만 Handle에 넘기고, 잘림·후행 바이트를 거부하는지와 용량 초과 송신 시 풀 사용량이 복구되는지도 확인했다.
- `Portfolio.sln`과 `Chatting.sln`의 Debug x64 MSBuild가 통과했다. 채팅 솔루션은 Python을 사용할 수 없도록 설정한 상태에서 빌드했고, 실행 중인 기존 `ChatServer.exe`를 건드리지 않도록 서버 출력 파일명만 임시로 바꿨다. IDE 및 두 실제 클라이언트의 채팅은 미검증이다.
- 생성 패킷이 기존 수동 송신 빌더를 대체하므로 채팅 프로젝트의 `CGenPacket.h/.cpp`를 삭제했다. 보존 프로젝트의 원본은 변경하지 않았다.

## 후속 계획: 패킷 송신 함수 자동 생성

**상태: 구현, 생성기 테스트 15개, 네이티브 빌드 및 Release 루프백 채팅 검증 완료.** 로컬 로그인·섹터 진입·양방향 채팅을 확인했다. 기존 5단계 완료 범위와 구분한다.

- YAML의 `kind`, `direction`, `fields`를 사용해 각 프로젝트의 `Generated/PacketHandler`에 `CChatNetClient`와 `CServerPacketSender`의 송신 함수 선언·정의를 생성한다. 이름은 `Send<Req|Res|Noti><기능>`을 따른다. 함수는 필드 값을 받아 구조체를 채우고 기존 `MakePacket*()`과 전송 경로에 넘긴다. `IClientPacketHandler`와 `IServerPacketHandler`는 수신 전용으로 유지한다.
- `CConsoleChatClient`는 `CChatNetClient`를 공개 상속한다. `CChatNetClient`는 `CNetClient`를 공개 상속해 현재 연결에서 송신하고, `IClientPacketHandler`를 비공개 상속해 수신을 디스패치한다. 콘텐츠는 `client.SendReqMessage(accountNo, text)`처럼 호출하고 `HandleRes*()`를 구현한다. 서버의 `CProcessPacket`은 `CServerPacketSender`를 공개 상속하며, `SendResLogin(sessionId, status, accountNo)`처럼 대상을 인자로 받는다.
- 서버의 단일 대상 송신은 Net 헤더를 준비하는 공통 경로를 사용한다. 로그인 성공과 섹터 이동은 기존처럼 `MakePacket*()`으로 버퍼를 먼저 확보하고 상태를 등록한 뒤 `submitPreparedPacket()`으로 송신한다. 기존 `CNetServer::SendPacket()`의 반환 계약과 패킷 ID·본문 형식은 바꾸지 않는다.
- 생성된 모든 서버 `Send*`는 직렬화와 Net 헤더 준비가 끝난 `pPacket`을 **호출자 소유 참조 1개**와 함께 반환한다. 버퍼 준비 실패 시 `nullptr`을 반환한다. 이 값은 첫 전송의 성공을 뜻하지 않는다. 채팅 응답은 `SendSector()`에서 같은 버퍼를 재사용하고, 나머지 응답은 재사용 없이 기존 `DecreaseRef()`/`Free()` 규칙으로 호출자 참조를 반환한다.
- **확인 기준:** 방향별 송신 함수와 필드 인자가 올바르게 생성되고 반대 방향 송신 함수는 생성되지 않는지 확인한다. 클라이언트·서버 생성물을 빌드하고 로컬 로그인·섹터 진입·양방향 채팅을 확인한다. 섹터 송신은 버퍼를 한 번만 준비하고, 첫 대상에 큐 등록이 되지 않거나 첫 송신이 먼저 완료돼도 호출자가 참조를 내리기 전에는 버퍼를 재사용할 수 있어야 한다.
- **제외:** 서버 버퍼 참조의 RAII 전환, 연결 라이프사이클·Mailbox 리팩터링, 수신 핸들러 본문 생성. 이번 후속 계획은 `Send*` 생성과 그 함수의 연결에 한정한다.
