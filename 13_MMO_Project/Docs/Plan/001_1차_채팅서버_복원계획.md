# 1차 작업 계획: 채팅 서버 복원

## 목표와 현재 상태
- `05_Multi_IOCP_ChatServer`의 채팅 구현을 참고하여 `13_MMO_Project`에 채팅 서버를 복원한다.
- 네트워크 구현은 05번 프로젝트에 포함된 구버전이 아니라 `12_NetworkLib`를 사용한다.
- 콘솔 클라이언트 여러 개가 접속하여 서로 메시지를 주고받을 수 있으면 1차 목표를 달성한다. 완성된 MMO나 무결점 네트워크 라이브러리 개발이 목표는 아니다.
- 현재 상태는 **1~5단계 완료, 6단계 클라이언트 네트워크 분리·공용 IOCP·콘솔 송수신 연결 구현 및 클라이언트 코드 검토 완료**다. 4단계 실제 채팅은 사용자가 확인했다. DummyClient는 미착수이고 ChatServer·ChatClient의 PCH 정리는 보류한다.
- [1단계 변경 내용·이름 대응·빌드 방법·검증 결과](../Server/001_라이브러리_이전_정리.md)

## 이전 원칙과 작업 범위
- 원본 디렉터리는 그대로 보존한다. 여기서 이전은 원본을 삭제하는 이동이 아니라 새 프로젝트로의 복사를 뜻한다.
- `11_MHLib`는 `Server/MHLib/`로, `12_NetworkLib/NetworkLib/`는 `Server/NetworkLib/`로 가져온다. 소스·필수 설정·프로젝트 파일을 대상으로 하며 `.vs`, 중간 산출물, 기존 실행 파일은 가져오지 않는다.
- 채팅 콘텐츠는 `05_Multi_IOCP_ChatServer/IOCP_ChatServer/IOCP_CHAT_SERVER/`를 기준으로 복원한다. 해당 프로젝트의 네트워크·풀 구현을 별도로 중복 복사하지 않는다.
- 원본 디렉터리는 수정하지 않으며, `13_MMO_Project`에 가져온 복사본에는 [공통 코딩 규칙](../Rule/001_공통_코딩컨벤션.md)과 [C++ 코딩 규칙](../Rule/002_Cpp_코딩컨벤션.md)의 네이밍·PCH 규칙을 적용한다.
- 타입·함수·변수·멤버·상수·소스 파일명은 코딩 규칙에 맞추고, 선언·정의·호출부·include 경로·프로젝트 및 필터 참조를 함께 갱신한다. 이름 변경과 패킷 번호·전송 필드·설정 키 등 외부 계약 변경은 구분하며, 외부 계약은 그대로 유지한다.
- 원본의 처리 순서, 알고리즘, 소유권·스레딩 방식과 주석 스타일은 최대한 유지한다. 컨벤션 적용을 이유로 동작 변경·스마트 포인터로의 일괄 치환·새 추상화 도입·기존 결함 수정을 함께 진행하지 않는다.
- 새 주석은 사용자가 기존 코드에 작성한 것처럼 짧은 한국어 설명을 기본으로 한다. 기존 주석을 불필요하게 다시 작성하지 않는다.
- 복사본의 경로·네임스페이스·프로젝트 참조와 서로 달라진 인터페이스는 컨벤션 적용 및 채팅 연결에 필요한 범위에서 맞춘다. 이름·include 배치 변경과 연결을 위한 동작 변경은 검토 시 구분하여 설명한다. 원본 파일은 수정하지 않는다.
- 원본에서도 발생할 수 있는 결함은 이번 단계에서 선제적으로 수정하지 않는다. 발견 사항은 필요하면 이 문서에 간단히 기록하고 후속으로 미룬다.
- 단, 빌드·접속·정상 메시지 교환을 막는 문제와 새 연결 코드가 만든 문제는 구분하여 보고하고 최소한으로 처리한다. 큰 구조 변경이 필요하면 사용자와 먼저 논의한다.
- 기존 결함을 숨기기 위해 검증 결과를 성공으로 표시하거나 진단을 일괄 억제하지 않는다.

### 모니터링 서버 관련 코드의 제외
- 별도 모니터링 서버는 이번 복원과 이후 개발에서 사용하지 않는다.
- 모니터링 서버 전용 클라이언트, 접속·재접속, 지표 전송, 전용 설정·패킷·이벤트와 프로젝트 참조는 가져오지 않거나 새 프로젝트의 복사본에서 제거한다. 채팅과 공용으로 사용하는 항목은 실제 사용처를 확인한 뒤 전용 부분만 제외한다.
- 프로세스 내부의 모니터 코드, 카운터·성능 지표 수집, 콘솔·로그 출력은 유지한다. 지표를 수집하는 기능과 외부 모니터링 서버로 보내는 기능을 구분한다.
- `CLanClient` 등 범용 통신 구현은 전용 코드로 간주하여 삭제하지 않는다. 특히 CNetClient 구현의 참고 코드는 유지한다.
- 제외 작업도 원본 디렉터리에는 적용하지 않는다. 이후 구현 결과에서 제외한 전용 코드와 유지한 모니터 코드를 구분하여 보고한다.

## 빌드 기준
- IDE는 Visual Studio 2026, `PlatformToolset`은 `v145`를 사용한다. 기존 `v143` 설정은 새 프로젝트 안의 복사본에서 변경한다.
- MHLib 요구 사항과 NetworkLib의 현재 설정에 맞춰 C++20을 유지한다. Windows SDK 등 다른 설정은 불필요하게 함께 변경하지 않는다.
- 우선 `x64 / Debug`를 기준으로 빌드·동작을 확인한다. 다른 구성의 전체 검증은 1차 완료의 필수 조건으로 추가하지 않는다.
- 구현 시작 시 설치된 VS 2026·v145·SDK를 확인한다. 현재 계획 작성만으로 설치나 빌드 성공을 확인한 것은 아니다.
- 대상별 PCH와 증분 빌드를 유지하고, 출력·중간 디렉터리는 새 프로젝트 안에 둔다. 원본 디렉터리에는 빌드 산출물을 쓰지 않는다.
- PCH 사용 대상은 자기 프로젝트의 PCH를 `.cpp` 첫 include로 둔다. 안정적인 헤더·표준 라이브러리만 PCH에 모으고, 다른 프로젝트의 PCH나 컴파일된 PCH 산출물을 공유하지 않는다.
- 일반 헤더의 `#include`는 제거하고 포인터·참조 의존성은 전방 선언을 우선한다. 값 멤버·상속·템플릿에 필요한 완전한 타입 정의는 PCH 또는 사용하는 `.cpp`의 선행 include에서 순서에 맞게 공급한다. PCH용 include 집계 헤더는 예외이며, include를 자동 정렬하지 않는다.
- 원본의 인코딩을 읽기 전용으로 확인한다. 이전 과정에서 인코딩·개행을 일괄 변환하지 않고, 빌드에 꼭 필요한 변경은 내용 변경과 구분하여 알린다.

## 진행 순서
각 단계는 하나의 검토 단위로 진행하고, 결과를 사용자가 검토한 뒤 다음 단계로 넘어간다. 이번에는 사용자 승인에 따라 2·3단계를 하나의 구현·검토 단위로 묶었다.

### 1. 라이브러리 복사와 빌드 연결
- [x] MHLib와 NetworkLib의 실제 파일·의존성과 PCH 구성을 확인한다.
- [x] 지정한 새 경로로 필요한 파일을 복사하고 v145 프로젝트·include 경로·참조를 연결한다.
- [x] 모니터링 서버 전용 의존성은 제외하고, 내부 모니터 코드와 범용 통신 코드는 유지한다.
- [x] 복사본의 네이밍과 PCH/include 배치를 코딩 규칙에 맞추고 관련 선언·사용처·프로젝트 및 필터 참조를 함께 확인한다.
- [x] NetworkLib의 증분 빌드가 가능한 상태를 확인한다.

결과: VS 2026 / v145 / C++20 / x64 Debug 빌드, 별도 소비 코드의 전체 라이브러리 링크·실행, 변경 없는 증분 빌드를 확인했다. 초기 이전 당시 남긴 경고 5건은 이후 사용자 승인으로 원인을 수정했으며 현재 해당 구성의 빌드는 경고·오류 0건이다. 원본 결함의 전수 수정과 네트워크 기동·채팅 검증은 하지 않았다.

### 2. 채팅 서버 복원
- [x] `CChatServer`를 `NetworkLib::CNetServer` 상속으로 복원한다.
- [x] 05번 프로젝트의 플레이어, 섹터, 패킷 처리·생성, 필요한 설정을 최대한 그대로 가져온다.
- [x] 가져온 채팅 코드에도 네이밍·PCH 규칙을 적용하되, 기존 채팅 동작과 전송 계약은 유지한다.
- [x] 로그인, 섹터 등록·이동, 메시지 배포 등 기존 채팅 흐름을 유지한다. 테스트 클라이언트는 채팅 전 같은 섹터로 진입하도록 한다.
- [x] NetworkLib의 실제 수신 처리와 채팅 처리 연결을 확인하고 최소한의 호환 코드를 적용한다.
- [x] 서버가 시작되어 클라이언트 접속을 기다리는 상태까지 확인한다.

현재 확인한 연결 주의점: 05번 채팅은 `OnRecv` 콜백에서 패킷을 처리하지만, 12번 NetworkLib의 `CNetSession::RecvCompleted`는 `CSerializableBuffer<FALSE>`를 수신 큐에 넣는다. 헤더의 `OnRecv` 선언만 보고 같은 방식으로 연결됐다고 가정하지 않는다. 기존 `CBaseContents` 소비 경로와 버퍼 수명을 먼저 추적하고, 기존 구조를 우선 활용하여 채팅 처리까지 연결한다. 이를 새로운 콘텐츠 런타임 설계 작업으로 확대하지 않는다.

### 3. CNetClient와 콘솔 클라이언트
- [x] `12_NetworkLib`의 `CLanClient`와 `CNetServer`를 참고하여 `Server/NetworkLib/`의 `NetworkLib::CNetClient`를 구현한다.
- [x] 접속·송신·수신·연결 해제와 버퍼 수명은 기존 코드의 방식을 우선 따른다.
- [x] CNetClient와 콘솔 클라이언트도 동일한 네이밍·PCH 규칙을 적용하고, 주석은 기존 코드의 설명 스타일에 맞춘다.
- [x] LAN 전용 프레이밍을 그대로 사용하지 않고, 서버와 같은 NetHeader·직렬화·인코딩/체크섬 계약으로 통신한다.
- [x] Config에서 접속 정보와 사용자 식별 정보를 읽고, 로그인·초기 섹터 진입 후 콘솔에 입력한 메시지를 전송하고 수신 메시지를 출력한다.
- [x] 별도 로그인 서버·DB·Redis 없이 이번 테스트 안에서 기존 채팅 프로토콜을 실행한다. 운영용 인증 완성을 요구하지 않는다.

### 2·3단계 결과와 검토 위치
- `Tests/Chatting/Server/CChatServer`는 접속을 `CChatContents`에 넘긴다. `CChatContents`는 기존 `CBaseContents`의 프레임에서 입장·퇴장·수신을 순서대로 처리한다. 플레이어·섹터·패킷 처리·생성의 역할은 기존 방식에 맞췄고, 맵과 섹터 접근은 같은 콘텐츠 프레임 안에서 수행한다.
- `NetworkLib::CNetClient`는 단일 접속에 필요한 IOCP 송수신·완료 처리·연결 해제를 담당한다. `CConsoleChatClient`가 로그인 응답 후 섹터 진입을 요청하고 채팅·하트비트 패킷을 처리한다. 종료 시 자신의 pending IO를 취소·소비하고 worker를 join한 뒤 자원을 정리한다.
- 채팅 패킷 정의는 `Tests/Chatting/Common/CommonProtocol.h`에 두고, Net 헤더 준비는 `Server/NetworkLib/NetPacket.cpp`에서 처리한다. 패킷 번호·필드 순서·UTF-16 이름 길이·NetHeader 계약은 유지했다. 하트비트는 원본 실제 처리 코드의 `Type + AccountNo`를 따른다.
- 정상 채팅 연결에 필요하여 Net 직렬화 버퍼만 128에서 1024바이트로 확대했다. LAN 버퍼는 유지했다. 복사본의 `CGenPacket`은 바이트 단위인 `messageLen`을 다시 `sizeof(WCHAR)`배로 복사하던 부분만 바로잡았다. 공유 응답은 전송 큐에 넣기 전에 한 번만 인코딩한다.
- 고정 테스트 키를 사용하므로 서버와 클라이언트의 접속 IP는 `127.0.0.1`로 제한한다. 운영용 인증이 아니며 외부 로그인 서버·DB·Redis·모니터링 서버는 추가하지 않았다.
- Config 전환 전 채팅 복원본의 v145 / C++20 / x64 Debug 솔루션 Build는 경고·오류 0건이었다. 기존 PCH·중간 출력 경로를 재사용했다. 해당 실행 파일로 두 클라이언트의 로그인·같은 섹터 진입·양방향 한글/이모지 메시지·EOF 및 종료 명령·비루프백 인자 거부를 확인했다.
- 초기 통합본에서는 최대 512바이트 메시지, 연속 메시지 순서, 중복 계정 거부, 같은 계정의 재접속도 확인했다. 이후 변경되지 않은 통신 경로의 앞선 검증으로 구분하여 보존하며, 최종 실행 파일에서 전부 반복했다고 표시하지 않는다.
- 실제 콘솔 입력 함수의 대리쌍 분할 입력·백스페이스·Enter/EOF와 실제 파이프 입력은 제어된 네이티브 입력 검사로 확인했다. 사람이 GUI 콘솔을 직접 조작한 검증과는 구분한다. 채팅 복원 당시 독립 소스 검토는 수정 9개 파일 재검토와 바이트가 동일한 이전 21개 파일 검토를 합쳐 완료했다.
- `CNetClient`를 NetworkLib로 옮긴 뒤 `Portfolio.sln`과 `Chatting.sln`의 x64 Debug 빌드를 확인했다. 이후 사용자가 Config 버퍼의 널 문자 공간을 수정하고 변경 코드를 검토했다. 해당 수정 이후의 양방향 채팅은 이 완료 처리에서 다시 검증하지 않았다.
- 서버의 `/exit`와 EOF는 프로세스 종료 경계다. 기존 `CNetServer::Stop`과 정적 풀의 정상 종료를 완성한 것은 아니다. 참조 관리·일반 버퍼 경계·풀/링버퍼 소멸·PDH 선택의 보류 항목은 수정하지 않았다.

### 시작 설정의 Config 전환
- 사용자 요청에 따라 서버·클라이언트 진입점을 모두 `int main(void)`로 변경하고, 실행 인자 파싱을 제거했다. 공용 `Tests/Chatting/Config.h/.cpp`의 `SChatConfig`와 `LoadConfig`에서 기존 `MHLib::utils::CFileLoader::Parse/Load`를 사용한다.
- 서버 원본 설정은 `Tests/Chatting/Server/ServerConfig.conf`, 클라이언트 원본 설정은 `Tests/Chatting/Client/ClientConfig.conf`다. 빌드할 때 각 실행 파일 옆에 복사하고, 실행 시 현재 작업 디렉터리가 아니라 실행 파일 디렉터리를 기준으로 읽는다.
- 기존 로더와 동일하게 설정 파일은 **UTF-16LE BOM** 형식이다. 서버는 `IP`, `PORT`, 클라이언트는 이에 더해 `ACCOUNT_NO`, `NICKNAME`, `SECTOR_X`, `SECTOR_Y`를 읽는다. `ACCOUNT_NO = 0`은 프로세스 ID 자동 선택이므로 같은 설정으로 클라이언트 여러 개를 실행할 수 있다. 양수 계정 번호도 지정할 수 있다.
- 필수 설정 누락·잘못된 인코딩·숫자 범위 초과·비루프백 IP는 접속 전에 `CONFIG ERROR`와 종료 코드 2로 거부한다. 설정 실패를 기본값으로 대체하지 않는다. 기존 로더 자체의 임의 손상 파일·구문 전수 방어를 완성한 것은 아니다.
- 보류 전에는 실제 설정 파일을 바꿔 포트·64비트 계정·닉네임·섹터 적용, 자동 계정의 다중 실행, 설정 실패를 확인했다. `diagnostics` 경로 수정 후 현재 의존성으로 다시 빌드하고, 인자 없는 두 클라이언트의 설정 적용·양방향 한글/이모지 채팅·종료·비루프백 설정 거부를 확인했다. 현재 x64 Debug 빌드는 경고·오류 0건이며 Config 변경 14개 파일의 독립 소스 검토를 완료했다.
- 원본 프로젝트와 사용자의 컨벤션 문서는 수정하지 않았다. 라이브러리의 정상 종료·참조 관리·일반 버퍼 경계 등 기존 보류 항목은 Config 전환에 포함하지 않았다.

## 완료 기준과 제외 범위
- 지정된 라이브러리를 사용하는 CChatServer와 CNetClient 기반 콘솔 클라이언트가 v145로 빌드되고, 여러 콘솔 사이에서 실제 채팅이 된다.
- 이전·복원한 코드와 새로 작성한 코드의 네이밍·PCH/include 배치를 문서 기준으로 확인한다. 빌드 성공만으로 컨벤션 준수를 확인했다고 처리하지 않는다.
- 검증은 로컬의 정상 사용 흐름을 대상으로 한다. 원본 결함의 전수 수정, 장기간 부하 테스트, 퍼징, 성능 최적화, 운영 배포, MMO 콘텐츠 추가는 이번 완료 조건이 아니다.
- 현재 로컬 채팅 검증을 과거 한 달 부하 테스트나 운영 안정성 보증으로 확대하여 보고하지 않는다.
- Git 상태 변경 작업은 사용자가 직접 한다. 이 계획 작성이나 이후 구현은 스테이징·커밋·푸시 권한을 포함하지 않는다.
