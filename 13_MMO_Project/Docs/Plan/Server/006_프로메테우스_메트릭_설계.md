# Prometheus 메트릭과 Grafana 설계

상태: **1차 구현 및 사용자 코드 검토 완료.** `MetricsLib`를 추가하고 기존 `CMonitor` 지표를 ChatServer `/metrics`에 연결했다. x64 Debug·Release 빌드와 `/metrics` 통합 테스트, 동일 호스트 Docker Prometheus 수집을 확인했다. 다른 머신에서의 수집은 미검증이며, Grafana 패널과 신규 콘텐츠 프레임·섹터 계측은 아직 구현하지 않았다. 더미의 실행·판정은 [DummyClient 검증](004_DummyClient_검증.md), 로그 파일·수집은 [서버 비동기 로그 설계](005_서버_비동기_로그_설계.md)를 따른다.

## 목표와 1차 범위

750명에서는 60초 실행이 성공했고 875명에서는 실패가 보고됐다. 875명의 상세 결과는 확보하지 못했으므로, 콘텐츠 프레임이나 섹터 전파가 병목이라는 결론은 내리지 않는다. 먼저 실제 FPS가 목표를 따르는지, 밀린다면 프레임 시작이 늦는지 아니면 실행 자체가 길어지는지 구분한다.

현재 채팅 서버는 `CChatContents` 하나에 `SChatFrameEvent` 하나를 등록하고 목표를 **25 FPS(40ms 간격)**로 지정한다. 콘텐츠 워커 설정을 늘리는 것과 이 채팅 프레임이 분할 실행되는 것은 별개다. `SendSector()`는 채팅 처리 중 주변 섹터를 순회해 송신을 요청한다. 소요 시간은 서버 측 순회·요청 경로 비용이며 수신 확인이나 네트워크 왕복 시간은 아니다.

1차에서 **기존 `CMonitor` → ChatServer `/metrics` → Prometheus**를 연결했다. 다음 작업은 모니터 계측 코드의 소유권 분리이며, 신규 프레임·섹터 계측과 Grafana 패널은 그 뒤에 다룬다. 더미는 기존 종료 코드·`RunSummary.json`을 유지한다. 더미 HTTP 노출, `windows_exporter`, 로그 수집(Loki/Alloy), Jenkins 변경, 알림은 후속으로 둔다.

## 라이브러리 경계

`Server/MetricsLib`는 별도 라이브러리이며, `ChatServer`가 첫 사용처다.

| 위치 | 책임 |
|---|---|
| `ServerNetworkLib` | `CMonitor`에서 기존 세션·트래픽·Windows 상태를 샘플링하고 스냅샷 복사본을 앱에 제공한다. `MetricsLib`나 HTTP에 의존하지 않는다. |
| `Server/ServerMetrics` | 세션·네트워크·작업 분배·프로세스·호스트의 공통 지표를 `MetricsLib` 스냅샷에 추가한다. |
| `ChatServer` (`Tests/Chatting/Server`) | `ChatMetrics.cpp`에서 새 샘플의 공통 매핑을 호출하고 채팅 전용 지표를 추가한다. 게시 콜백 등록·해제와 리스너 시작·종료를 소유한다. |
| `Server/MetricsLib` | 앱의 집계 함수를 받아 게시 콜백을 제공한다. 지표를 Prometheus 형식으로 변환하고, 최신 불변 스냅샷을 보관해 `/metrics`로 반환한다. `cpp-httplib`는 공개 API에 노출하지 않는다. 네트워크·채팅·더미·로거 구현에 의존하지 않는다. |

`ServerMetrics`는 별도 라이브러리 프로젝트가 아니다. ChatServer가 `ServerMetrics.cpp`를 직접 컴파일한다. 이 파일은 ChatServer의 `pch.h`에 의존하지 않고 `ServerNetworkLibPch.h`를 일반 헤더로 읽으며, 프로젝트 설정에서 이 파일만 `PrecompiledHeader=NotUsing`으로 둔다.

`CLogger`는 등록된 범용 콜백을 로그 스레드에서 주기적으로 호출할 뿐, 채팅 타입이나 HTTP를 알지 않는다. 정상 종료 시 `ChatServer`는 새 콜백 실행을 차단하고 진행 중인 호출이 반환할 때까지 기다린 뒤 리스너와 HTTP 워커를 종료하고 `MetricsLib`를 해제한다. 더미를 연동할 때는 더미 쪽 계측과 게시 시점만 별도로 정하고, 같은 `MetricsLib`를 사용한다.

## 스냅샷 게시와 HTTP 응답

```text
콘텐츠·IOCP 워커: 계측값 갱신
    → 로그 스레드: MetricsLib가 제공한 게시 콜백 실행
    → 게시 콜백: ChatServer 집계 함수 호출 → Prometheus 응답으로 변환 → 최신 스냅샷 교체
    → MetricsLib HTTP 워커: 요청당 스냅샷 한 개를 읽어 응답
    → Prometheus → Grafana
```

- `CMonitor`가 약 1초마다 샘플을 만든다. 로그 스레드는 폴링 중 콜백을 실행한다. `ChatMetrics.cpp`는 새 샘플만 공통·채팅 지표로 매핑하고, `MetricsLib`가 이를 직렬화한다. 로그 메시지를 파싱하지 않으며 `CLogger`에는 채팅 타입이나 HTTP 의존성이 없다.
- **최신 응답 슬롯 하나**를 사용한다. 응답 문자열을 완성한 뒤 `std::atomic<std::shared_ptr<const std::string>>`에 `store(release)`하고, 핸들러는 요청당 `load(acquire)` 한 번으로 얻은 포인터를 응답 생성이 끝날 때까지 유지한다. 교체와 겹친 요청은 이전 또는 새 응답 하나만 읽는다. 원자적 포인터 교체가 원본 계측값 전체의 동시 샘플링이나 락프리를 뜻하지는 않는다.
- `httplib::Server::listen()`은 별도 스레드에서 실행한다. 실제 핸들러는 HTTP 워커 풀에서 실행되므로 핸들러들이 SPSC 큐를 직접 소비하는 구조는 사용하지 않는다. HTTP 워커는 최신 응답만 반환하고, 세션·콘텐츠 락을 잡거나 PDH를 조회하거나 로그 큐를 비우지 않는다. 채팅 워커는 HTTP 처리나 스냅샷 포인터 교체에 참여하지 않는다.
- 기본 비활성으로 두고, 활성화하면 채팅 리스너와 다른 주소·포트 조합을 지정한다. `MetricsLib`는 `Start()` 호출자가 지정한 주소만 사용하며 실패 시 다른 주소로 바꾸지 않는다. 첫 게시 전에는 HTTP 503을 반환하고 수집·포맷 실패 시 마지막 정상 응답을 유지한다. 메트릭 리스너 자체의 바인딩이 실패하면 오류를 남기고 채팅 서버 시작을 계속한다. 단, 두 리스너를 같은 주소·포트로 설정해 메트릭 리스너가 먼저 바인딩하면 채팅 리스너의 바인딩이 실패해 서버가 기동하지 않는다. 정상 종료에서는 HTTP 리스너와 진행 중인 핸들러가 정리된 뒤 스냅샷 저장소를 해제한다.

## 메트릭 포트와 로컬 수집

- `ServerConfig.conf`에서 `METRICS_PORT`가 없거나 `0`이면 비활성이다. 사용할 경우 `METRICS_PORT`와 구체적인 IPv4 주소인 `METRICS_BIND_ADDRESS`를 지정한다. 동일 호스트 Docker 검증에서는 `127.0.0.1`과 `9464`를 사용했다. 다른 머신에서 수집할 때는 채팅 서버의 사설 또는 Tailscale 주소에 바인딩하고 Prometheus에도 그 주소와 포트를 대상으로 지정한다. 접근은 수집 머신에만 허용한다.
- 작업 Windows 호스트의 Docker Desktop에서 [Compose](../../../Infra/Monitoring/compose.yml)로 Prometheus(`127.0.0.1:9090`)와 Grafana(`127.0.0.1:3000`)를 실행한다. Prometheus의 [수집 설정](../../../Infra/Monitoring/prometheus.yml)은 `host.docker.internal:9464`를 대상으로 한다. 이 경로에서 실제 ChatServer를 임시 설정으로 실행하고 `up=1`, 활성 세션, 작업 집합 메모리, 수신 패킷을 조회했다. 배포 서버의 설정은 변경하지 않았다.

- `observability_snapshot_timestamp_seconds`는 마지막으로 성공한 게시의 Unix 초다. 조회하거나 새 게시에 실패하면 변하지 않는다. `time() - observability_snapshot_timestamp_seconds{job="chat_server"}`로 게시 경과 시간을 보고, 연결 상태인 `up`과 구분한다.

### 분산 서버에서 지표 구분

- 같은 의미와 단위의 공용 지표는 같은 이름을 쓴다. Prometheus가 수집할 때 붙이는 `job`으로 서비스 역할(`chat_server`, `auction_server` 등)을, `instance`로 각 수집 주소(`호스트:포트`)를 구분한다. 예를 들어 `net_sessions{job="auction_server"}`는 경매장 서버들의 세션을 인스턴스별로 보여준다. `auction_server`는 후속 구성 예시이며 현재 설정에는 추가하지 않는다.
- 역할 전용 지표는 `chat_*`, `auction_*`처럼 의미가 드러나는 이름을 쓴다. `host_*`는 여러 프로세스가 같은 PC에서 같은 자원을 보고할 수 있으므로 인스턴스 값을 합산하지 않는다.
- 지표 이름을 바꾼 버전은 기존 데이터와 별도 시계열이 된다. 배포할 때 서버 실행 파일과 Grafana 쿼리를 함께 전환한다.

## 후속 콘텐츠 대시보드 지표 후보

아래는 구현 후보 이름이다. 지속 시간의 단위는 초, 처리율 단위는 초당 건수로 통일한다.

| 지표 후보 | 측정 기준 |
|---|---|
| `chat_content_frames_total`, `chat_content_frame_target_fps` | 완료한 프레임 수와 설정 목표. 실제 FPS는 `rate`로 계산한다. |
| `chat_content_frame_start_delay_seconds`, `chat_content_frame_duration_seconds` | 각각 예약된 시작 → 실제 시작, 실제 시작 → 프레임 처리 완료. Histogram에서 p95/p99를 비교한다. |
| `chat_content_frame_overruns_total` | 처리 시간 자체가 프레임 간격(현재 40ms)을 넘긴 횟수. 시작 지연은 별도 지표다. |
| `chat_sector_send_duration_seconds`, `chat_sector_send_targets_total` | `SendSector()` 호출의 소요 시간과 송신을 요청한 대상 수. 실제 송신 완료·수신과 구분한다. |
| `chat_requests_total{operation,result}`, `net_sessions` | 채팅 처리율과 활성 세션 수. 처리율은 부하 크기와 함께 본다. |


Counter는 프로세스 시작 이후 누적값이며 Prometheus에서 `rate`/`increase`로 계산한다. Gauge는 현재 값, Histogram은 고정 버킷을 사용한다. 실패·타임아웃을 정상 지연 표본에 섞지 않는다. `operation`, `result`, `reason` 등은 고정 집합만 쓰고 계정·세션·메시지 ID와 `run_id`는 라벨로 만들지 않는다. 더미 실행은 Jenkins 빌드 번호, 결과 파일의 `run_id`와 시작·종료 시각으로 대조한다.

## 기존 모니터와 후속 범위

- [공통 지표 매핑](../../../Server/ServerMetrics/ServerMetrics.cpp)은 활성 세션, 수락·수신·송신, 작업 분배, WSASend 호출·pending, 프로세스와 호스트 CPU, 프로세스 메모리·페이지 폴트, 호스트 PDH를 포함한다. [채팅 전용 매핑](../../../Tests/Chatting/Server/ChatMetrics.cpp)은 콘텐츠 갱신, 로그인·이동·채팅을 추가한다. 구간 카운터는 `InterlockedExchange`가 반환한 값으로 누적 건수와 실제 경과 시간 기준 초당 건수를 만든다. 수락 완료와 세션 등록, 송신 요청과 실제 전달 성공은 다른 지표다. 생산자가 없는 기존 `m_serverFrame`은 노출하지 않는다.
- 시스템 nonpaged pool, 가용 메모리, 호스트 TCPv4 재전송은 검증 머신에서 유효했다. `CMonitor`는 배열 순서 대신 `m_nonpagedPoolBytes`, `m_availableMemoryBytes`, `m_tcpV4RetransmittedSegmentsPerSecond`로 의미와 단위를 전달한다. 가용 메모리의 바이트 변환도 `CMonitor`에서 처리하며, 공통 매핑은 기존 Prometheus 지표 이름만 붙인다. NIC는 런타임에 발견한 인터페이스별 송수신 합계(`host_nic_total_bytes_per_second{interface="…"}`)를 내보낸다. NIC와 TCP 수치는 채팅 서버 전용이 아니며, 워밍업 중이거나 유효하지 않은 표본은 생략한다.
- `process_info{process="…"} 1`에는 실행 중인 프로세스의 파일 이름만 담으며 전체 경로는 노출하지 않는다. CPU와 메모리는 프로세스 이름이 아니라 기존 핸들로 수집한다.
- 공통 전송 패널 후보는 세션/슬롯, 풀 사용량/용량, 수락 결과, 패킷·TCP 페이로드 바이트, 종료 원인과 송신 배치다. 바이트는 IOCP 완료 기준 TCP 페이로드(애플리케이션 패킷 헤더 포함, IP/TCP 헤더 제외), 소켓 송신 완료와 앱 전달은 따로 정의한다. 수신 큐 대기·깊이, IOCP→더미 `Tick()` 지연은 첫 프레임 계측으로 설명되지 않을 때 추가한다.
- 더미 노출을 추가할 때는 더미 쪽 스냅샷 어댑터만 붙여 기존 `MetricsLib`를 재사용한다. 후보는 목표 대비 Ready, 단계·동작 결과, 자기 echo 지연과 Tick 지연이다. 피어 완전 전달·중복·오전달은 고정 섹터 오라클을 구현한 뒤 노출한다. 짧은 실행은 scrape 없이 끝날 수 있으므로 항상 로컬 종료 코드·결과 파일로 판정한다.

## 모니터 계측 코드 개선

위의 계측 설명은 로그 스레드 전환 이전의 구현과 검증 기록이다. 현재 `ChatServer`는 로그 스레드 콜백에서 `CSystemMetrics`, `ServerMetrics`, `ChatMetrics`를 호출해 함께 게시한다. 구 `CMonitor`와 전용 타이머, 구 워커 분배·스틸 지표는 제거했다. 변경과 검증 기록은 [구버전 콘텐츠 런타임과 모니터 제거 계획](012_구버전_콘텐츠_런타임과_모니터_제거_계획.md)에 있다.

## 구현 순서와 확인 기준

1. **완료 — 기존 모니터 연동 및 사용자 코드 검토.** x64 Debug·Release 빌드와 `python -B Tests/Chatting/test_server_event_input.py metrics <Debug|Release>`로 주소 설정, 루프백 채팅 중 지표 변화, 비활성화, 포트 충돌 및 종료 후 포트 반환을 확인했다. PCH 의존성 및 PDH 필드 정리 후에도 두 구성에서 빌드와 통합 테스트를 통과했다. 동일 호스트 Docker Prometheus 수집은 앞선 연동 검증에서 확인했다.
2. [모니터 계측 코드 개선](#모니터-계측-코드-개선)은 구버전 제거 계획의 순서를 따른다.
3. 후속으로 프레임·섹터 계측을 정리해 붙이고 루프백 채팅에서 카운터 증가와 시간 단위를 확인한다.
4. Grafana에서 기본 서버 지표를 확인하고 후속 프레임·섹터 계측을 같은 시간축에 배치한다.
5. 설정을 고정하고 750명·875명 실행을 비교한다. 처리율, 타임아웃 발생 시점, 서버 프레임·섹터 지표를 나란히 본다. FPS가 정상인데 echo만 늦으면 프레임을 병목으로 단정하지 말고 큐·송신·더미 수신 경로를 다음 계측 대상으로 본다.
