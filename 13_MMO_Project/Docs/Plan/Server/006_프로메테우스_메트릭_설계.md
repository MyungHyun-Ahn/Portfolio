# Prometheus 메트릭과 Grafana 설계

상태: **설계 단계.** `third-party/cpp-httplib/`에 v0.67.0 원본 헤더와 라이선스를 추가했다. `Common/MetricsLib`, 채팅 서버 빌드 연결, `/metrics`, Prometheus 수집, Grafana 패널은 아직 구현·검증하지 않았다. 더미의 실행·판정은 [DummyClient 검증](004_DummyClient_검증.md), 로그 파일·수집은 [서버 비동기 로그 설계](005_서버_비동기_로그_설계.md)를 따른다.

## 목표와 1차 범위

750명에서는 60초 실행이 성공했고 875명에서는 실패가 보고됐다. 875명의 상세 결과는 확보하지 못했으므로, 콘텐츠 프레임이나 섹터 전파가 병목이라는 결론은 내리지 않는다. 먼저 실제 FPS가 목표를 따르는지, 밀린다면 프레임 시작이 늦는지 아니면 실행 자체가 길어지는지 구분한다.

현재 채팅 서버는 `CChatContents` 하나에 `SChatFrameEvent` 하나를 등록하고 목표를 **25 FPS(40ms 간격)**로 지정한다. 콘텐츠 워커 설정을 늘리는 것과 이 채팅 프레임이 분할 실행되는 것은 별개다. `SendSector()`는 채팅 처리 중 주변 섹터를 순회해 송신을 요청한다. 소요 시간은 서버 측 순회·요청 경로 비용이며 수신 확인이나 네트워크 왕복 시간은 아니다.

1차는 **서버 프레임/채팅 계측 → 로컬 `/metrics` → Prometheus → Grafana**만 연결한다. 더미는 기존 종료 코드·`RunSummary.json`을 유지한다. 더미 HTTP 노출, `windows_exporter`, 로그 수집(Loki/Alloy), Jenkins 변경, 알림, 원격 수집은 후속으로 둔다.

## 라이브러리 경계

1차부터 `Common/MetricsLib`를 별도 라이브러리로 만들고, `ChatServer`를 첫 사용처로 연결한다.

| 위치 | 책임 |
|---|---|
| `ServerNetworkLib` | 세션 수와 수락·수신·송신 등 전송 계층에서 발생하는 값만 계측하고 앱에 제공한다. `MetricsLib`나 HTTP에 의존하지 않는다. |
| `ChatServer` (`Tests/Chatting/Server`) | 콘텐츠 프레임과 `SendSector()`를 계측하고, 전송 계층의 값과 함께 스냅샷을 구성해 게시한다. 노출 활성화·바인딩 설정과 리스너 시작·종료를 소유한다. |
| `Common/MetricsLib` | 앱이 넘긴 지표를 Prometheus 응답 형식으로 변환하고, 최신 불변 스냅샷을 보관해 `/metrics`로 반환한다. `cpp-httplib`는 내부 구현에만 사용하고 공개 API에 노출하지 않는다. 네트워크·채팅·더미·로거 구현에 의존하지 않는다. |

로그 스레드를 집계에 재사용해도 `CLogger`는 채팅 타입이나 HTTP를 알지 않는다. 더미를 연동할 때는 더미 쪽 계측과 게시 시점만 별도로 정하고, 같은 `MetricsLib`를 사용한다.

## 스냅샷 게시와 HTTP 응답

```text
콘텐츠·IOCP 워커: 계측값 갱신
    → 로그 스레드에서 실행되는 ChatServer 집계: 주기적으로 지표 묶음을 게시
    → MetricsLib: Prometheus 응답으로 변환해 최신 스냅샷 교체
    → MetricsLib HTTP 워커: 요청당 스냅샷 한 개를 읽어 응답
    → Prometheus → Grafana
```

- 콘텐츠 프레임 시작·완료, `SendSector()` 시간과 대상 수는 콘텐츠 워커에서 측정한다. 같은 프레임으로 묶어 해석할 값은 프레임이 끝날 때 한 묶음으로 공개한다. 독립 누적 카운터를 로그 스레드가 각각 읽는 방식은 항목별 관측 시점이 다를 수 있다.
- 로그 스레드는 메트릭용 주기가 되었을 때만 스냅샷을 만든다(초기 후보 1초). 로그 폴링 주기마다 직렬화하거나 로그 메시지를 파싱하지 않는다. 집계 코드는 채팅 앱의 계측 모듈이 소유하고, `CLogger`에 채팅 타입이나 HTTP 의존성을 넣지 않는다. 파일 출력이 밀리면 게시도 지연될 수 있으므로 최종 게시 시각을 함께 노출한다. 실제로 지연이 문제가 되면 집계만 분리한다.
- **최신 스냅샷 슬롯 하나**를 사용한다. 스냅샷과 응답 문자열을 완성한 뒤 `std::atomic<std::shared_ptr<const Snapshot>>`에 `store(release)`하고, 핸들러는 요청당 `load(acquire)` 한 번으로 얻은 포인터를 응답 생성이 끝날 때까지 유지한다. 게시한 객체나 내부 저장소는 수정하지 않는다. 교체와 겹친 요청은 이전 또는 새 스냅샷 한 개만 읽는다. 원자적 포인터 교체가 원본 계측값 전체의 동시 샘플링이나 락프리를 뜻하지는 않는다.
- `httplib::Server::listen()`은 별도 스레드에서 실행한다. 실제 핸들러는 HTTP 워커 풀에서 실행되므로 핸들러들이 SPSC 큐를 직접 소비하는 구조는 사용하지 않는다. HTTP 워커는 최신 응답만 반환하고, 세션·콘텐츠 락을 잡거나 PDH를 조회하거나 로그 큐를 비우지 않는다. 채팅 워커는 HTTP 처리나 스냅샷 포인터 교체에 참여하지 않는다.
- 기본 비활성, 채팅 포트와 분리한 `127.0.0.1` HTTP 포트로 시작한다. 같은 호스트의 Prometheus만 대상으로 하며 첫 게시 전에는 수집 가능한 정상 데이터로 응답하지 않는다(예: HTTP 503). 포트 충돌과 수집 실패는 관측 실패로 처리하고 채팅과 로컬 검증은 계속한다. 정상 종료에서는 HTTP 리스너와 진행 중인 핸들러가 정리된 뒤 스냅샷 저장소를 해제한다.

## 첫 대시보드에 넣을 지표

아래는 구현 후보 이름이다. 지속 시간의 단위는 초, 처리율 단위는 초당 건수로 통일한다.

| 지표 후보 | 측정 기준 |
|---|---|
| `game_chat_content_frames_total`, `game_chat_content_frame_target_fps` | 완료한 프레임 수와 설정 목표. 실제 FPS는 `rate`로 계산한다. |
| `game_chat_content_frame_start_delay_seconds`, `game_chat_content_frame_duration_seconds` | 각각 예약된 시작 → 실제 시작, 실제 시작 → 프레임 처리 완료. Histogram에서 p95/p99를 비교한다. |
| `game_chat_content_frame_overruns_total` | 처리 시간 자체가 프레임 간격(현재 40ms)을 넘긴 횟수. 시작 지연은 별도 지표다. |
| `game_chat_sector_send_duration_seconds`, `game_chat_sector_send_targets_total` | `SendSector()` 호출의 소요 시간과 송신을 요청한 대상 수. 실제 송신 완료·수신과 구분한다. |
| `game_chat_requests_total{operation,result}`, `game_net_sessions` | 채팅 처리율과 활성 세션 수. 처리율은 부하 크기와 함께 본다. |
| `game_observability_snapshot_timestamp_seconds` | 마지막 게시 시각(Unix 초). scrape 연결의 `up`과 스냅샷 최신성은 별개다. |

Counter는 프로세스 시작 이후 누적값이며 Prometheus에서 `rate`/`increase`로 계산한다. Gauge는 현재 값, Histogram은 고정 버킷을 사용한다. 실패·타임아웃을 정상 지연 표본에 섞지 않는다. `operation`, `result`, `reason` 등은 고정 집합만 쓰고 계정·세션·메시지 ID와 `run_id`는 라벨로 만들지 않는다. 더미 실행은 Jenkins 빌드 번호, 결과 파일의 `run_id`와 시작·종료 시각으로 대조한다.

## 기존 모니터와 후속 범위

- 현재 `SMonitorTimerEvent`는 약 1초마다 `CMonitor::Update()`를 호출한다. 소스에서 `UpdateServer()`가 구간 카운터를 리셋하며, 주기 콘솔 출력 호출은 현재 경로에 없다. 이 카운터를 Prometheus Counter로 직접 내보내거나 샘플을 바로 TPS로 간주하지 않는다. 기존 `Accept TPS`와 송신 요청 수 역시 실제 접속/전달 성공과 다르다. 새 누적 카운터와 기존 계측의 수명은 별개로 관리한다.
- 기존 OS 샘플은 `GetSystemTimes`·`GetProcessTimes`·`GetProcessMemoryInfo`와 PDH를 사용한다. 과거 로컬 PDH 조사에서는 옛 프로세스 이름 및 하드코딩된 NIC 대표 경로가 `PDH_INVALID_DATA / PDH_CSTATUS_NO_INSTANCE`였고, 시스템 nonpaged pool·Available MBytes·호스트 TCPv4 재전송은 유효 샘플을 얻었다. 호스트 TCP 값은 서버별·루프백 전달 지표가 아니다. 추후 호스트 지표는 `windows_exporter`를 우선하고, 미수집이나 워밍업은 정상 0으로 표시하지 않는다.
- 공통 전송 패널 후보는 세션/슬롯, 풀 사용량/용량, 수락 결과, 패킷·TCP 페이로드 바이트, 종료 원인과 송신 배치다. 바이트는 IOCP 완료 기준 TCP 페이로드(애플리케이션 패킷 헤더 포함, IP/TCP 헤더 제외), 소켓 송신 완료와 앱 전달은 따로 정의한다. 수신 큐 대기·깊이, IOCP→더미 `Tick()` 지연은 첫 프레임 계측으로 설명되지 않을 때 추가한다.
- 더미 노출을 추가할 때는 더미 쪽 스냅샷 어댑터만 붙여 기존 `MetricsLib`를 재사용한다. 후보는 목표 대비 Ready, 단계·동작 결과, 자기 echo 지연과 Tick 지연이다. 피어 완전 전달·중복·오전달은 고정 섹터 오라클을 구현한 뒤 노출한다. 짧은 실행은 scrape 없이 끝날 수 있으므로 항상 로컬 종료 코드·결과 파일로 판정한다.

## 구현 순서와 확인 기준

1. 프레임·섹터 계측을 붙이고 루프백 채팅에서 카운터 증가, 프레임 단위 값의 일치, 시간 단위를 확인한다.
2. `Common/MetricsLib`에 스냅샷 게시·포맷 변환·로컬 `/metrics`를 구현하고 `ChatServer`에 연결한다. `ServerNetworkLib`와 `CLogger`에 새 의존성이 생기지 않는지 확인한다. 동시에 여러 요청을 보내도 응답 하나에 이전 값과 새 값이 섞이지 않고, 미갱신 상태·포트 충돌·종료에서도 채팅과 로그가 정상 동작하는지 확인한다.
3. Prometheus에서 scrape 성공과 게시 시각 갱신을 각각 확인한다. Grafana에서 실제 FPS/목표, 시작 지연/처리 시간/초과 수, `SendSector()` 시간/대상 증가율 및 채팅 처리율을 같은 시간축에 배치한다.
4. 설정을 고정하고 750명·875명 실행을 비교한다. 처리율, 타임아웃 발생 시점, 서버 프레임·섹터 지표를 나란히 본다. FPS가 정상인데 echo만 늦으면 프레임을 병목으로 단정하지 말고 큐·송신·더미 수신 경로를 다음 계측 대상으로 본다.
