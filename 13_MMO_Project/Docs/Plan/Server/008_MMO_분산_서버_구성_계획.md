# MMO 분산 서버 구성 계획

상태: **큰 그림 초안.** 첫 구현은 [ContentsRuntimeLib와 고정 워커 배정](009_ContentsRuntime_1차_계획.md#phase-1--contentsruntimelib와-고정-워커-배정)이다. 서비스 경계는 아래와 같이 잡되, 배치 대수와 통신·저장 구현은 아직 확정하지 않는다.

## 서버별 상태와 책임

| 서버 | 소유하는 상태와 처리 단위 | 초기 방향 |
|---|---|---|
| 게임 | `MapInstanceId` 단위의 캐릭터 실시간 상태, 전투, 맵 오브젝트 | 맵 인스턴스 단위로 프레임과 요청을 처리한다. 이동 중 무소속 연결의 입력은 네트워크 수신 큐에 남는다. |
| DB / 캐시 | DB 작업 요청 및 저장 상태. 캐시를 두면 캐시 키 단위 | 별도 캐시 서버는 보류한다. 게임 서버에 붙는 `DBConnectorLib`의 DB 실행기와 전용 워커로 시작하는 안을 우선 검토한다. DB 실행기는 게임 프레임을 돌리지 않는다. |
| 경매장 | 경매 건, 입찰·정산 상태 | 별도 서버와 RPC를 구현한다. 게임 서버의 잔액 검사는 예비 검사이며, 최종 잔액·입찰 확정 책임은 별도로 정의한다. |
| 랭킹 | 시즌·종류별 점수 집계와 조회 | 게임에서 확정된 점수를 받아 집계한다. 게임 프레임은 집계를 기다리지 않는다. |
| 길드 | `GuildId` 단위의 멤버십과 권한 | 가입·추방·권한 변경을 길드 서버가 확정한다. |
| 매칭 | 모드 등으로 구분된 매칭 풀의 대기열과 매치 결과 | 매칭 서버는 매치까지만 결정하고, 던전 생성·입장·전투는 게임 서버가 맡는다. |
| 로그인 | 계정 인증과 접속 자격 발급 | C++로 제한하지 않는다. 게임 서버가 접속 자격을 어떻게 검증할지는 로그인 설계에서 정한다. |

로그인 서버를 제외한 별도 서비스는 필요한 서버 간 RPC 연결을 둔다. 초기에 게임 서버가 각 소비 서비스와 연결하고, 서비스끼리는 실제 의존이 있을 때만 직접 연결한다. 게임 서버의 맵 프레임과 워커 배정 정책을 나머지 서비스에 강제하지 않는다.

## RPC 호출 및 완료 처리 방향

- 게임 핸들러에서 예비 검사 후 `auctionRpc.Execute(request, 실행_대상, 응답_람다)`처럼 호출하고, 후속 처리를 같은 코드에서 읽을 수 있게 한다. 표기는 API 초안이다.
- RPC 응답 스레드는 캐릭터 상태를 직접 수정하지 않는다. 응답은 요청을 시작한 게임 실행단위의 완료 큐로 전달한다. 캐릭터 상태에 반영할 Job은 기존 맵에서 완료 콜백까지 처리한 뒤 소속을 넘긴다. 처리 시 접속 세대와 소속을 재확인하고, 응답 람다는 `User*`나 `User&`를 캡처하지 않는다. 다른 게임 프로세스로 전달할 때는 람다가 아니라 결과 데이터를 보낸다.
- RPC 호출을 구분하는 `callId`와 거래를 구분하는 `operationId`는 목적이 다르다. 타임아웃은 거래 실패로 확정하지 않고, 동일 `operationId`로 결과 조회·재시도한다. 로그아웃으로 화면에 응답을 보낼 수 없어도 확정된 거래는 남아야 한다.
- 경매장 잔액을 따로 예치하고 입찰금 예약과 입찰 갱신을 한 트랜잭션으로 확정하는 안은 후보로 둔다. 게임 지갑을 직접 쓸지, 누가 잔액과 아이템 인도를 최종 확정할지는 경매장 설계에서 결정한다.

## 진행 순서

1. [ContentsRuntime Phase 1~3](009_ContentsRuntime_1차_계획.md#phase별-구현-및-검증-순서)에서 고정 워커 배정, 두 맵의 소속별 요청 처리, 캐릭터 이동과 완료 콜백 경계를 차례로 검증한다.
2. `ContentsRuntime`의 워커 재배치는 Phase 4~6에서 수동 Delegate → 관리 콘텐츠와 정책 경계 → 프레임 예산 기반 자동 Delegate 순으로 검증한다. 이 단계는 DB/RPC 연동의 선행 조건이 아니다.
3. Phase 3에서 확인한 완료·이동 계약 위에 별도 `DBConnectorLib`와 RPC 연동을 붙인다. 경매장 `PlaceBid`를 첫 RPC로 삼아 정상 응답, 응답 대기 중 이동 요청과 기존 맵의 완료 처리 후 인계, DB 확정 후 응답 유실, 동일 요청 재전송을 검증한다.
4. 이후 랭킹·길드·매칭·로그인을 각 서비스 책임에 맞게 개발한다. 별도 캐시 서버 도입은 DB 작업 분리만으로 부족하다는 근거가 있을 때 다시 검토한다.
