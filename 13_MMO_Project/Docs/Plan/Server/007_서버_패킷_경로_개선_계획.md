# 서버 패킷 경로 개선 계획

상태: **계획만 작성, 미착수.** `ContentsRuntime` 개편 전에 서버 네트워크가 검증된 수신 패킷을 콘텐츠 `OnRecv()`에 넘기는 경계를 정리한다. 송신은 콘텐츠가 직접 관리하는 패킷 참조를 없애는 범위만 포함한다.

기존 `Net`/`Lan` 설정, 5바이트 `SPacketHeader` 규격, 패킷 크기 한도와 검증 순서는 유지한다. 클라이언트 경로, 세션 I/O 카운터, 콘텐츠 스케줄링·이동·세션 해제 구조, 락프리 큐 구현은 이번 범위가 아니다.

## 1. Net 수신 복호화와 체크섬 통합

- 현재 `CSession::RecvCompleted()`는 체크섬 바이트와 본문을 복호화한 뒤, 평문 본문을 다시 순회해 체크섬을 계산한다.
- 서버 수신 전용 처리에서 체크섬 필드도 기존 순서대로 복호화하되, **복호화된 본문 바이트만** 합산한다. 계산값이 복호화된 체크섬 필드와 다르면 기존처럼 패킷을 큐에 넣지 않고 연결을 종료한다. `Lan`과 송신 경로는 건드리지 않는다.
- 기존 2회 순회 구현을 기준으로 평문 바이트와 성공·실패 판정이 같은지 비교한다. 빈 본문, 최대 본문, 루프 나머지 길이, 상위 비트가 켜진 바이트, 체크섬 불일치와 `Net`·`Lan` 채팅 왕복을 확인한다. CPU 개선은 같은 입력으로 별도 측정하고, 동작 일치와 구분한다.

## 2. 수동 RefCount를 콘텐츠에서 감추기

- 서버 버퍼의 기존 intrusive RefCount와 풀은 유지한다. `std::shared_ptr` 도입이나 세션의 `m_ioCountAndRelease` 치환은 하지 않는다.
- 네트워크 경계에 패킷 참조 하나를 맡는 RAII 핸들을 둔다. 수신은 큐에서 성공적으로 꺼낸 참조를 핸들이 인수하고, `OnRecv()`에는 콜백 동안만 유효한 View를 빌려준다. 기존 큐는 raw 포인터를 전달하되, 큐가 가진 참조의 인수는 `Dequeue` 성공 후에만 한다. 더미 노드에는 소유 핸들을 저장하지 않는다.
- 송신은 패킷 생성과 재사용 송신에 쓰는 소유 핸들을 제공한다. 송신 접수 시 큐가 자기 참조를 확보하고 I/O 완료·취소·세션 정리 경로에서 반납한다. 브로드캐스트에서 호출자 핸들은 제출이 끝날 때까지 패킷을 유지한다. 서버 송신 생성기 템플릿과 채팅 호출부를 같이 바꾸고, 콘텐츠 코드에서 `IncreaseRef()`·`DecreaseRef()`·`Free()`를 직접 부르지 않게 한다.
- 일반 처리, 이동·거부로 인한 조기 종료, 큐를 비우는 세션 정리, 재사용 패킷의 여러 대상 송신과 실패 경로에서 참조가 남거나 두 번 반환되지 않는지 확인한다. 패킷 하나를 꺼낸 뒤 다음 패킷이 없어도 마지막 소유권 해제 시 반환되는지도 확인한다.

## 3. 서버 수신 View로 복사 줄이기

- 현재는 링버퍼에서 완성 패킷마다 본문을 별도 `CSerializableBuffer`에 복사한 뒤 큐에 넣는다. 서버에서 `CRecvBuffer` / `CSerializableBufferView`를 활용해, 한 수신 페이지 안에서 연속인 완성 패킷은 해당 페이지를 보유하는 View로 넘기는 방식을 비교한다.
- 미완성 프레임은 게시하지 않는다. 페이지 경계를 넘는 프레임은 필요한 조각만 복사해 조립한다. 검증을 마친 뒤에만 View를 게시하고, 큐에 있는 동안이나 콜백이 읽는 동안 해당 바이트를 다음 수신이 덮어쓰지 못하게 한다. 검증 실패·연결 종료 시에도 마지막 소유권이 해제되기 전에는 페이지를 풀에 반환하지 않는다.
- 같은 트래픽으로 현행 복사 경로와 비교한다. 수신 처리 시간, 복사 바이트, View 할당 수, TLS 공용 풀 왕복, 최대 페이지 점유량을 본다. 큐 대기 시간은 별도로 기록한다. 같은 스레드에서 바로 재사용하지 못하는 비용과 페이지 보유 비용까지 포함해 효과가 확인될 때만 전환한다.
- 헤더·본문 분할, 여러 프레임 연속 수신, 페이지 경계, 느린 소비자, 대기 패킷이 있는 연결 종료를 확인한다. `Net`의 검증과 `Lan`의 평문 처리, 전달 순서가 기존과 같아야 한다.

## 작업 기준

체크섬 통합 → 소유권 경계 정리 → View 비교 순서로 각각 검토한다. 각 단계의 변경과 검증 결과를 확인한 뒤 다음 단계로 넘어간다. View는 비교 결과에 따라 기존 복사 경로를 유지할 수 있다. 장시간 원격 부하 시험은 이 계획의 필수 조건으로 두지 않는다.
