# 서버 패킷 경로 개선 계획

상태: **서버 패킷 경로 개선 완료.** `Net` 수신 복호화·체크섬을 통합했고, 서버 수신 View 개선과 송신 소유권 정리는 사용자 확인을 마쳤다. 다음 작업은 `ContentsRuntime` 설계다.

기존 `Net`/`Lan` 설정, 5바이트 `SPacketHeader` 규격, 패킷 크기 한도와 검증 순서는 유지한다. 클라이언트 변경은 1단계 `Net` 수신에 한정한다. 세션 I/O 카운터, 콘텐츠 스케줄링·이동·세션 해제 구조, 락프리 큐 구현은 이번 범위가 아니다.

## 1. Net 수신 복호화와 체크섬 통합

- 기존 `CSession::RecvCompleted()`는 체크섬 바이트와 본문을 복호화한 뒤, 평문 본문을 다시 순회해 체크섬을 계산했다.
- 서버와 클라이언트의 `Net` 수신은 `CEncryption::DecodeAndValidateChecksum()`으로 체크섬 필드를 먼저 복호화하고, **본문은 복호화하면서 합산**한다. 체크섬이 다르면 기존처럼 패킷을 전달하지 않고 연결을 종료한다. `Lan`과 송신 경로는 그대로다.
- x64 Debug·Release 빌드와 `ClientLifecycle`이 통과했다. 빈 본문부터 최대 본문까지 기존 2회 순회 구현과 복호화 결과 및 체크섬 일치·불일치 판정을 비교했다. 클라이언트 루프백에서 체크섬이 틀린 패킷이 게시되지 않고 `ERROR_INVALID_DATA`로 연결이 종료되는 것도 확인했다. Release `Net`·`Lan` 채팅 왕복도 통과했다.
- [독립 마이크로벤치마크](../../../Tests/PacketGenerator/NetChecksumBenchmark.cpp)에서 실제 `ReqMessage`를 연속 프레임으로 구성했다. x64 `/O2`로 워밍업 3회와 측정 21회의 중앙값을 구하는 실험을 3회 실행했다. 256·2,048개 묶음의 수신 시간 차이는 1% 미만, 8,192개 묶음에서는 통합 경로가 1.9~3.0% 짧았다. 모든 측정에서 복호화 결과가 원본과 일치했다. 직렬화·입력 복사·소켓 I/O는 측정에서 제외했으며, 이 결과는 서버 전체 CPU 사용률 개선을 뜻하지 않는다.

## 2. 수동 RefCount를 콘텐츠에서 감추기

- 상태: **사용자 확인으로 완료.** 생성기 테스트 18개, 직렬화·풀 반환 테스트, x64 Debug·Release 빌드, Release `Net`·`Lan` 채팅 왕복을 확인했다.
- 서버 버퍼의 기존 intrusive RefCount와 풀은 유지한다. `std::shared_ptr` 도입이나 세션의 `m_ioCountAndRelease` 치환은 하지 않는다.
- 수신은 3단계에서 먼저 정리했다. 기존 큐가 전달한 View는 `Dequeue` 성공 후에만 인수하고, `OnRecv()`에는 콜백 동안만 빌려준다. 더미 노드에는 소유 핸들을 저장하지 않는다.
- 서버 `MakePacket(response)`는 생성된 구조체의 `kPacketType`을 본문 앞에 한 번 쓰고, 기존 풀 버퍼를 소유하는 서버 공용 `ServerNetworkLib::SendPacketPtr`를 반환한다. 호출부는 패킷 타입이나 반환 책임을 따로 넘기지 않고 `SendPacket(sessionId, spPacket)`으로 제출한다. 큐는 기존대로 자기 참조를 확보해 I/O 완료·세션 정리에서 반환한다. 브로드캐스트에서도 호출자 핸들이 마지막 제출까지 패킷을 유지한다. 수동 참조 조작 금지는 [C++ 코딩 규칙](../../Rule/002_Cpp_코딩컨벤션.md#소유권오류)으로 적용한다.
- 일반 처리, 이동·거부로 인한 조기 종료, 큐를 비우는 세션 정리, 재사용 패킷의 여러 대상 송신과 실패 경로에서 참조가 남거나 두 번 반환되지 않는지 확인한다. 패킷 하나를 꺼낸 뒤 다음 패킷이 없어도 마지막 소유권 해제 시 반환되는지도 확인한다.

## 3. 서버 수신 View로 복사 줄이기

- 상태: **사용자 확인으로 완료.** 최종 `RecvCompleted(int size)` 경로는 x64 Release 빌드와 `Net`·`Lan` 채팅 왕복을 확인했다. 운영 성능은 재측정하지 않았다.
- `04_Single_IOCP_ChatServer/IOCP_ChatServer_PagePool`의 흐름을 가져왔다. 매 `WSARecv()`가 TLS 풀에서 빌린 새 4 KiB `CRecvBuffer`에 쓰고, 한 페이지에서 끝난 프레임은 본문 복사 없이 페이지 오프셋으로 View를 만든다. 수신 완료 사이에 걸친 프레임만 조각을 이어 붙인다.
- 원본처럼 `CSession`이 수신 페이지와 분할 패킷을 직접 보유한다. `CServer.cpp`의 `PostRecv()`가 페이지를 준비하고 `RecvCompleted()`가 수신 완료를 처리한다. 헤더·길이 및 `Net` 체크섬 검증을 통과한 View는 콜백 없이 세션 큐에 직접 넣는다. 미완성 프레임은 게시하지 않는다. `CBaseContents`는 큐에서 꺼낸 View를 `OnRecv()` 동안만 빌려주고 직접 반환한다. 다음 수신에는 새 페이지를 사용하며, 마지막 참조가 남아 있는 페이지는 풀에서 재사용하지 않는다.
- `CSerializableBuffer`와 `NetworkBufferPools.cpp`는 그대로 둔다. `CSerializableBufferView`는 풀 반환 시 `CSmartPtr`의 소멸자를 직접 호출하지 않고 `Reset()`으로 페이지 참조만 내려놓는다. `CBaseContents`까지 연속 프레임을 복사하지 않고, 테스트 채팅 콘텐츠에서만 기존 생성 디스패처를 사용하기 위해 본문을 풀 직렬화 버퍼에 복사한다. x64 Debug·Release 채팅 솔루션 빌드 및 Release `Net`·`Lan` 채팅 왕복을 확인했다.
- 독립 목업은 소켓 없이 `CSession`의 실제 페이지 처리 함수와 TLS 풀을 사용했다. 테스트 전용 `friend`를 제거하기 전에 소비자 1명과 생산자 4명·8명을 각각 검증했다. [목업 소스](../../../Tests/ServerRecvView/ServerRecvViewMock.cpp)와 스크립트는 비교 기록으로 보존하며, `friend`가 없는 현재 서버에서는 실행하지 않는다. 각 모드에서 기존 링 경로와 View 경로가 동일한 입력 4,096개·8,192개를 같은 내용과 생산자별 순서로 전달했다. View 경로는 각각 3,072개·6,144개가 수신 페이지를 직접 참조하고 나머지만 조립했다.
- 실제 페이지의 바이트를 바꿔 View가 같은 메모리를 읽는지 확인했다. 네 번의 완료에 걸친 분할, 잘못된 헤더·체크섬 거부, 소비를 늦춘 상태에서 수신 스트림을 정리해도 게시된 View가 유효한지도 확인했다. 소비 완료 뒤 TLS 풀 사용량은 시작 값으로 돌아왔다.

### N:1 목업 성능 비교

`python -B Tests/ServerRecvView/run_server_recv_view.py --producers 4 8 --groups 4096 --benchmark 10`

- Windows x64 MSVC `/O2`, 소비자 1개. 두 경로가 동일한 합성 입력을 처리했다. `packed`는 패킷 4개가 한 완료에 들어오고, `split`은 4개 중 1개가 네 완료에 걸친다. 각 경로·표본에서 생산자당 256그룹으로 워밍업한 뒤 4,096그룹을 12회 재생했다(4:1은 786,432개, 8:1은 1,572,864개). 조건마다 10쌍을 실행했으며 링/View 순서는 교대했다.
- CPU는 목업 프로세스의 사용자·커널 CPU 시간 합계(패킷당 ns), 처리량은 생산 시작부터 소비·반납 완료까지의 실경과 시간 기준(백만 패킷/초)이다. 큐와 TLS 풀 반환은 포함하고 소켓·IOCP와 실제 콘텐츠 처리는 제외했다. 아래 변화율은 경로별 중앙값 기준이며 양수가 개선이다.

| 생산자 | 모드 | 입력 | CPU ns/패킷 링 → View | CPU 절감 | 백만 패킷/초 링 → View | 처리량 증가 |
|---:|---|---|---:|---:|---:|---:|
| 4 | Net | packed | 1490.1 → 1470.2 | +1.3% | 3.266 → 3.302 | +1.1% |
| 4 | Net | split | 1490.1 → 1480.2 | +0.7% | 3.357 → 3.401 | +1.3% |
| 4 | Lan | packed | 1480.2 → 1440.4 | +2.7% | 3.209 → 3.303 | +2.9% |
| 4 | Lan | split | 1599.4 → 1619.3 | -1.2% | 3.059 → 3.070 | +0.4% |
| 8 | Net | packed | 3591.2 → 3576.3 | +0.4% | 2.413 → 2.464 | +2.1% |
| 8 | Net | split | 3273.3 → 3213.7 | +1.8% | 2.639 → 2.681 | +1.6% |
| 8 | Lan | packed | 3476.9 → 3496.8 | -0.6% | 2.468 → 2.475 | +0.3% |
| 8 | Lan | split | 3486.9 → 3501.8 | -0.4% | 2.498 → 2.499 | +0.1% |

표는 수신 로직을 `CSession`으로 옮기고 수신 콜백을 없애기 전 측정값이다. 이후 목업에서는 실제 세션 큐에서 View를 꺼내 공유 소비 큐로 옮겼고, 링버퍼 비교 경로도 같은 단계를 거쳤다. 이 구조에서는 기능 회귀와 성능 옵션 실행만 확인했다. 표의 모든 조건에서 반복에 따라 개선·악화가 모두 관찰됐으므로 일관된 CPU 절감이나 운영 서버 성능 향상을 결론 내릴 수는 없다. 연속 프레임의 본문 복사를 제거하는 View 경로는 유지한다.

## 작업 기준

체크섬 통합 뒤 사용자 요청에 따라 서버 수신 View를 먼저 적용했다. 수신 `OnRecv()`에는 소유권을 노출하지 않으며, 송신 소유권 정리는 별도 단계다. 장시간 원격 부하 시험은 이 계획의 필수 조건으로 두지 않는다.
