# 콘텐츠 완료 Handle 전환 계획

상태: **설계·검증 계획. 미구현.** 이 문서는 기존 완료 큐 락·워커 깨움 비교 문서를 대체한다. [ContentsRuntime 1차 계획](009_ContentsRuntime_1차_계획.md#phase-4--수동-delegate)의 완료 이력과 Phase 5~6 범위는 바꾸지 않는다.

## 문제와 목표

현재 `PostCompletion(instanceId, ...)`은 `m_registrationLock` 아래에서 접수 상태 확인 → `m_routes` 조회 → 콘텐츠 큐 삽입 → 워커 깨움을 수행한다. 콘텐츠마다 완료 큐 락이 있어도, 다른 콘텐츠에 게시하는 호출끼리 전역 락에서 직렬화된다. 완료를 요청한 쪽이 콘텐츠를 이미 알고 있다면 결과가 돌아올 때 다시 ID를 조회할 필요가 없다.

목표는 **결과 도착 경로를 `PostCompletion(handle, ...)`로 바꿔 라우트 조회와 전역 락을 제거**하는 것이다. 같은 콘텐츠에 대한 게시만 그 콘텐츠의 큐 락에서 직렬화한다. 세마포어는 깨움 유실을 막는 장치이므로 유지한다.

## 전후 비교

| 구분 | 기존 CV 방식 | 현재 세마포어 방식 | 목표: Handle 방식 |
| --- | --- | --- | --- |
| 게시 경로 | 등록 락 → ID 조회 → 워커 락으로 큐 삽입 → CV 알림 | 등록 락 → ID 조회 → 콘텐츠 큐 락으로 삽입 → 세마포어 신호 | Handle로 접수 객체 확보 → 해당 큐 락으로 접수·삽입·담당 워커 신호 |
| 경합 범위 | 전역 등록 락과 워커 락 | 전역 등록 락과 콘텐츠 큐 락 | 같은 콘텐츠의 게시·인계·접수 종료에서만 큐 락 경합 |
| 수명 | 런타임이 등록 콘텐츠를 보유 | 동일 | 런타임이 콘텐츠를 단독 소유. Handle은 접수 객체의 수명만 잠깐 유지 |

현재 방식의 x64 Debug·Release `WorldServer`, `FixedMaps`, 채팅 Net/Lan 회귀는 통과했다. 생산자 4개의 완료 128건과 후속 완료 처리도 확인했다. 이 결과는 Handle 방식의 검증이 아니다. 처리량·락 대기 시간의 전후 수치는 아직 없다.

## 소유권 및 API

- 완료 큐는 **`IContents` 인스턴스당 하나**다. 기존 인라인 큐·락을 별도 접수 객체로 만드는 이유는 Handle이 **콘텐츠가 아닌 접수 객체만** 안전하게 참조할 수 있게 하기 위함이다. 단순히 `SEntry`로 큐를 옮기는 변경은 하지 않는다.
- 런타임은 등록한 `IContents`를 계속 `unique_ptr`로 단독 소유한다. 콘텐츠가 자기 접수 객체를 강하게 소유하고, 외부 `ContentsHandle`은 그 객체의 약한 참조만 갖는다. 약한 참조를 잠그는 데 성공해도 콘텐츠나 워커의 수명이 연장되는 것은 아니다.
- Handle은 등록하거나 비동기 요청을 만들 때 얻어 결과를 돌려줄 쪽에 **값으로** 전달한다. 외부에 큐나 워커 포인터를 노출하지 않는다. 등록 전이거나 아직 접수를 열지 않은 Handle, 빈 콜백, 닫히거나 만료된 Handle은 거절한다. 동일 ID를 이후 재사용해도 기존 Handle은 새 접수 객체를 가리키지 않는다.
- `m_routes`는 시작 전 등록, ID 기반 제어 및 인계에 남긴다. 일반 완료 게시에는 사용하지 않는다. 샤딩, 전역 `shared_mutex` 전환, 런타임 중 등록·등록 해제, 새 런타임 인터페이스, 실제 DB/RPC 연동은 이번 범위 밖이다.

호출 형태 예시(미구현):

```cpp
// 요청을 만들 때 받은 Handle을 결과와 함께 전달한다.
const bool accepted = runtime.PostCompletion(handle, std::move(completion));
```

`true`는 큐 접수 성공이며 실행 완료는 아니다. 호출이 거절되면 콜백을 실행하지 않는다. Handle이 콘텐츠 수명을 보장하지 않으므로, 외부 결과 스레드는 콘텐츠 포인터로 직접 접근하지 않는다. 접수된 콜백 안에서만 담당 워커가 콘텐츠 상태를 사용한다. 런타임 멤버 API를 호출하는 동안 런타임 객체 자체가 살아 있어야 한다.

## 게시·인계·종료 경계

| 경로 | 계약 |
| --- | --- |
| 게시 | Handle로 접수 객체를 잠깐 확보한다. 해당 큐 락에서 접수 상태를 확인하고 FIFO로 삽입한 뒤 담당 워커에 신호를 남긴다. 전역 등록 락이나 워커 락을 잡지 않는다. |
| 소비 | 담당 워커만 큐에서 꺼낸다. 콜백 실행과 캡처 해제는 락 밖에서 한다. 한 콘텐츠의 프레임과 콜백은 겹치지 않는다. |
| 인계 | 현재 프레임·콜백이 끝난 뒤 같은 엔트리를 목적지 `delegateQueue`에 게시한다. 게시·담당 워커 전환은 큐 락으로 완료 생산자와 직렬화하고, 목적지를 반드시 깨운다. 편입 전 재인계 거절, 같은 FIFO와 다음 프레임 예정 시각은 유지한다. |
| 종료 | 제어 경로에서 신규 등록·인계를 차단하고 안정된 접수 객체 목록을 확정한다. 각 접수 객체를 삽입과 같은 큐 락으로 닫은 **뒤에만** 워커에 종료를 전달한다. 게시가 먼저면 그 작업까지 기존 계약대로 비우고, 닫기가 먼저면 게시를 거절한다. 워커가 큐를 비우고 종료한 뒤 `join`한다. |

락 순서는 **제어·라우트 → 워커 → 완료 큐**로 유지한다. 게시자는 완료 큐 락만 사용하고, 큐 락을 잡은 채 제어 락이나 워커 락을 얻지 않는다. 신호는 담당 워커를 보호하는 큐 락 안에서 보내므로 접수 종료 뒤 워커가 사라졌는데 포인터를 사용하는 경로를 만들지 않는다. `Stop()`은 콜백이나 `join()`을 락 안에서 기다리지 않는다.

훗날 동적 삭제가 필요하면 **접수 닫기 → 실행 경계에서 남은 완료 처리 → 담당 워커에서 콘텐츠 파괴**를 별도로 검증한다. Handle의 만료나 마지막 참조 반환을 콘텐츠 파괴 시점으로 삼지 않는다.

## 구현 순서와 완료 기준

1. **접수 객체와 Handle:** 등록 시 콘텐츠별 Handle을 얻을 수 있게 한다. 실행 전·종료 후·만료·빈 콜백 거절과 일반 완료의 정확히 한 번 실행을 단위 시험으로 확인한다.
2. **인계·종료 연결:** 실행 중인 프레임 또는 콜백을 멈춘 상태에서 같은 Handle로 인계 전·목적지 큐 대기 중·편입 후에 게시한다. FIFO, 올바른 실행 워커, 프레임 시각 유지와 중복 실행 없음을 확인한다. 게시와 접수 종료의 두 순서를 강제해 성공한 게시가 누락되지 않고 닫힌 접수에는 추가 삽입이 없는지 확인한다.
3. **호출부 이전:** WorldServer·FixedMaps·채팅에서 Handle을 미리 확보해 보관하거나 요청에 담게 한다. 기존 ID 기반 완료 API는 소비자가 모두 이전한 뒤 제거한다. Packet·NetworkLib·자동 스케줄러는 건드리지 않는다.
4. **최종 검증:** `WorldServer`·`FixedMaps` `RunTests`와 채팅 Net/Lan을 x64 Debug·Release로 실행한다. 소스 검수에서 일반 게시 경로가 전역 락과 맵 조회를 하지 않는지 확인한다. 성능을 비교할 경우 같은 콘텐츠에 몰리는 부하와 여러 콘텐츠에 분산된 부하를 따로 측정하고, `PostCompletion()` 지연과 완료 처리량을 수치로 기록한다.
