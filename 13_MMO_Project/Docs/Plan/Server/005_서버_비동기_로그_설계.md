# 서버 비동기 로그 설계

상태: 서버 이벤트의 `WriteLog()` 경로 통합, MHLib SPSC 큐, 서버 비동기 로거 구현·검증 및 사용자 코드·주석 검토를 완료했다. `CLogger`는 기존 MHLib 위치에 유지한다. 원본 로그 오프라인 분할 도구는 구현·검증을 마쳤으며 사용자 확인으로 완료 처리했다. [Loki·Alloy 외부 로그 수집](#외부-로그-수집)도 완료했다. [DummyClient 검증](004_DummyClient_검증.md)과 [Prometheus 메트릭 설계](006_프로메테우스_메트릭_설계.md)는 별도 문서를 따른다. 전체 작업 순서와 상태는 [로드맵](../../ROADMAP.md#서버-작업-순서)을 기준으로 한다.

## 1. 통합 전 동작과 적용 범위

아래의 기존 파일·콘솔 경로 설명은 서버 비동기 전환 전 기준이다.

- `CLogger::WriteLog()`는 **작업 디렉터리 기준** `LogFile/<분류>/<YYYYMM>_<타입>.txt`에 UTF-16LE로 append 한다. 이번에 이미 빌드된 Release 서버 복사본을 격리된 임시 디렉터리에서, 테스트가 소유한 점유 루프백 포트로 실행했다. `LogFile/SYSTEM/*_NetworkLib.txt`의 BOM과 실제 `bind()` 오류 `10048`, 서버 종료 코드 `1`을 확인했다. 즉 네트워크 오류의 파일 기록 경로는 작동한다. 모든 실패 로그와 정상 플레이 로그의 파일 저장을 검증한 것은 아니다.
- 서버 ENTER/LEAVE/LOGIN/SECTOR, 모니터링 화면, 클라이언트 READY/CHAT 등은 현재 주로 `WriteLogConsole()`이다. `SetMainDirectory(L"LogFile")`이나 스모크의 `stdout.txt` 캡처는 그 메시지가 앱 로그 파일에도 남는다는 증거가 아니다. 기존 파일 write/close 성공 검사와 여러 프로세스가 같은 경로에 쓰는 경우는 별도 검증 대상이다.
- 현재 `CNetServer`의 `WSARecv()`·`WSASend()` 오류 경로는 `CLogger::WriteLog()`를 직접 호출한다. 기존 `CLogger`는 SRW 락 아래 로그마다 파일을 열고 쓰며, 콘솔 출력도 별도 락을 사용한다. 목표는 로거 전체의 락프리가 아니라 **서버 IOCP·콘텐츠 워커가 출력 락과 I/O를 기다리지 않게 하는 것**이다.
- 서버의 정상 이벤트가 대상이다. 콘솔·LAN 클라이언트의 기존 `CLogger` 사용이나 서버 패킷·전송·종료 수명을 한꺼번에 바꾸지 않는다. 기존 주기 계측과 대체 패널은 [Prometheus 메트릭 설계](006_프로메테우스_메트릭_설계.md#기존-모니터와-후속-범위)에서 다루며, 이벤트 로그와 별개다.

## 2. 단일 입력과 출력 정책

- 모든 서버 이벤트는 `CLogger::WriteLog()` 하나로 제출한다. 이벤트 호출부에서 파일 전용·콘솔 전용을 지정하지 않는다. 서버 이벤트에서 기존 `WriteLogConsole()`로 직접 출력하는 경로는 대체한다.
- `CLogger::Start()` 이후 생산자 스레드마다 미리 등록한 고정 용량 SPSC 큐 하나를 사용한다(채팅 서버 설정 샘플은 1,024건). 서버 이벤트용 `WriteLog()`는 해당 스레드의 큐에 레코드를 넣고 반환하며 파일·콘솔에는 직접 쓰지 않는다. 단일 로그 스레드는 한 라운드에 생산자당 최대 64건을 처리한 뒤 `ServerConfig.conf`의 `Logging:`에 필수로 명시한 `LOG_POLL_INTERVAL_MS`만큼 대기한다(정수 `1..1000` ms, 샘플은 `10` ms). 로그마다 깨우지는 않으며 종료 요청을 확인한 뒤 잔여 큐를 비울 때는 주기 대기를 생략한다. 생산자별 FIFO는 유지하지만, 큐 사이의 기록 순서는 생산 시각 순서로 보장하지 않는다.
- 로그 스레드는 같은 레코드에 `CONSOLE_LOG_LEVEL`과 `FILE_LOG_LEVEL`을 독립적으로 적용한다. 예를 들어 콘솔 `Info`, 파일 `Debug`이면 `Debug`가 파일에만 남는 것은 설정의 결과다. `[Info]`는 서버 초기화 성공·워커 시작·프로세스 종료 등 서버 상태 확인에, `[Debug]`는 세션 진입·이탈, 로그인 성공, 섹터 입장 등 반복되는 진단에, `[Error]`는 실패와 오류 코드에 쓴다. `ELogLevel`은 `Debug`, `Info`, `Error`만 둔다.
- 큐가 꽉 차면 생산자는 대기·무한 재시도·동기 출력으로 우회하지 않는다. 레벨별 누락 수를 집계하고 로그 스레드가 합산한다. 정상 패킷별 로그는 기본으로 끄고 반복 오류는 유형별로 제한·합산한다. 인증값·키·패킷 덤프·실제 대화문은 기본 로그에서 제외한다.

## 3. 포맷과 C++20 적용

- 콘솔과 파일은 [공통 코딩 컨벤션](../../Rule/001_공통_코딩컨벤션.md#오류데이터)의 `필드 | 본문` 형식을 공유한다. `datetime`은 생산 시점 UTC, `Thread ID`는 생산자 스레드, `SessionID`가 없으면 `-`다. `event`는 고정 영문 식별값을 쓰고 필요 시 `phase`, `result`, `reason`, `error_code`, `run_id` 등을 추가한다. 서버와 클라이언트의 `SessionId`는 별개다.

  ```text
  [datetime][log level][로그 발생 프로젝트명][Thread ID][SessionID][함수 : 코드 라인] key=value ... | 한국어 본문
  [2026-11-19T10:20:30.123Z][Error][ChatServer][42][1037][onRecv : 123] event=recv_failed error_code=10054 | 수신 중 연결이 끊겼습니다.
  ```

- `SLogEntry`의 멤버는 두 개만 둔다. `level`(`ELogLevel`)은 로그 스레드가 콘솔·파일 레벨을 각각 적용하는 데 쓰고, `message`는 헤더·`key=value` 필드·` | ` 구분자·한글 본문을 모두 담은 **완성된 로그 한 줄**이다.
- 생산자가 `WriteLog()`에서 발생 시각·생산자 Thread ID·세션 ID·호출 위치를 반영해 `std::wstring`으로 한 줄을 완성한 뒤 큐에 소유권을 넘긴다. 로그 스레드는 레벨을 다시 파싱하거나 한 줄을 재조립하지 않는다. 프로젝트는 실행 파일 이름이 아니라 로그 호출 지점이 속한 프로젝트다. 세션 포인터·임시 문자열 포인터·`va_list`는 큐에 넣지 않는다.
- SPSC 인덱스는 `std::atomic`, 시각·주기는 `std::chrono`, 호출 위치는 `std::source_location`을 사용한다. 메시지 포맷은 기존 가변 인자와 고정 버퍼를 유지한다. `CLogger::Start()`에서 실행별 원본 파일을 동기로 열고, 실패하면 스레드를 시작하지 않는다. 성공하면 열린 파일을 `std::thread`에 넘기고, 이후 쓰기·flush·닫기는 로그 스레드가 담당한다.
- 실제 Windows 콘솔이면 `GetConsoleMode()`로 확인하고 `WriteConsoleW()`에 UTF-16을 넘긴다. stdout이 파일·파이프로 리디렉션되면 UTF-8로 쓴다. `> stdout.txt`는 콘솔의 캡처라 `CONSOLE_LOG_LEVEL`을 따르고, 로거 원본은 `FILE_LOG_LEVEL`을 따른다.
- 비동기 원본은 작업 디렉터리 기준 `LogFile/run-<시각 카운트>-<번호>/YYMMDD-HHMMSS-실행파일명.log`에 BOM 없는 UTF-8로 기록한다. 파일명에는 로거 시작 시각(UTC)과 `.exe`를 뺀 실행 파일 이름을 쓴다. 같은 초에 실행해도 실행별 폴더로 구분한다. 비동기 경로는 파일별 락 맵을 사용하지 않으며 시작할 때만 파일을 연다. 기존 동기 경로(서버 이벤트용 `WriteLog()`의 시작 전 출력과 `CLanClient` 등이 쓰는 기존 오버로드)는 파일별 락 맵을 계속 사용한다.

## 4. 종료와 재사용 경계

- `Stop()` 호출 전에 생산자의 등록과 로그 제출을 끝낸다. `m_isStopRequested`는 새 등록·제출을 막고 출력 스레드에 종료를 알린다. 출력 스레드가 남은 로그를 기록하고 파일을 닫으면 `Stop()`이 스레드를 join한 뒤 생산자를 해제한다. `/exit`와 백그라운드 작업이 남은 부분 기동 실패의 `ExitProcess()`는 drain을 보장하지 않는다. 부분 기동 중 워커 생성 실패의 원인은 `WriteEmergencyLogToStderr()`로 별도 기록하며, 이 경로는 비동기 원본에 쓰지 않는다.
- `NetworkLib`는 사건과 카운터의 출처다. 큐·출력·파일 경로·`/metrics`·수집 제품 선택을 네트워크 라이브러리에 넣지 않는다. `ChatServer`가 출력과 어댑터 설정을 연결한다. 추후 `Observability` 안에 `Logging`과 `Metrics`를 나누는 방안은 후보이며, 물리 이관과 라이브러리 개수 결정은 서버 로그 개선 범위에서 제외한다.

## 5. 구현 순서와 확인 기준

각 단계의 결과를 사용자 검토한 뒤 다음 단계로 진행한다.

| 단계 | 변경 범위 | 완료 확인 |
|---|---|---|
| **서버 이벤트 입력 통합 (완료)** | 현재 MHLib 위치에서 호출부를 단일 `WriteLog()`로 통합한다. 레벨·이벤트 필드와 한글 본문을 구분하고, 호출부의 출력 대상 지정은 없앤다. | 서버 시작·네트워크 오류·콘텐츠 전이 대표 경로가 같은 엔트리로 들어오고 연결·채팅이 기존대로 동작한다. 콘솔/LAN 클라이언트 호출 동작은 보존한다. |
| **MHLib SPSC 큐 구현 (완료)** | `MHLib::containers::CLFSpscQueue`를 범용 고정 용량 링으로 구현한다. 생산자 한 스레드만 `TryEnqueue()`, 소비자 한 스레드만 `TryDequeue()`를 호출한다. 꽉 찼거나 비어 있으면 대기하지 않고 실패를 반환한다. 이번 작업은 큐와 단독 테스트까지며 `CLogger`에 연결하지 않는다. | 정확한 용량, 빈 큐·포화, FIFO, 인덱스 순환, 이동 전용 값과 실패 시 소유권 보존, 실제 두 스레드 전달을 검증한다. |
| **로거 연결과 단일 출력 스레드 (완료)** | 생산자별 큐 등록과 주기 소비, 독립 레벨 필터, 콘솔 어댑터, 실행별 원본 한 파일, 로거 drain. | [서버 비동기 로거 확인 결과](#서버-비동기-로거-확인-결과) 참조. |
| **원본 분할 도구 (완료)** | 서버에서 별도 파일들을 쓰지 않고, 오프라인 도구가 원본을 읽어 프로젝트명·Thread ID·SessionID·레벨별로 또는 조합으로 필터링·분할한다. | 네 기준과 조합으로 분할한 결과가 맞고 원본은 변경되지 않는다. |

- 분할 도구의 입력 파일 경로는 선택 인자다. 경로를 지정하면 그 파일만 처리한다. 생략하면 명령을 실행한 작업 디렉터리의 `LogFile/run-*`에서 원본 `.log`만 찾고, 파일명에 기록된 UTC 시작 시각이 가장 최근인 원본 한 개를 선택한다. 같은 초에 시작한 실행은 실행 폴더의 시각 카운트와 번호를 숫자로 비교해 구분한다. 선택한 경로를 표시하고, 후보가 없으면 오류로 종료한다. 분할 결과는 자동 탐색 대상에서 제외한다.
- [분할 도구 사용법](../../../Tools/LogSplitter/README.md). CMD를 통한 통합 테스트와 실제 Release 채팅 서버 원본의 레벨별 분할에서 결과 바이트 및 원본 불변을 확인했다.

### 서버 이벤트 입력 통합 확인 결과

- `Chatting.sln` x64 Debug/Release 빌드 통과. 점유 포트의 `bind_failed`(`[Error]`, `10048`)와 두 클라이언트의 Ready·양방향 전달을 두 구성에서 확인했다. 시작·진입·로그인·섹터 이벤트의 구조화 레코드가 원본 파일과 리디렉션된 stdout에서 일치했다. 검증 재실행: `python -B Tests/Chatting/test_server_event_input.py bind Release`, `python -B Tests/Chatting/test_server_event_input.py chat Release`.
- 서버 준비·워커 시작은 `Info`, 세션 진입·이탈, 로그인 성공, 섹터 입장은 `Debug`를 확인했고 `ELogLevel::System`은 삭제했다. 시작 실패 요약 `server_start_failed`는 `Error`로 검증했으며, `Start()`가 `TRUE`로 반환할 때의 `Info` 요약은 실행하지 않았다.
- 공용 Config·입력 진단, 모니터 화면과 `/exit` 수명은 그대로다. 실제 Windows 콘솔 렌더링 및 SPSC 포화·drain은 이번에 검증하지 않았다.

매초 출력하던 기존 모니터 화면은 제거했다. 이후 지표 수집·게시를 기존 로그 스레드 콜백으로 옮기고 `SMonitorTimerEvent`를 제거했다. 전환 및 검증 내용은 [구버전 콘텐츠 런타임과 모니터 제거 계획](012_구버전_콘텐츠_런타임과_모니터_제거_계획.md)에 있다.

### MHLib SPSC 큐 확인 결과

- `CLFSpscQueue(capacity)`가 수용량 `N`에 내부 슬롯 `N+1`개를 한 번 확보한다. `TryEnqueue()`와 `TryDequeue()`는 용량을 변경하지 않는다. 생산자가 값 생성 후 쓰기 인덱스를 `release`로 공개하고 소비자는 `acquire`로 읽는다. 소비자는 슬롯 정리 후 읽기 인덱스를 `release`로 공개하고 생산자는 `acquire`로 읽은 뒤 재사용한다. 자신의 인덱스 읽기는 `relaxed`다.
- 캐시라인을 분리한 구현을 `CLFSpscQueue.h` 하나로 정리했다. [캐시라인 분리 및 대기 정책 측정 결과](../../../Tests/SpscQueue/README.md)는 단독 큐 벤치마크이며, 실제 로거의 처리량이나 대기 주기 검증은 아니다.
- 정렬 전 구현은 `SpscQueueTests.vcxproj`의 `RunTests`를 x64 Debug/Release에서 통과했다. 정렬 적용 후 같은 기능 테스트를 별도 x64 최적화 빌드에서 실행해 용량 거부·포화·빈 큐·FIFO·인덱스 순환·이동 전용 객체의 소유권 보존 및 두 스레드 간 50만 건 순차 전달을 확인했다. 기본 Release `RunTests` 빌드는 의도한 정렬 패딩 경고 `C4324`가 `/WX`에서 오류로 처리되어 실행 전에 막혔다. 프로젝트 경고 설정은 변경하지 않았다.

### 서버 비동기 로거 확인 결과

- `AsyncLoggerTests.vcxproj`의 `RunTests`를 x64 Debug·Release에서 통과했다. stdout 출력이 막힌 동안 두 생산자가 제출을 완료하는지, 생산자별 FIFO와 포화 누락 집계, 독립 레벨 필터, UTF-8, `Stop()`의 잔여 로그 처리를 확인했다.
- Release 채팅 서버에서 점유 포트의 `bind_failed`(`10048`), 유효·무효 `LOG_POLL_INTERVAL_MS` 설정, 루프백 두 클라이언트의 양방향 채팅을 확인했다. 서버 실행별 원본이 하나이며 새 파일명 형식과 BOM 없는 UTF-8 기록을 확인했다.
- Windows ConPTY에서 한글·이모지·CRLF와 콘솔 필터를 확인했다. 실제 콘솔 창의 글리프는 수동 확인하지 않았다. 이 결과는 로거 자체 검증이며, 원본 분할과 외부 수집 결과는 각각 별도로 기록했다.

### 외부 로그 수집

- **완료:** 원격 Windows 노드의 ChatServer 원본 로그가 Loki에 도착하고 Grafana에서 조회되는 것을 확인했다.
- [Alloy 설정](../../../Infra/Monitoring/alloy/config.alloy)은 `CHATSERVER_LOG_GLOB`으로 `server-*/LogFile/run-*/*-ChatServer.log`에 해당하는 원본만 찾는다. `loki.source.file`에서 `loki.write`로 전달하며, `LOKI_PUSH_URL`을 통해 tailnet 전용 수신 경로로 보낸다. 분할 결과는 수집하지 않는다.
- Grafana의 **Dashboards → ChatServer 로그**를 열면 `{service="chatserver"}` 쿼리가 자동으로 실행된다. 기본은 최근 1시간, 최신순 최대 500줄, 10초마다 새로고침이다.
- 완료 범위는 원본 수집과 조회다. 재시작 후 읽기 위치 보존, 보존 기간·재수집, 관측 장애 시 동작은 이번 완료 범위에 포함하지 않는다. Loki 연결은 더미 테스트 합격 조건이 아니다.
