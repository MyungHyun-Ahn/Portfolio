# ContentsRuntime 1차 계획: 실행단위 확정

상태: **Phase 1·2 구현·검증 및 사용자 코드 확인 완료. Phase 3~6 미착수.** Phase 3 선행 작업인 [패킷 생성기 개편과 채팅 콘텐츠 이전](002_패킷_생성기_추가계획.md#후속-계획-패킷-생성기-개편)은 구현·검증과 사용자 검수를 마쳤다. 이 계획은 [분산 서버 구성 계획](008_MMO_분산_서버_구성_계획.md)의 첫 단계이며, 실제 DB/RPC 연동은 완료 기준이 아니다.

## 실행단위

- 게임 서버의 실행단위는 `User`가 아니라 **맵 인스턴스**로 잡는다. `Dungeon`은 콘텐츠 종류이며 같은 종류의 던전 두 개는 서로 다른 `MapInstanceId`를 가진다. 유저는 맵 인스턴스에 속한다.
- 한 인스턴스의 입력 처리와 프레임 갱신은 서로 겹쳐 실행하지 않는다. 맵에 진입한 캐릭터의 실시간 상태는 그 맵의 실행 경계 안에서만 변경하므로, 게임 로직은 캐릭터마다 락을 잡지 않는다. 외부 큐와 실행권 인계에 필요한 동기화까지 없앤다는 뜻은 아니다.
- 스레드는 실행 자원이지 소유권의 기준이 아니다. `ContentsRuntime`의 워커 `N`개에 여러 `IContents` 인스턴스를 배정한다. 게임의 맵 인스턴스는 `IContents`를 구현하며, 프레임은 필요한 인스턴스에만 등록한다. 초기 배정과 실행 중 재배치는 아래에서 분리해 설계한다.
- 신규 MMO 콘텐츠의 동적 객체는 [C++ 소유권 규칙](../../Rule/002_Cpp_코딩컨벤션.md#소유권오류)에 따라 TLS 풀 대신 스마트 포인터로 관리한다. 캐릭터가 맵을 옮길 때는 단독 소유권을 인계하고, 같은 맵의 담당 워커만 바뀔 때는 소유권을 그대로 유지한다.
- 블로킹 DB 작업은 게임 서버에 붙는 `DBConnectorLib`의 `DbExecutor` 하나가 전용 워커 `M`개에서 실행한다. DB 작업 한 건은 일회성 `DbJob`이며 게임 워커나 IOCP 워커에서 실행하지 않는다. 초기 검증은 DB 워커 1개로 시작하고, `N`과 `M`은 독립 설정으로 둔다. 라이브러리 구현은 후속 범위다.
- 각 `IContents` 인스턴스에는 자신에게 돌아오는 완료 콜백 큐가 있다. `ContentsRuntime`은 같은 인스턴스에서 완료 콜백·패킷 처리·프레임을 겹치지 않게 실행한다. 처음에는 람다 콜백을 사용하고, C++20 코루틴 포팅은 현재 범위와 선행 조건에서 제외한 장기 선택 과제로 둔다.

## IContents 정의 초안

`IContents`는 가상 함수만 선언하는 인터페이스가 아니라, **인스턴스 ID와 자기 완료 큐를 가진 공통 베이스 클래스**다. 아래는 [Phase 1 구현](../../../Server/ContentsRuntimeLib/IContents.h)의 핵심 선언을 요약한 것이다.

```cpp
namespace ContentsRuntimeLib
{
	using ContentsInstanceId = std::uint64_t;

	class CContentsRuntime;

	class IContents
	{
	public:
		virtual ~IContents() = default;

		[[nodiscard]]
		ContentsInstanceId GetInstanceId() const noexcept;

	protected:
		explicit IContents(ContentsInstanceId instanceId) noexcept;

		// 프레임을 등록한 인스턴스에서만 호출한다.
		virtual void OnFrame();

	private:
		friend class CContentsRuntime;

	private:
		const ContentsInstanceId m_instanceId;
		std::deque<std::function<void()>> m_completionQueue;
	};
}
```

- **완료 등록:** DB·RPC는 `IContents*`를 보관하거나 큐를 직접 건드리지 않는다. `CContentsRuntime`에 대상 인스턴스 ID와 람다를 넘기면, 런타임이 등록 상태를 확인해 대상 큐에 넣는다. 늦게 도착한 완료가 다른 인스턴스에 들어가지 않도록 인스턴스 ID는 런타임 수명 동안 재사용하지 않는다.
- **완료 실행:** Phase 1의 고정 배정에서는 담당 워커의 작업 락이 완료 큐 게시·꺼내기와 대기 조건을 함께 보호한다. 워커는 락을 놓고 콜백을 실행한다. 같은 인스턴스에서는 `OnFrame()`과 완료 콜백이 겹치지 않으며, 이 락으로 맵 상태를 보호하지 않는다. 재배치 중 완료 게시와 깨우기는 Phase 4에서 다룬다.
- **맵 구현:** `CMapInstance`는 `IMap`을 통해 `IContents`를 상속하고, 캐릭터와 맵 상태를 소유한다. 런타임 등록 시 프레임 사용 여부만 지정한다. 프레임을 쓰는 인스턴스는 런타임의 공통 `FrameInterval`을 사용하며, `OnFrame()`을 재정의했다는 이유만으로 주기 실행하지 않는다.
- **밀린 프레임:** 실행 중에는 틱을 버리지 않는다. `OnFrame()` 한 번에 이전 예정 시각을 `FrameInterval`만큼 전진시키며, 아직 밀려 있어도 같은 인스턴스는 워커 순회당 한 번만 실행한다. 완료 콜백은 프레임과 별도로 순회당 최대 한 건을 처리한다. 여유가 생기면 남은 틱을 따라잡지만, 지속 과부하에서는 지연이 누적될 수 있다.

## IMap 정의 초안

`IMap`은 게임 서버에 두는 맵 전용 인터페이스다. `IContents`의 인스턴스 ID와 실행 경계를 그대로 사용하고, 맵 사이에서 캐릭터를 인계하는 계약만 추가한다. 아래 타입명과 선언은 초안이며, 같은 프로세스 내 맵 이동을 대상으로 한다.

```cpp
namespace GameServer
{
	using CharacterId = std::uint64_t;
	class CCharacter;
	class IMap : public ContentsRuntimeLib::IContents
	{
	public:
		// 이동 준비가 끝난 캐릭터의 소유권을 꺼낸다. 실패하면 맵에 남긴다.
		[[nodiscard]]
		virtual std::unique_ptr<CCharacter> DetachCharacterForTransfer(CharacterId characterId) = 0;

		// 접수된 이동의 캐릭터를 추가 입장 판정 없이 등록한다.
		virtual void AttachAdmittedCharacter(std::unique_ptr<CCharacter> upCharacter) = 0;

	protected:
		using ContentsRuntimeLib::IContents::IContents;
	};
}
```

- 각 함수는 해당 `IMap`의 담당 워커에서만 실행한다. 출발 맵은 캐릭터 상태 변경 Job의 완료 콜백과 목적지 접수를 마친 뒤 분리한다. 목적지 등록 전에는 인계 작업이 캐릭터를 단독 소유한다.
- 목적지 접수 전에만 이동을 거절할 수 있다. 거절 시 출발 맵은 캐릭터를 분리하지 않으므로 별도 복구 API가 필요 없다. 접수 뒤 목적지 등록은 새 입장 판정이 아니라 이미 접수한 인계를 완료하는 단계다.
- 이동 요청 접수, 캐릭터별 Job 추적, `MoveJob` 전달과 패킷 디스패치는 게임 서버가 맡는다. `IMap`이 상대 맵의 핸들러를 직접 호출하거나 `ContentsRuntimeLib`가 캐릭터·세션 타입을 알 필요는 없다.

## 요청 처리와 인계

| 상황 | 실행 위치와 책임 |
|---|---|
| 플레이 중 패킷 | 맵은 `OnFrame()`에서 자기 소속 캐릭터의 수신 패킷만 꺼낸다. 프로토콜별 읽기 전용 디스패처 하나가 opcode로 핸들러를 고른다. 호출 시 현재 맵을 참조로 넘기므로 맵 상태는 공유하지 않는다. |
| 마을·던전 제한이 있는 요청 | 장소를 이유로 다른 맵으로 보내지 않는다. 현재 맵의 핸들러가 장소·캐릭터 상태를 확인하고, 허용되지 않으면 게임 요청으로 거절한다. |
| 인스턴스 이동 | 출발 맵이 수신 큐 읽기를 멈추고 진행 중인 상태 변경 Job을 완료 콜백까지 처리한 뒤, 캐릭터와 연결의 소비권을 `MoveJob`으로 넘긴다. 무소속 동안 입력은 세션의 기존 `RecvQueue`에 그대로 쌓인다. |
| DB·RPC 같은 외부 결과 | 외부 스레드는 캐릭터를 직접 수정하지 않고 요청을 시작한 인스턴스의 완료 큐에 결과를 전달한다. 이동을 준비하는 중에도 기존 맵은 콜백을 실행하며, 실행 시 접속 세대와 소속을 확인한다. |

### 맵 이동과 MoveQueue

1. **출발 맵:** 이동 요청을 처리한 순간 해당 연결의 다음 패킷부터 꺼내지 않는다. 이미 진행 중인 캐릭터 상태 변경 Job은 출발 맵에서 완료 콜백까지 마친다. 맵 워커 자체는 기다리지 않고 다른 캐릭터와 프레임을 처리한다.
2. **목적지 접수:** 출발 맵이 아직 캐릭터를 소유한 상태에서 입장 조건을 판정하고, 목적지 수명 참조를 확보한 뒤 `MoveQueue` 락 아래 접수 가능 상태를 확인하고 큐·입장 자리를 예약한다. 맵 상태가 필요한 입장 판정은 목적지 워커가 맡는다. 목적지가 없거나 닫혔거나 자리를 예약하지 못하면 출발 맵에 그대로 남기고 실패 `ResMove`를 보낸 뒤 패킷 소비를 재개한다. 분리 전에 이동이 취소되면 예약도 해제한다.
3. **무소속:** 접수 성공 뒤 출발 맵 워커는 락 밖에서 기존 맵 소속을 제거하고, 필요한 경우 그 맵에만 속한 상태를 정리한 뒤 연결 소비권을 분리한다. 연결 종료용 `OnLeave()`를 호출하거나 캐릭터를 해제하지 않고, 캐릭터 소유권과 연결 식별자를 담은 `MoveJob`을 예약된 자리에 게시한다. 예약된 게시에는 큐 용량 재검사나 입장 거절이 없다. 인계 중에는 어느 맵도 수신 큐를 읽지 않으며, IOCP는 맵 소속을 조회하지 않고 수신을 계속 적재한다. 별도 이동용 입력 큐를 두거나 패킷을 다른 큐로 복사하지 않는다.
4. **목적지 맵:** 정해진 처리 시점에 자기 `MoveQueue`에서 `MoveJob` 하나를 꺼내고 락을 푼다. 접수한 이동은 다시 입장 판정을 하지 않고 등록한다. 새 맵 등록과 소비권 인계가 끝나면 성공 `ResMove`를 보내고 기존 수신 큐를 FIFO로 이어서 읽는다. 이동 중 연결 종료는 입장 거절이 아니라 별도 연결 정리로 처리한다.

맵 종속 패킷에 담긴 맵 인스턴스 ID는 실행 시 서버가 확정한 현재 소속과 비교한다. 패킷의 ID로 라우팅하지 않으며, 불일치하면 해당 요청만 거절한다. 접수 실패 뒤에도 실패한 목적지를 대상으로 보낸 요청은 출발 맵에서 실행하지 않는다. `MoveQueue` 락은 접수·예약·게시·꺼내기와 종료 상태 전환에만 사용한다. 맵 상태를 보호하기 위한 캐릭터별 락이나 두 맵에 걸친 락은 두지 않는다. 수신 큐 자체와 네트워크 세션 수명에 필요한 동기화는 이와 별개다.

### 맵 소멸 조건

- 담당 워커가 소속 유저가 없음을 확인한 뒤, `MoveQueue` 락 안에서 큐가 비었고 **아직 게시되지 않은 예약과 이미 꺼내서 처리 중인 이동도 없음**을 확인한다. 이 조건 확인과 새 접수를 닫는 상태 전환은 같은 임계 구간에서 수행한다.
- 종료 전환이 먼저면 새 이동 접수는 실패한다. 접수가 먼저면 그 예약과 이동의 처리가 끝날 때까지 맵을 없애지 않는다. 실제 객체 해제는 등록 해제 후 목적지 조회나 워커 실행 등 맵을 사용하는 곳이 모두 끝난 뒤에 한다. 이미 소멸한 큐의 락으로 접수 실패를 판별하지 않는다.

### 수신 인터페이스

```cpp
// ServerNetworkLib::CServer의 수신 API
[[nodiscard]]
bool TryPopRecvPacket(UINT64 sessionId, RecvPacketPtr &outPacket) noexcept;
```

- `CServer`가 기존 슬롯에서 세션을 조회하고 I/O 참조를 올린 뒤, 해제 플래그와 세션 ID를 확인해 `CSession::m_recvMsgQueue`에서 패킷 한 건을 꺼낸다. 세션 사용이 끝나면 참조를 내린다. 한 건을 꺼냈을 때만 `true`를 반환하며, 꺼낸 View는 `RecvPacketPtr`가 풀에 반환한다. 별도 락·슬롯 테이블·수신 큐를 추가하지 않는다.
- 맵의 `OnFrame()`은 소속 연결의 세션 ID로 이 함수를 부른다. `IContents`와 `ContentsRuntimeLib`에는 세션·수신 API를 넣지 않는다. 어느 맵이 읽을지는 게임 서버 소속 규칙이 보장한다.
- 연결 종료는 수신 결과와 분리한다. 테스트 월드의 `OnClientLeave()`는 담당 맵에 연결 제거 작업을 등록하고, 담당 워커가 맵 소속을 정리한다.
- 패킷은 한 개씩 꺼낸다. 이동을 시작한 핸들러가 끝난 뒤에는 다음 패킷을 미리 꺼내지 않는다. 이동 중 연결이 종료되면 목적지가 끊어진 연결을 활성 소속으로 등록하지 않으며, 남은 패킷은 네트워크의 세션 정리 경로가 반환한다.

## ContentsRuntimeLib 분리안

**Phase 1 런타임은 `Server/ContentsRuntimeLib`에 분리했다.** 지금 채팅 서버에 쓰이는 `CBaseContents`와 `CContentsThread`는 `Server/NetworkLib`에 그대로 유지한다. 새 런타임은 아래 경계를 따른다.

새 라이브러리에는 이전 `ContentsRuntime` 구현을 별도로 보존하지 않는다. 남아 있는 원본은 수정하지 않고, `FContentThread`의 워커 등록·시작·종료(`join`)와 작업 도착 또는 다음 프레임 시각에 워커를 깨우는 방식만 참고한다. 기존 라우팅과 Delegate·Work Stealing 정책은 첫 구현에 이식하지 않는다.

- `IContents`는 기존 `IContent`를 복사하지 않고 새로 설계한다. 인스턴스 식별과 자기 완료 큐를 공통으로 두되, 세션 입퇴장과 패킷 처리를 모든 콘텐츠에 강제하지 않는다. 맵 인스턴스는 새 인터페이스를 구현하고, 프레임은 필요한 콘텐츠만 등록한다.
- `ServerNetworkLib`: 소켓, IOCP, 비공개 세션 수신 큐와 패킷 송수신 수명. 게임 서버에는 패킷 꺼내기 API만 노출한다.
- `ContentsRuntimeLib`: 실행단위 등록·식별, 작업 전달·직렬 실행, 워커 배정과 프레임 스케줄링. 던전 규칙이나 opcode를 알지 않는다.
- `DBConnectorLib`: DB 연결·쿼리·트랜잭션과 `DbExecutor`. `ContentsRuntimeLib`와 직접 의존하지 않으며, 게임 서버가 완료 결과를 요청을 시작한 콘텐츠에 연결한다.
- 게임 서버: 맵·캐릭터 상태, 연결의 게임상 소속과 이동 정책, 프레임에서 패킷 꺼내기, 디스패치·핸들러. 핸들러에 빌려준 패킷은 처리 범위 밖에 보관하지 않는다.

경매장·길드 등은 맵 프레임 런타임을 의무로 참조하지 않는다. 실제 공통 수요가 생기면 직렬 실행과 작업 큐처럼 필요한 요소만 재사용한다.

## 콘텐츠 배치와 Delegate 초안

`ContentsRuntime`이 `ContentsInstanceId → 담당 워커` 배정을 관리한다. **배정 단위는 인스턴스 전체**다. 한 워커가 여러 인스턴스를 맡을 수 있지만, 같은 인스턴스의 패킷·프레임·완료 콜백을 두 워커가 나눠 실행하지 않는다.

| 시점 | 배정 방식 |
|---|---|
| 최초 등록 | 게임 서버가 워커를 지정할 수 있다. 지정하지 않으면 런타임이 활성 워커 가운데 배정된 인스턴스 수가 가장 적은 쪽을 선택한다. 인스턴스 수는 초기 배치의 기준일 뿐, 실제 부하로 간주하지 않는다. |
| 실행 중 재배치 | **Delegate** 요청은 수동으로 제출하거나 런타임 내부 관리 콘텐츠가 정책 판단에 따라 제출한다. 런타임이 요청을 검증하고 출발 워커가 실행 경계에서 인스턴스 전체를 넘긴다. 여유 워커가 다른 워커의 큐에서 직접 작업을 꺼내는 **Work Stealing**은 이번 계획에 넣지 않는다. |

### Delegate 실행권 인계

1. **요청:** 런타임은 인스턴스별로 재배치 요청 하나만 유지한다. 종료 중인 워커나 등록 해제 중인 콘텐츠에는 새 재배치를 접수하지 않는다. 목적지 등록을 확보하지 못하면 출발 워커가 계속 실행한다.
2. **전환:** 출발 워커는 실행 중인 프레임 또는 콜백이 끝나는 경계에서 새 실행을 멈춘다. 런타임이 출발 워커의 실행 예약을 무효화하고 담당 워커를 전환한다. 목적지 워커는 전환이 확정되기 전에는 실행하지 않는다.
3. **재개:** 인스턴스 ID, 맵 상태, 소속 유저, 완료 큐, `MoveQueue`와 다음 프레임 예정 시각은 그대로 유지한다. 바뀌는 것은 실행 워커뿐이다. 전환 중 도착한 작업도 같은 인스턴스 큐에 쌓고, 담당 워커 전환과 재실행 예약을 같은 동기화 경계에서 처리해 대기 작업이나 프레임이 누락되지 않게 한다.

캐릭터의 맵 이동과 맵의 워커 재배치는 별개다. Delegate는 `MoveJob`을 만들거나 캐릭터를 무소속으로 바꾸지 않는다. 기존 런타임에서는 작업 경계에서 담당 워커를 바꾸는 흐름만 참고하고, 기존 라우팅 갱신과 자동 부하 정책은 이식하지 않는다.

### 관리 콘텐츠와 교체 가능한 Delegate 정책

- **실행 주체:** 자동 Delegate를 사용할 때만 `ContentsRuntime`이 내부 관리용 `IContents`를 하나 등록하고 기존 워커에 고정 배치한다. 서버 메인프레임이나 별도 관리 스레드를 만들지 않는다. 관리 콘텐츠는 Delegate 대상에서 제외하되 실행 시간은 담당 워커의 부하에 포함한다. 자동 Delegate를 꺼도 수동 인계는 동작한다.
- **실행 시점:** 관리 콘텐츠의 `OnFrame()`은 공통 `FrameInterval`을 따르되, 별도로 설정한 정책 평가 시각이 됐을 때만 워커별 측정 스냅샷을 읽고 정책을 호출한다. 인계 요청을 제출하면 완료를 기다리지 않고 반환한다. 런타임 종료가 시작되면 새 인계 요청을 받지 않는다.
- **정책 경계:** `IDelegatePolicy`는 읽기 전용 스냅샷을 받아 `이동 없음` 또는 `ContentsInstanceId + 목적지 워커 ID`를 반환한다. 런타임은 현재 배정과 등록·종료 상태를 다시 확인해 요청을 접수하며, 출발 워커가 실행 경계에서 실제 인계를 수행한다. 정책을 바꿔도 관리 콘텐츠의 실행 방식이나 인계 절차는 바꾸지 않는다.

### 프레임 예산 기반 정책 초안

- 같은 런타임에서 프레임을 쓰는 콘텐츠는 공통 주기를 공유한다. 동시에 시작하거나 서로의 종료를 기다리지는 않는다. 프레임을 등록하지 않은 콘텐츠와 별도 `DbExecutor`에는 이 주기를 적용하지 않는다.
- 워커는 `OnFrame()` 실행 시간과 **예정 시각 대비 시작 지연**을 따로 측정한다. 인스턴스의 프레임 부하는 `최근 평균 OnFrame() 실행 시간 ÷ FrameInterval`로 추정한다. 워커 부하는 소속 인스턴스의 프레임 부하 합에 프레임 밖에서 실행한 완료 콜백 등의 점유 비율을 더한다. 프레임이 밀려도 분모는 설정 주기를 쓰며, 프레임 안에서 실행한 작업은 중복 계수하지 않는다.
- 시작 지연이 여러 측정 구간에 걸쳐 지속되고 목적지 워커에 여유가 있을 때만 재배치를 검토한다. 늦게 시작한 맵을 곧바로 옮기지 않고, 후보 인스턴스의 부하를 출발지에서 빼고 목적지에 더해 **이동 후 최대 워커 부하를 가장 많이 줄이는 조합**을 고른다. 목적지에 여유가 남지 않거나 개선이 없으면 이동하지 않는다.
- 한 번에 하나만 옮기고 새 측정 구간을 확보한 뒤 다음 이동을 판단한다. 이동 효과는 예상 부하뿐 아니라 실제 프레임 시작 지연으로 확인한다. 단일 맵의 `OnFrame()` 자체가 예산을 넘는 경우는 Delegate로 빨라지지 않는다. 구체적인 평가 간격, 임계값과 여유 기준은 구현 후 부하 검증으로 정한다.

## Phase별 구현 및 검증 순서

각 Phase에서 확인 기준을 검증하고 사용자 검토를 마친 뒤 다음 Phase로 넘어간다. 먼저 고정 배정에서 콘텐츠와 캐릭터의 소유권을 검증하고, 그 위에 워커 재배치와 자동 정책을 순서대로 붙인다.

### Phase 1 — ContentsRuntimeLib와 고정 워커 배정

- **작업:** `Server/ContentsRuntimeLib`에 `IContents`와 `CContentsRuntime`을 만든다. 워커 시작·깨우기·종료, 인스턴스 등록과 고정 배정, 공통 프레임 주기와 인스턴스별 완료 큐까지만 구현한다. 게임 서버와 네트워크 연결은 이 단계에서 바꾸지 않는다.
- **완료 기준:** 워커 두 개에 배정한 테스트 콘텐츠에서 같은 인스턴스의 `OnFrame()`과 완료 콜백이 겹치지 않고, 서로 다른 인스턴스 상태가 섞이지 않는다. 프레임을 쓰지 않는 콘텐츠도 ID로 전달한 완료를 처리하며, 종료 시 워커가 모두 `join`된다.
- **구현 경계:** 인스턴스 등록은 `Start()` 전까지만 받는다. 시작·등록·종료는 제어 스레드가 맡는다. 외부 스레드의 `PostCompletion()`은 실행 중에만 받으며, `Stop()`이 접수를 닫으면 이미 접수된 콜백을 비우고 워커를 `join`한다. 런타임 재시작은 지원하지 않는다.
- **검증:** [Tests/WorldServer](../../../Tests/WorldServer/WorldServer.vcxproj)의 `RunTests`에서 x64 Debug·Release 통과. 네트워크 없이 두 워커의 고정 배정, 한 프레임이 대기하는 동안 다른 워커의 진행, 프레임 없는 인스턴스의 완료 처리, 완료 FIFO와 종료 중 접수 차단·큐 비우기를 확인했다. Release 실행 파일 30회 반복도 통과했다.
- **프레임 따라잡기 검증:** 첫 프레임을 여러 주기 동안 보류한 뒤, 같은 워커의 다른 인스턴스 완료 사이에서 밀린 프레임이 한 번씩 실행되는지 확인했다. 기존 스킵 구현에서는 실패했고, 변경 후 x64 Debug·Release와 Release 20회 반복에서 통과했다.
- **최종 확인:** 라이브러리 전용 `ContentsRuntimeLibPch`를 사용한다. 프레임 예정 시각은 `+= frameInterval`로 전진시키고, 완료 콜백은 담당 워커의 락 아래에서 큐로부터 `std::move`로 꺼낸 뒤 락을 풀고 실행한다. 변경 후 WorldServer `RunTests`가 x64 Debug·Release에서 통과했고, 사용자 코드 확인을 마쳤다.

### Phase 2 — 고정 배정 맵과 실제 수신 연결

- **작업:** 테스트 월드에 `IContents`를 구현한 `CMapInstance` 두 개를 고정 배치한다. 맵의 `OnFrame()`은 `CServer::TryPopRecvPacket()`으로 자기 소속 연결만 읽고, `CBaseContents`는 호출하지 않는다. 기존 채팅의 수신·세션 조회 경로는 변경하지 않는다.
- **완료 기준:** 루프백에서 두 맵의 패킷이 각자 소속 맵의 상태만 바꾼다. 잘못된 맵 ID가 담긴 요청은 해당 건만 거절하고, 콘텐츠가 `CSession`이나 `RecvQueue`를 직접 접근하지 않는다.
- **검증:** [FixedMaps](../../../Tests/WorldServer/FixedMaps.vcxproj)와 Phase 1 `WorldServer`의 `RunTests`가 x64 Debug·Release에서 통과했다. 실제 IOCP 루프백(Lan)에서 서로 다른 담당 워커, 맵별 누계, 잘못된 맵 ID 거절 후 정상 처리, 미지원 opcode 거절, 연결 제거 및 재접속을 확인했다. 기존 채팅은 두 구성에서 Net·Lan 모두 통과했다. MSBuild에서 `python`을 찾지 못하면 `/p:PythonExecutable=<python.exe 경로>`로 지정한다.
- **검증 범위:** 테스트 실행기가 자신이 시작한 서버 프로세스만 회수한다. 테스트 월드의 정상 종료와 같은 슬롯을 강제로 재사용한 뒤 이전 세션 ID로 조회하는 시험은 실행하지 않았다.
- **최종 확인:** 사용자 코드 확인과 커밋(`7ee7ee8`)을 마쳤다. 패킷 생성기 연동은 이 단계의 완료 범위에 포함하지 않는다.

### Phase 3 — 캐릭터 맵 이동

- **작업:** 워커 배정은 고정한 채 캐릭터별 상태 변경 Job의 완료 추적, 목적지 예약, `MoveQueue` 인계, 대상 맵의 패킷 소비 재개를 붙인다. 실제 DB/RPC 대신 테스트 완료를 지연시켜 출발 맵에서 완료를 처리하는 경계를 검증한다.
- **완료 기준:** 완료 콜백 전에는 캐릭터를 분리하지 않고, 무소속 동안 패킷을 꺼내지 않으며, 대상 맵 등록 후 기존 수신 큐의 FIFO를 이어서 처리한다. 예약 실패라면 출발 맵에 남고, 예약에 성공했다면 목적지의 재거절이 없다. 종료와 접수의 순서가 뒤바뀌는 경우와 이동 중 연결 종료도 확인한다.

### Phase 4 — 수동 Delegate

- **작업:** 인스턴스 ID와 목적지 워커를 지정해 인계 요청을 제출하고, 실행 경계에서 맵 전체의 실행권만 바꾸는 경로를 구현한다. 자동 판단은 넣지 않는다.
- **완료 기준:** 같은 맵 ID·캐릭터 소속·큐·다음 프레임 예정 시각을 유지하면서 담당 워커만 바뀐다. 전환 도중 들어온 완료 콜백이 한 번만 실행되고, 양쪽 워커의 동시 실행이나 이전 워커의 재실행이 없다. 목적지 등록을 확보하지 못하면 출발 워커가 계속 실행한다.

### Phase 5 — 관리 콘텐츠와 정책 교체 경계

- **작업:** 기존 워커에 내부 관리 콘텐츠를 고정 배치한다. 워커별 `OnFrame()` 실행 시간·시작 지연·프레임 밖 작업 점유를 스냅샷으로 제공하고, 관리 콘텐츠가 평가 주기에만 `IDelegatePolicy`를 호출한다. 실제 부하 판단 대신 고정 결과를 반환하는 검증용 정책으로 연결을 먼저 확인한다.
- **완료 기준:** 새 스레드나 메인프레임 없이 관리 콘텐츠가 평가 주기에만 정책을 호출하고, 결과를 Phase 4와 같은 인계 경로에 제출한다. 관리 콘텐츠 자체는 인계 대상이 아니며, 기능을 끄면 관리 콘텐츠 없이 수동 Delegate가 동작한다.

### Phase 6 — 프레임 예산 기반 자동 Delegate

- **작업:** 스냅샷의 프레임 예산 비율과 시작 지연을 바탕으로 이동 후보를 고르는 정책을 구현한다. 실제 실행권 인계나 관리 콘텐츠 코드는 바꾸지 않는다.
- **완료 기준:** 재현 가능한 부하에서 순간 지연이나 여유 워커가 없는 경우는 이동하지 않고, 지속 불균형에서는 한 번에 하나만 옮긴다. 고정 배정과 같은 부하로 비교해 이동 뒤 실제 프레임 시작 지연이 줄어드는지 확인한다.

`DBConnectorLib`와 경매장 RPC는 [분산 서버 구성 계획](008_MMO_분산_서버_구성_계획.md#진행-순서)의 별도 후속 작업이다. 실제 DB/RPC 연동에는 Phase 3의 완료·이동 계약이 필요하지만, 자동 Delegate는 선행 조건이 아니다. Work Stealing과 코루틴 전환은 Phase 1~6에 넣지 않는다.
