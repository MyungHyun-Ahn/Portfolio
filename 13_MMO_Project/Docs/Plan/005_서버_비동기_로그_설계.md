# 서버 비동기 로그 설계

상태: 서버 이벤트의 `WriteLog()` 경로 통합 완료(사용자 확인). `CLogger`는 기존 MHLib 위치에 있고, 통합된 서버 호출은 아직 기존 동기 콘솔·파일 출력을 사용한다. SPSC·독립 레벨 필터·분할 도구는 미착수다. DummyClient와 메트릭은 [별도 설계](004_DummyClient_검증과_메트릭_설계.md)를 따른다. 전체 작업 순서와 상태는 [로드맵](../ROADMAP.md#2차-서버-로그-개선-및-dummyclient-검증)을 기준으로 한다.

## 1. 통합 전 동작과 적용 범위

- `CLogger::WriteLog()`는 **작업 디렉터리 기준** `LogFile/<분류>/<YYYYMM>_<타입>.txt`에 UTF-16LE로 append 한다. 이번에 이미 빌드된 Release 서버 복사본을 격리된 임시 디렉터리에서, 테스트가 소유한 점유 루프백 포트로 실행했다. `LogFile/SYSTEM/*_NetworkLib.txt`의 BOM과 실제 `bind()` 오류 `10048`, 서버 종료 코드 `1`을 확인했다. 즉 네트워크 오류의 파일 기록 경로는 작동한다. 모든 실패 로그와 정상 플레이 로그의 파일 저장을 검증한 것은 아니다.
- 서버 ENTER/LEAVE/LOGIN/SECTOR, 모니터링 화면, 클라이언트 READY/CHAT 등은 현재 주로 `WriteLogConsole()`이다. `SetMainDirectory(L"LogFile")`이나 스모크의 `stdout.txt` 캡처는 그 메시지가 앱 로그 파일에도 남는다는 증거가 아니다. 기존 파일 write/close 성공 검사와 여러 프로세스가 같은 경로에 쓰는 경우는 별도 검증 대상이다.
- 현재 `CNetServer`의 `WSARecv()`·`WSASend()` 오류 경로는 `CLogger::WriteLog()`를 직접 호출한다. 기존 `CLogger`는 SRW 락 아래 로그마다 파일을 열고 쓰며, 콘솔 출력도 별도 락을 사용한다. 목표는 로거 전체의 락프리가 아니라 **서버 IOCP·콘텐츠 워커가 출력 락과 I/O를 기다리지 않게 하는 것**이다.
- 서버의 정상 이벤트가 대상이다. 콘솔·LAN 클라이언트의 기존 `CLogger` 사용이나 서버 패킷·전송·종료 수명을 한꺼번에 바꾸지 않는다. `MonitoringConsole()`의 주기 계측 화면은 [메트릭 연동](004_DummyClient_검증과_메트릭_설계.md#메트릭과-검증-결과-연동)에서 대체 패널을 검증할 때까지 유지하며, 새 이벤트 로그가 아니다.

## 2. 단일 입력과 출력 정책

- 모든 서버 이벤트는 `CLogger::WriteLog()` 하나로 제출한다. 이벤트 호출부에서 파일 전용·콘솔 전용을 지정하지 않는다. 서버 이벤트에서 기존 `WriteLogConsole()`로 직접 출력하는 경로는 대체한다.
- 생산자 스레드마다 미리 등록한 고정 용량 SPSC 큐 하나를 사용한다. `WriteLog()`는 해당 스레드의 큐에 레코드를 넣고 반환하며 파일·콘솔에는 쓰지 않는다. 단일 로그 스레드가 주기적으로 큐를 비운다. 생산자별 FIFO는 유지하지만, 큐 사이의 기록 순서는 생산 시각 순서로 보장하지 않는다.
- 로그 스레드는 같은 레코드에 `CONSOLE_LOG_LEVEL`과 `FILE_LOG_LEVEL`을 독립적으로 적용한다. 예를 들어 콘솔 `Info`, 파일 `Debug`이면 `Debug`가 파일에만 남는 것은 설정의 결과다. `[Info]`는 서버 초기화 성공·워커 시작·프로세스 종료 등 서버 상태 확인에, `[Debug]`는 세션 진입·이탈, 로그인 성공, 섹터 입장 등 반복되는 진단에, `[Error]`는 실패와 오류 코드에 쓴다. `ELogLevel`은 `Debug`, `Info`, `Error`만 둔다.
- 큐가 꽉 차면 생산자는 대기·무한 재시도·동기 출력으로 우회하지 않는다. 레벨별 누락 수를 집계하고 로그 스레드가 합산한다. 정상 패킷별 로그는 기본으로 끄고 반복 오류는 유형별로 제한·합산한다. 인증값·키·패킷 덤프·실제 대화문은 기본 로그에서 제외한다.

## 3. 포맷과 C++20 적용

- 콘솔과 파일은 [공통 코딩 컨벤션](../Rule/001_공통_코딩컨벤션.md#오류데이터)의 `필드 | 본문` 형식을 공유한다. `datetime`은 생산 시점 UTC, `Thread ID`는 생산자 스레드, `SessionID`가 없으면 `-`다. `event`는 고정 영문 식별값을 쓰고 필요 시 `phase`, `result`, `reason`, `error_code`, `run_id` 등을 추가한다. 서버와 클라이언트의 `SessionId`는 별개다.

  ```text
  [datetime][log level][로그 발생 프로젝트명][Thread ID][SessionID][함수 : 코드 라인] key=value ... | 한국어 본문
  [2026-11-19T10:20:30.123Z][Error][ChatServer][42][1037][onRecv : 123] event=recv_failed error_code=10054 | 수신 중 연결이 끊겼습니다.
  ```

- `SLogEntry`는 생산 시각(`std::chrono::system_clock::time_point`), 레벨, 프로젝트 식별자, 생산자 Thread ID, 선택적 세션 ID, 함수·코드 라인, 소유하는 구조화 필드와 본문을 담는다. 프로젝트는 실행 파일 이름이 아니라 로그 호출 지점이 속한 프로젝트다. 세션 포인터·임시 문자열 포인터·`va_list`를 큐에 넣지 않는다. 필드 타입·본문 저장·건별 힙 할당 여부는 구현 시 정한다.
- 표준 C++20을 우선한다. SPSC 인덱스는 대상 빌드에서 락프리임을 확인한 기본 타입의 `std::atomic`, 로그 스레드는 `std::jthread`, 시각·주기는 `std::chrono`를 사용한다. 기존 `...`/고정 버퍼 대신 `std::format_string`/`std::format`을 검토하고, `std::source_location`은 실제 호출 지점을 남기게 설계한다. 생산자는 본문을 만들 수 있지만 전체 출력 줄 조립은 소비자가 맡는다. 경로와 필터는 시작 시 확정하고 로거가 소유한다.
- **Windows API는 콘솔 출력 어댑터에만 남긴다.** 실제 Windows 콘솔이면 `GetConsoleMode()`로 확인하고 `WriteConsoleW()`에 UTF-16을 넘긴다. stdout이 파일·파이프에 리디렉션되면 UTF-8 바이트를 쓴다. 내부가 UTF-8이면 실제 Windows 콘솔 경로에서만 UTF-16으로 변환한다. `> stdout.txt`는 콘솔의 캡처라 `CONSOLE_LOG_LEVEL`을 따르고, 로거 원본은 `FILE_LOG_LEVEL`을 따른다.
- `std::filesystem::path`와 `std::ofstream`으로 원본 파일 하나를 로그 스레드만 열어 유지하고, 묶어서 기록·flush한다. 파일별 락 맵과 로그마다 파일을 여는 동작은 없앤다. open·write·flush 실패와 포맷 실패는 같은 로거로 재귀 보고하지 않는다. 원본 인코딩은 구현 시 확정하고 실제 수집 경로에서 검증한다.

## 4. 종료와 재사용 경계

- 정상 종료에서는 생산자 종료 → 접수 종료 → 남은 로그 drain/flush → 로그 스레드 join 순으로 처리한다. 시작 전 실패·크래시는 별도 최소 진단 경계로 두며 정상 이벤트의 출력 대상 선택으로 사용하지 않는다. 현재 `/exit`의 `ExitProcess()`는 drain을 보장하지 않는다. 로거 단독 종료는 테스트에서 검증하고 서버 종료 수명 변경은 별도 승인으로 다룬다.
- `NetworkLib`는 사건과 카운터의 출처다. 큐·출력·파일 경로·`/metrics`·수집 제품 선택을 네트워크 라이브러리에 넣지 않는다. `ChatServer`가 출력과 어댑터 설정을 연결한다. 추후 `Observability` 안에 `Logging`과 `Metrics`를 나누는 방안은 후보이며, 물리 이관과 라이브러리 개수 결정은 서버 로그 개선 범위에서 제외한다.

## 5. 구현 순서와 확인 기준

각 단계의 결과를 사용자 검토한 뒤 다음 단계로 진행한다.

| 단계 | 변경 범위 | 완료 확인 |
|---|---|---|
| **서버 이벤트 입력 통합 (완료)** | 현재 MHLib 위치에서 호출부를 단일 `WriteLog()`로 통합한다. 레벨·이벤트 필드와 한글 본문을 구분하고, 호출부의 출력 대상 지정은 없앤다. | 서버 시작·네트워크 오류·콘텐츠 전이 대표 경로가 같은 엔트리로 들어오고 연결·채팅이 기존대로 동작한다. 콘솔/LAN 클라이언트 호출 동작은 보존한다. |
| **SPSC와 단일 출력 스레드** | 생산자별 큐와 주기 소비, 독립 레벨 필터, 콘솔 어댑터, 실행별 원본 한 파일, 로거 drain을 구현한다. 큐 용량과 깨우기 주기는 이 작업에서 정한다. | 다른 레벨 설정에서 같은 이벤트의 콘솔·원본 선별이 맞고 생산자별 순서·중복·포화 누락 집계가 맞는다. 느린 출력에서 워커가 기다리지 않는지, attached 콘솔의 한글·이모지와 리디렉션 UTF-8 바이트, 줄 경계, 원본 기록·flush·종료 뒤 잔존을 각각 확인한다. |
| **원본 분할 도구** | 서버에서 별도 파일들을 쓰지 않고, 오프라인 도구가 원본을 읽어 프로젝트명·Thread ID·SessionID·레벨별로 또는 조합으로 필터링·분할한다. | 네 기준과 조합으로 분할한 결과가 맞고 원본은 변경되지 않는다. |

### 서버 이벤트 입력 통합 확인 결과

- `Chatting.sln` x64 Debug/Release 빌드 통과. 점유 포트의 `bind_failed`(`[Error]`, `10048`)와 두 클라이언트의 Ready·양방향 전달을 두 구성에서 확인했다. 시작·진입·로그인·섹터 이벤트의 구조화 레코드가 원본 파일과 리디렉션된 stdout에서 일치했다. 검증 재실행: `python -B Tests/Chatting/test_server_event_input.py bind Release`, `python -B Tests/Chatting/test_server_event_input.py chat Release`.
- 서버 준비·워커 시작은 `Info`, 세션 진입·이탈, 로그인 성공, 섹터 입장은 `Debug`를 확인했고 `ELogLevel::System`은 삭제했다. 시작 실패 요약 `server_start_failed`는 `Error`로 검증했으며, `Start()`가 `TRUE`로 반환할 때의 `Info` 요약은 실행하지 않았다.
- 공용 Config·입력 진단, 모니터 화면과 `/exit` 수명은 그대로다. 실제 Windows 콘솔 렌더링 및 SPSC 포화·drain은 이번에 검증하지 않았다.

### 외부 로그 수집

- 원본 파일만 Alloy `loki.source.file` → `loki.process` → `loki.write`로 수집한다. 분할 결과는 수집하지 않는다. `service`, `environment`, `role`, `level` 정도만 인덱싱하고 `run_id`, 세션 ID, 계정·메시지 ID는 로그 필드로 둔다. 보존·재수집은 운영 설정으로 분리한다.
- 실제 원본의 인코딩과 한글·이모지, Alloy 재시작 후 읽기 위치, 권한 오류·미수집 감지, 관측 장애 중 채팅 계속 동작을 확인한다. Grafana에서는 메트릭 시간 범위와 `service`로 이동해 `run_id` 등 고정 필드로 로그를 찾는다. Loki 연결은 로컬 로그 완료나 더미 합격의 조건이 아니다.
