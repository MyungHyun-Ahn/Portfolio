# 게임 데이터 생성기 선행 계획

## 우선순위와 범위

**Phase 0: 게임 데이터 생성기 최소판 → Phase 1: 플레이어 이동 동기화.** 첫 정적 테이블 `PlayerMovement` 하나로 Excel → CSV → 바이너리 생성과 양쪽 C++ 판독을 검증한 뒤 `GameClient` 작업을 시작한다. 첫 프로젝트 등록 자체에는 데이터가 필요 없지만, 이동 구현은 처음부터 원본 데이터에서 속도와 반경을 읽도록 한다. UE 적재·패키징과 서버 실제 소비는 각 앱 Phase로 남긴다. 전체 테이블 이관·배포 시스템·범용 런타임 매니저가 준비될 때까지 프로젝트 생성을 기다리지는 않는다.

프로젝트 공통 [게임 데이터 정책](../../Rule/001_공통_코딩컨벤션.md#게임-데이터)을 따르며, 기존 [이동 동기화 계획](../Client/001_플레이어_이동_동기화_계획.md#구현-순서와-완료-기준)의 번호는 유지한다. 외부 원본은 읽기 전용 참고 대상이다.

## 재사용과 제외

| 구분 | 가져오거나 유지할 것 | 가져오지 않을 것 |
| --- | --- | --- |
| 기존 `GameDataGenerator` | 사용자 테이블 템플릿, 워크북 읽기·일반 테이블 모델·셀 위치 진단·범용 검증, 검증 후 출력 교체 방식. 도구 호스트는 기존 .NET CLI와 Excel 파서를 우선 재사용한다. | 테이블 이름별 전용 검증, 이전 게임의 데이터·런타임 라이브러리, C# 생성 코드, JSON·YAML·스키마 파일 출력. 기존 문자열 PK 설정이나 지원 범위도 그대로 가져오지 않는다. |
| 별도 `TableGenerator` 사례 | 입력 검증, 클라이언트·서버별 헤더 생성과 바이너리 출력 분리. | 레거시 바이너리 호환, GUI, 생성 래퍼·리더, 암호화, 엔진 전용 타입 및 외부 시스템 연동. 그 도구의 실제 작성 경로는 워크시트를 읽으므로 CSV를 필수 중간 입력으로 만드는 부분은 이번 변경이다. |

[GameDataGenerator](../../../Tools/GameDataGenerator/README.md)는 [Tools.sln](../../../Tools/Tools.sln)에 등록한다. 일반 데이터 테이블은 클라이언트용/서버용 C++ 행 `struct` 헤더만 생성한다. **`Enum.xlsx`만 예외로, 모든 게임 데이터용 `enum class`를 공용 `GameDataEnums.h` 한 파일에 생성한다.** 콘텐츠 행·필드 값·키별 상수·엔진 매크로·로더 함수는 생성 헤더에 넣지 않는다. 도구가 .NET으로 구현되는 것과 C# 게임 코드를 생성하는 것은 별개다. 테이블별 읽기 시험은 수기 C++로 작성하며 범용 매니저나 런타임 등록 코드는 생성하지 않는다.

## Excel → CSV 계약

- **Excel만 편집 원본**이다. Phase 0.2에서 검증한 레이아웃은 1행 `#Table`, 2행 `#Target`, 3행 구분, 4~12행 `#Key`, `#Scope`, `#Type`, `#Required`, `#Min`, `#Max`, `#Default`, `#Allowed`, `#Reference`, 13행 `#Field`, 14행부터 데이터다. Phase 0.3에서는 기존 양식에 13행 `#Description`만 추가한다. 1~12행은 그대로 두고 `#Field`와 첫 데이터는 각각 14행과 15행으로 이동한다. 저장소의 템플릿·`Player.xlsx`·생성기·회귀 기대값을 같은 변경에서 맞춘다. 첫 테이블에는 실제 사용하는 고정폭 정수 필드만 두고, 지원하지 않는 선언은 무시하지 않고 거절한다.
- `GameData/Excel/`의 각 데이터 시트를 `GameData/Csv/`의 UTF-8 CSV 하나로 변환한다. 시트 이름과 `#Table` 값은 같아야 하고, 대소문자만 다른 이름도 같은 출력 이름으로 보아 거절한다. 메타데이터 행·열 순서와 빈칸을 보존하고, 쉼표·따옴표·개행은 [RFC 4180의 필드 인용 규칙](https://www.rfc-editor.org/rfc/rfc4180.html#section-2)을 사용한다. 수식·오류 셀은 캐시 값으로 대체하지 않는다. CSV는 저장소에서 검수하거나 바이너리를 재생성할 중간 산출물이지, 수동 편집용 두 번째 원본이 아니다. **둘째 단계는 CSV만 읽어 C++ 헤더와 바이너리를 만든다.** Excel을 거치지 않고 같은 CSV로 둘째 단계만 다시 실행해 같은 결과를 낼 수 있어야 한다.
- 일반 데이터 테이블마다 **숫자 기본키 하나**가 필수다. 템플릿과 같은 `uint32`, 범위 `1..UINT32_MAX`로 제한한다. `#Key=Primary`·`#Required=true`·`#Scope=Shared`를 요구한다. Excel에서는 숫자 셀의 정수값을 검증해 CSV에 10진 정수로 쓴다. CSV에서는 이를 정수로 직접 읽고 부동소수점을 거치지 않는다. 문자열 키, 빈 값, 기본값으로 채운 키, 0·음수·소수·범위 초과·중복을 거절한다. 문자열 라벨이나 행 번호·해시로 키를 만들지 않는다. `Enum.xlsx`의 시트는 일반 테이블이 아니라 타입 정의이므로 이 PK 규칙의 대상이 아니다.

### Phase 0.3 메타데이터 검증 계약

| 메타데이터 | 의미와 검증 |
| --- | --- |
| `#Table`, `#Field` | 시트명과 테이블명을 일치시키고 중복 테이블과 누락·중복 컬럼명을 거절한다. |
| `#Target`, `#Scope` | 테이블의 생성 대상과 컬럼의 포함 범위를 각각 선언한다. 인식하지 못하는 값은 거절한다. |
| `#Type`, `#Key` | `int32`·`uint32` 데이터는 Excel 숫자 셀의 정수여야 한다. 테이블의 단일 숫자 PK는 중복될 수 없다. |
| `#Required`, `#Default` | `true`면 Excel 데이터 셀에 값이 반드시 있어야 한다. `false`면 비워도 되고, `#Default`가 선언됐을 때만 그 값을 사용한다. 기본값도 타입·범위·허용 목록·참조 조건을 똑같이 만족해야 한다. 필수 컬럼과 PK의 누락을 기본값으로 숨기지 않는다. |
| `#Min`, `#Max` | 선언된 하한·상한을 양 끝 포함으로 적용한다. 한쪽만 선언할 수 있다. 선언값의 타입이 틀리거나 하한이 상한보다 크면 실패한다. |
| `#Allowed` | 허용값 목록이다. 예를 들어 `10\|20\|30`이면 셀 값은 이 중 하나여야 한다. 빈 목록은 제한 없음이다. 값은 `#Type`으로 비교하고, 잘못된 목록 항목이나 중복은 거절한다. |
| `#Reference` | `Workbook.Sheet.Field`로 대상 시트의 PK를 지정한다. `Workbook`은 확장자 없는 Excel 파일명이며 세 이름 모두 대소문자를 정확히 맞춘다. 대상 존재·PK 여부·타입을 확인하고, 원본 입력값과 선언된 `#Default`는 대상 PK 집합에 있어야 한다. 둘 다 없는 선택값은 조회하지 않는다. |
| `#Description` | 비워도 되는 컬럼 설명이다. 검증 조건이 아니라 기존 메타데이터와 같이 CSV에 보존한다. 런타임 바이너리에는 넣지 않는다. |

Excel의 모든 입력을 읽어 선언과 셀 값을 검증하고 PK 집합을 만든 다음 교차 참조를 검사한다. 하나라도 실패하면 파일·시트·셀과 원인을 보고하고, 이번에는 CSV를 새로 만들거나 덮어쓰지 않는다. CSV에는 검증에 사용한 메타데이터와 원본 빈칸을 남긴다. 완전히 빈 행은 레코드로 검증하지 않으며, 내부의 빈 행은 CSV에 그대로 둔다. CSV만 읽는 다음 단계에서는 기록 형식과 실제 인코딩 가능 여부를 확인하고, 선택 컬럼의 명시된 기본값은 같은 규칙으로 해석한다. 표현할 수 없는 빈 값을 암묵적으로 `0`으로 채우지 않는다. Excel 셀 유형이나 통합 문서의 존재를 확인하려고 다시 Excel을 열지 않는다.

### 타입 확장 계약

Excel → CSV 단계는 `int32`·`uint32`·`float32`·`string`·`enum:TypeName`과 각 타입의 1차원 배열을 지원한다. `PlayerMovement`의 기존 필드와 PK는 바꾸지 않는다.

- **소수·문자열:** `float32` 데이터는 Excel 숫자 셀을 단정밀도로 변환하고, 십진 메타데이터 텍스트는 단정밀도로 직접 읽는다. 유한한 결과에만 `#Min`·`#Max`·`#Allowed`를 적용하며, 0이 아닌 입력이 0으로 변환되면 거절한다. 숫자 셀에서 나온 데이터와 메타데이터는 로캘과 무관하게 같은 값으로 다시 읽히게 기록한다. `string`은 Excel 텍스트를 받아 CRLF·CR만 LF로 바꾸고 공백, 대소문자, 그 밖의 문자는 보존한다. `#Default`와 `#Allowed`도 텍스트로 받으며 `#Min`·`#Max`는 숫자 필드에만 적용한다.
- **Enum 정의:** `GameData/Excel/Enum.xlsx`에서 시트 이름이 `enum class`의 이름이다. A1/B1의 `Name`/`Value` 아래에 항목명(텍스트)과 명시 `uint32` 번호(숫자 셀)를 적는다. 예를 들어 `DamageType` 시트에 `Fire = 1`, `Ice = 2`를 둔다. 같은 타입 안에서 항목명이나 번호가 중복되면 거절하며 행 순서로 번호를 매기지 않는다. 패킷이나 런타임 내부 상태의 Enum은 이 파일의 대상이 아니다.
- **Enum 사용과 생성:** 일반 테이블에서는 `#Type=enum:DamageType`, 데이터·`#Default`·`#Allowed`에는 `Fire`처럼 대소문자가 일치하는 항목명을 쓴다. Excel → CSV 단계는 `Enum.xlsx`의 정의를 먼저 읽어 검증하고, 일반 CSV에는 항목명을 보존한다. 타입 정의는 일반 테이블에 배정하지 않는 `Enum.csv`(`Type,Name,Value`) 한 파일에 모은다. CSV → C++ 단계는 이 정의 CSV에서만 공용 `GameDataEnums.h`를 생성하고, 양쪽 행 `struct`는 동일한 타입을 참조한다. 바이너리는 항목의 고정 번호를 저장한다. `Enum.xlsx`용 게임 테이블 바이너리는 만들지 않는다.
- **배열:** 지원 스칼라 타입에 `[]`를 붙인 1차원 배열만 허용한다. 텍스트 셀에 `[1 | 2 | 3]`, `[Fire | Ice]`처럼 쓴다. `string[]`의 원소는 `["검 | 방패" | "활"]`처럼 큰따옴표로 감싸고 내부 큰따옴표는 두 번 쓴다. `[]`는 입력한 빈 배열이고 미입력 셀과 다르다. 원소의 순서와 중복을 보존하고 혼합 타입·중첩 배열·빈 원소를 거절한다. `#Default`는 배열 전체를, 숫자 범위와 괄호 없는 `#Allowed` 목록은 각 원소를 검사한다. 배열은 PK·`#Reference`에 쓰지 않는다. CSV에는 배열을 정규화해 기록하고 선택 컬럼의 미입력 셀은 비워 둔다.

## 바이너리와 배포 경계

- `#Target`은 테이블을 어느 쪽에 제공할지, `#Scope`는 각 컬럼을 어느 쪽에 포함할지 정한다. 클라이언트는 `Shared + Client`, 서버는 `Shared + Server` 컬럼만 사용한다. 대상마다 한 번 만든 필드 목록을 해당 C++ 행 선언과 바이너리가 함께 사용한다. 클라이언트 배포에는 클라이언트 바이너리만 넣고 Excel·CSV·서버 산출물을 제외한다. 서버 데이터는 숨겨 보내거나 암호화로 대체하지 않는다.
- C++ `struct`는 읽은 행의 **메모리 표현**이다. 파일은 그 객체를 통째로 복사하지 않고, 필드를 정해진 순서로 인코딩한다. 정수·소수·Enum은 고정폭 little-endian으로, 문자열은 UTF-8 바이트 길이와 내용으로, 배열은 원소 개수와 원소값으로 저장한다. `sizeof(struct)`에 의존하거나 파일 주소를 구조체 포인터로 캐스팅하지 않는다. 압축은 이번 범위가 아니다.
- 파일 헤더에 식별값, 형식 버전, 대상, 테이블 및 대상별 스키마 식별자, 행 수를 둔다. 스키마 식별자는 투영된 필드의 이름·순서·타입에서 결정하고, 비교값은 해당 행 `struct`의 형식 메타데이터로만 둔다. 값만 바뀌면 스키마는 같고, 같은 크기라도 필드명·순서·타입이 바뀌면 기존 판독기는 거절한다. 판독기는 길이·행 수·중복 키·잘림·남는 바이트를 확인한 뒤에만 완성된 결과를 사용한다. 양쪽 시험에서 엔진·패킷·플랫폼 타입을 필요로 하지 않는다.
- CSV와 헤더·바이너리는 임시 후보에 준비한다. 필수 파일의 목록과 해당 CSV에서 만든 값이 맞는지 검사한 뒤 완전한 출력 묶음만 교체한다. 파일 하나가 빠지거나 검증에 실패하면 이전 파일로 보충하지 않고 기존 발행본을 보존한다. 같은 입력으로 다시 생성하면 바이트가 같아야 한다. 앱에서는 필수 데이터가 없거나 형식·키가 틀리면 데이터 사용을 시작하지 않고 원인을 보고한다.

## 런타임 테이블의 공통 계약

공통 인터페이스는 **정적 게임 데이터의 테이블 단위**로만 두고, 첫 `PlayerMovement` 런타임 적재를 구현할 때부터 사용한다. 생성 행 `struct`와 실행 중 바뀌는 게임 상태에는 상속을 적용하지 않는다. Phase 0의 생성기 산출물과 독립 판독 범위는 그대로 유지한다.

| 구성 | 책임 |
| --- | --- |
| 생성 행 `struct` | 대상별 필드와 형식 메타데이터만 둔다. `Load()`, `Validate()`, `Initialize()`를 생성하지 않는다. |
| 수기 바이너리 판독기 | 파일 형식·대상·스키마·길이를 검증하고 행을 읽는다. 게임 규칙은 검사하지 않는다. |
| 수기 `IGameDataTable` | 적재 시 공통으로 쓰는 `Load()`와 `Validate() const`만 제공한다. 조회, 교차 참조 검증, 선택적인 후처리는 공통 인터페이스에 넣지 않는다. |
| 수기 `CPlayerMovementTable` 등 | `IGameDataTable`을 구현한다. `Load()`에서 행을 읽어 소유하고 PK 조회를 준비한다. `Validate() const`는 자기 테이블의 게임 규칙만 검사한다. `Find(id)`는 자기 행 타입의 `const` 포인터를 반환하며 없는 키는 `nullptr`이다. |
| `CGameData` | 두 번째 실제 테이블부터 구체 테이블을 소유하고 시작 순서와 공개 시점을 관리한다. 교차 참조와 실행 설정의 필수 ID를 같은 후보 묶음의 구체 테이블에서 확인한다. |

앱 시작 순서는 **모든 필수 테이블 읽기와 PK 조회 준비 → 테이블별 `Validate()` → 후보 묶음의 교차 참조·필수 ID 검증 → 필요한 파생 데이터 준비 → 완성된 묶음만 읽기 전용으로 공개**다. 예를 들어 `Map`에 이동 프로필 참조가 추가되면, 후보 묶음을 소유한 `CGameData`가 그 후보의 `PlayerMovement.Find(id)`로 확인한다. 시작 맵과 이동 프로필을 고르는 설정의 필수 ID도 이 단계에서 검사한다. 이미 공개된 데이터나 전역 상태를 참조하지 않는다.

- `Validate()`는 값을 바꾸거나 기본값으로 복구하지 않는다. `Initialize()`는 검증된 값으로 파생 인덱스·캐시를 준비할 필요가 생긴 테이블에만 둔다. 지금은 전 테이블에 빈 가상 함수를 강제하지 않는다.
- 첫 `PlayerMovement` 소비는 `IGameDataTable` 경로로 `Load()` → `Validate()`를 호출하고, 필요한 ID는 구체 테이블의 `Find()`로 확인한 뒤 사용한다. 첫 적재 검증에서는 정상 데이터가 이 경로를 통과하고, 형식은 맞지만 이동 규칙에 어긋나는 데이터는 `Validate()`에서 거절되어 사용되지 않는지 확인한다. `CGameData`의 다중 테이블 관리는 `Map`을 추가할 때 붙인다. 자동 등록, 전역 싱글턴, 실행 중 재로딩은 이번 범위가 아니다.
- 정상 테이블을 조회하다 없는 키를 찾으면 `nullptr`이며 파일 로드 실패는 아니다. 반면 다른 테이블의 필수 참조나 설정에서 요구하는 ID가 없으면 후보 검증 실패다. 로드·검증·후처리가 실패하면 후보 전체를 폐기한다. 게임은 공개된 행만 `const`로 조회하며, 행의 수명은 소유 테이블을 넘지 않는다.
- 교차 참조를 연결하는 단계의 회귀는 정상 후보와 누락 참조 후보를 비교한다. `Map` 행이 존재하지 않는 이동 프로필을 가리키면 출발 테이블·PK·참조 필드·누락 ID를 남기고, 일부 테이블도 공개되지 않는지 확인한다. 설정의 필수 ID 누락도 같은 경계에서 거절한다.

## 실제 소비로 이어지는 작업

- `GameServer`에서는 고정 틱 이동에 쓰기 전에 `PlayerMovement`를 읽고 속도·반경을 전달한다. 첫 맵의 경계·스폰·장애물 수치는 각 기능을 붙이는 Phase에 같은 템플릿의 `Map` 데이터로 추가한다. 첫 맵과 첫 이동 프로필의 선택 ID는 실행 설정으로 받되 실제 수치를 설정에 복제하지 않는다. 기존 `FixedMaps`의 시험용 상수는 이 작업으로 손대지 않는다.
- `GameClient`에서는 서버가 스폰 시 알려준 이동 프로필 ID를 기준으로 `PlayerMovement`의 클라이언트 데이터만 읽는다. UE 경로·패키징은 실제 클라이언트 소비 시 확인한다. 서버 이동 계산이나 서버 전용 값은 클라이언트 데이터로 넘기지 않는다.
- 핵심 최종 검증: Excel의 이동 속도만 바꾸고 다시 생성하여, **게임 실행 파일을 다시 빌드하지 않고**, 서버 재시작 후 같은 입력의 한 틱 이동량이 바뀌는 것을 확인한다. 이 앱 검증은 Phase 0 판독 시험과 구분한다.
