# Win32 + Direct2D 2D 게임 개발 라이브러리 계획

## 목표와 작업 범위

서버 개발이 진행되는 동안, 특정 MMO에 묶이지 않고 여러 2D 게임에서 재사용할 C++ 라이브러리 v1.0을 준비한다. 정식 `GameClient` 대신 라이브러리의 실제 사용 예제인 독립 실행형 `Sandbox`를 먼저 만든다. 각 단계는 Sandbox나 독립 테스트에서 확인하고, 사용자 검토 후 다음 단계로 진행한다.

- 작업은 `DevClient`의 별도 작업 폴더에서만 한다. `Server/`, `Tests/Chatting/Server/`, `01~12` 보존 프로젝트, 기존 네트워크·패킷 코드와 기존 솔루션은 변경하지 않는다.
- 공용 코드는 서버가 나중에 같은 구현을 링크할 수 있게 준비하되, 이번에는 서버에 연결하지 않는다. 서버 접속·멀티플레이·스냅샷 동기화, 맵 에디터, 스크립트, 사운드, 자체 셰이더, 복잡한 강체 시뮬레이션은 v1.0 범위에서 제외한다.
- Sandbox 캐릭터의 이동은 **마우스 클릭 이동**으로 유지한다. 키보드 입력은 카메라나 디버그 조작 등으로 검증하며, 캐릭터 이동 방식을 키보드로 바꾸지 않는다.

## 프로젝트 구성 초안

기존 트리를 유지하고, 클라 전용 솔루션(가칭 `GameFramework.sln`)에서 아래 라이브러리와 예제·테스트만 빌드한다. 이름과 배치는 제안이며 실제로 소비하는 단계에 필요한 프로젝트만 추가한다.

| 위치 | 역할 |
| --- | --- |
| `Common/`의 `CommonLib`, `ECSLib`, `Physics2DLib` | 공용 수학·기하 자료형, 엔티티·컴포넌트 저장/조회, 이동·충돌 계산. Win32·DirectX·네트워크 헤더에 의존하지 않는다. 충돌 계산은 ECS에도 의존하지 않는다. |
| `Client/`의 `ClientFrameworkLib` | 클라이언트 전용 실행 기반. 고정 틱 스케줄링을 맡고, Win32 메시지 처리·렌더링·콘텐츠 로직은 맡지 않는다. 서버에서는 링크하지 않는다. |
| `Client/`의 `PlatformWin32Lib`, `ClientRenderLib` | Win32 창·메시지·입력·시간과 Direct2D 렌더링. 플랫폼 입력은 게임 로직에 전달하고 렌더러는 월드 상태를 읽어 그린다. |
| `Client/Sandbox`, 클라 전용 `Tests/` | 라이브러리를 사용하는 독립 실행 예제와 ECS·충돌 등의 자동 테스트. |

## 개발 순서와 확인 기준

**한 번에 Phase 하나만 구현한다.** 시작할 때 이번에 바뀌는 파일과 이유를 설명하고, 끝나면 진입점부터의 호출 흐름, 직접 확인할 방법, 아직 추가하지 않은 기능을 정리한다. 사용자 검토 전에는 다음 Phase로 넘어가지 않는다.

### Win32 기반과 Direct2D 첫 화면

#### Phase 1.1 — 빈 Win32 창 열고 닫기

- **만드는 것:** 클라 전용 솔루션과 `Sandbox` 실행 프로젝트 하나. 진입점에서 창 클래스 등록 → 창 생성·표시 → 메시지 전달 → 종료 흐름만 연결한다.
- **직접 확인:** Sandbox를 빌드해 빈 창을 띄운다. X를 누르면 창이 닫히고 프로세스가 종료된다. 디버거에서 진입점 → `WndProc` → 종료 메시지 흐름을 따라간다.
- **여기서 멈춤:** 별도 라이브러리 프로젝트, Direct2D, 게임 루프, 입력, ECS, 충돌은 추가하지 않는다.
- **완료:** x64 Debug·Release에서 창 표시와 닫기 메시지에 따른 정상 종료를 자동 검증했다. 배경색 등록 수정 후에는 x64 Debug에서 등록값과 창 표시·종료를 재확인했다. 사용자가 창 표시와 코드 흐름을 확인하고 직접 주석을 추가했다.

#### Phase 1.2 — 프레임 루프

- **상태:** 완료. x64 Debug·Release에서 입력 없이 FPS가 표시되고 닫기 메시지로 정상 종료되는 것을 자동 검증했다. 사용자가 검토를 마쳤다.
- **만드는 것:** 메시지 처리와 업데이트가 번갈아 도는 루프. 창 제목에 최근 측정 구간의 초당 루프 횟수를 `FPS`로 표시한다. 아직 렌더링 FPS는 아니다.
- **직접 확인:** 키보드·마우스 입력 없이 창 제목에 FPS가 표시되고 X로 종료된다. 고정 업데이트는 Phase 1.3에서 다룬다.

#### Phase 1.3 — 고정 업데이트

- **상태:** 완료. x64 Debug·Release 자동 검증과 사용자 코드 검토를 마쳤다. 사용자가 검토 후 주석을 수정했다.
- **구현:** `GameFramework.sln`의 `ClientFrameworkLib`가 60Hz 고정 틱을 스케줄링하고 `Sandbox`가 틱마다 `FixedUpdate`를 실행한다. 루프당 최대 4회까지 처리하되, 아직 처리하지 못한 온전한 틱과 한 틱 미만의 시간을 모두 다음 루프로 넘긴다.
- **검증:** 창 없는 테스트로 시간 누적, 1초당 60틱, 실행 상한, 지연 후 남은 틱의 후속 처리와 한 틱 미만의 시간 보존을 확인했다. Sandbox 자동 테스트로 입력 없는 상태의 `FPS`·`UPS` 표시와 정상 종료를 확인했다. `FPS`는 아직 렌더링이 아닌 루프 횟수다.
- **직접 확인:** `Sandbox`를 실행하고 창 제목의 `FPS`와 `UPS`를 비교한다. 디버거로 따라갈 때는 `Advance` 반환값이 재개 직후에도 최대 4인지 확인한다.

#### Phase 1.4 — Direct2D 초기화

- **상태:** 완료. x64 Debug·Release 자동 검증과 사용자 코드 검토를 마쳤다.
- **구현:** `GameFramework.sln`에 `ClientRenderLib`를 추가했다. `CDirect2DRenderer::Initialize()`가 `HWND`에 연결된 DXGI 스왑 체인의 백 버퍼를 Direct2D 그리기 대상으로 지정한다. `Sandbox`는 고정 업데이트를 실행한 뒤 `DrawBackground()`를 호출한다.
- **검증:** Sandbox 창 중앙의 화면 픽셀에서 지정한 배경색을 확인했다. FPS·UPS 표시와 정상 종료도 확인했다.
- **직접 확인:** `Sandbox`를 실행하여 짙은 파란색 배경이 표시되는지 확인한다. `Initialize()`와 `DrawBackground()`를 보면서 초기화, 그리기, `Present()`를 구분한다. 사각형 그리기, 리사이즈 대응, 디바이스 손실 복구는 이 단계에서 추가하지 않는다.

#### Phase 1.5 — 사각형 그리기

- **상태:** 완료. x64 Debug·Release 자동 검증을 마쳤고, 사용자가 완료를 확인했다.
- **구현:** `Sandbox`가 프레임마다 `BeginFrame()` → `FillRectangle()` → `EndFrame()`을 호출한다. 같은 백 버퍼에 파란 배경과 고정 좌표의 흰색 사각형을 그린 뒤 한 번만 `Present()`한다.
- **검증:** 사각형 안쪽과 배경의 화면 픽셀 색을 각각 확인했다. FPS·UPS 표시 및 정상 종료 테스트도 통과했다.
- **직접 확인:** `Sandbox`를 실행해 창 왼쪽 위에 흰 사각형이 보이는지 확인한다. 리사이즈 대응은 Phase 1.6에서 다룬다.

#### Phase 1.6 — 리사이즈·최소화

- **상태:** 완료. x64 Debug·Release 자동 검증 및 사용자 코드 검토를 마쳤다.
- **구현:** `WM_SIZE`에서 창 상태를 기록하고, 프레임 직전에 크기가 바뀐 백 버퍼만 교체해 Direct2D 타깃을 다시 연결한다. 최소화 중에는 렌더링만 건너뛰고 고정 업데이트는 유지한다.
- **검증:** 창을 줄이고 늘린 후 사각형과 배경의 픽셀을 확인했다. 최소화 중 FPS 0·UPS 양수, 복원 후 렌더링 재개와 정상 종료도 확인했다.
- **직접 확인:** 창 크기를 바꿔도 흰 사각형 자체는 늘어나거나 줄어들지 않고, 최소화 후 복원하면 다시 보인다.

#### Phase 1.7 — 클릭 위치 확인

- **상태:** 완료. x64 Debug·Release 자동 검증을 마쳤고, 사용자가 완료를 확인했다.
- **만드는 것:** `ClientFrameworkLib`의 `CInputManager`에서 게임 액션을 키보드 키 또는 마우스 버튼에 매핑한다. `GetActionState()`로 현재 상태(`m_isDown`), 이번 고정 틱의 변화(`m_wasPressed`, `m_wasReleased`), 눌렀을 때의 좌표(`m_pressPosition`, 없으면 비어 있음)를 한 번에 조회한다. 키 설정 UI와 저장은 보류한다.
- **전달 규칙:** 다음 고정 틱까지 변화를 보관한다. 한 틱 사이의 짧은 클릭은 눌림과 떼어짐을 모두 보존하고, 같은 버튼을 여러 번 클릭하면 마지막 눌림 좌표를 사용한다. 누르고 있는 중 들어오는 반복 입력은 새 눌림이 아니다.
- **역할 분리:** `ClientFrameworkLib/Input`의 Win32 입력 어댑터가 `WndProc`에서 받은 입력 메시지를 해석하고, `CInputManager`는 버튼 상태와 액션 매핑을 관리한다. 액션 정의와 기본 바인딩은 `Sandbox`에 둔다.
- **직접 확인:** Sandbox의 `MoveTo` 액션은 좌클릭에 매핑된다. 현재는 Phase 1.8과 연결돼 사각형이 이동하는 동안 목적지 표식이 보인다.

| Phase | 이번에 추가하는 것 | 직접 확인할 것 |
| --- | --- | --- |
| 1.8 — 클릭으로 사각형 이동 | `MoveTo`의 눌림 위치를 목적지로 삼아 사각형의 중심을 고정 틱마다 이동시킨다. 도착 지점을 넘지 않고, 재클릭하면 목적지를 바꾼다. | 사각형 중심이 클릭 지점에 도착하고, 이동 중 다시 클릭하면 새 목적지로 향한다. 벽과 ECS는 아직 없다. |

**Phase 1.8 상태:** 완료. x64 Debug·Release에서 이동 중 재클릭, 새 목적지에서 정지, 창 수명주기 회귀 테스트를 통과했고, 사용자가 완료를 확인했다.

**첫 마일스톤:** Phase 1.8까지 완료. 클릭한 곳으로 사각형이 이동하며 창 크기 변경과 최소화·복원에 대응한다.

**후속 설계(미구현):** `ActionId → ActionFunc` 매핑은 버튼 매핑과 분리한다. 현재 `Sandbox`는 `FixedUpdate()`에서 `GetActionState()`를 직접 조회한다.

### 입력·카메라와 스프라이트

#### Phase 2.1 — 카메라 이동

- **상태:** 완료. 최종 `CCameraManager` 구조에서 x64 Debug·Release 프레임워크 테스트와 Release Sandbox 테스트를 통과했다. 최종 변경 후 Debug Sandbox는 재실행하지 않았다. 사용자가 완료를 확인했다.
- **구현:** `Camera/CCameraManager`는 카메라 한 대의 월드 중심 좌표를 보관하고 `FollowTarget()`으로 추적한다. `Sandbox`는 고정 틱에서 클릭을 월드 목적지로 변환하고, 사각형을 이동시킨 뒤 대상 위치를 매니저에 넘긴다. `Transform/CoordinateTransform2D`는 카메라 타입에 의존하지 않고 월드↔창 내부 좌표를 변환한다.
- **직접 확인:** 사각형은 창 중앙에 있고, 이동하면 월드에 고정된 작은 흰 기준점이 반대 방향으로 흐른다. 카메라가 이동한 후 다시 클릭해도 올바른 월드 지점으로 이동한다. 줌은 Phase 2.2에서 다룬다.

#### Phase 2.2 — 카메라 줌

- **상태:** 완료. 휠 변경 후 x64 Debug·Release 프레임워크 테스트와 Sandbox 테스트를 모두 통과했으며, 사용자가 검토를 마쳤다.
- **범위:** `CCameraManager`가 줌 배율을 보관하고, `Transform`은 배율을 값으로 받아 월드→창 내부 변환에서 곱하고 역변환에서 나눈다. 확대·축소 기준은 창 중앙이며, 사각형의 월드 위치와 이동 속도는 그대로 유지한다.
- **조작:** Sandbox에서 마우스 휠을 위로 굴리면 확대, 아래로 굴리면 축소한다. 배율은 0.5배, 1배(기본), 2배다. 한 칸 미만의 휠 입력은 누적하고, 클릭과 줌 변경이 같은 틱에 들어오면 클릭에는 변경 전 배율을 적용한다.
- **확인 기준:** 줌 전후 화면에서 보이는 위치는 달라도, 같은 월드 기준점을 클릭하면 같은 월드 목적지가 된다.

#### Phase 2.3 — PNG 한 장

- **상태:** 완료. x64 Debug·Release 빌드, 프레임워크 테스트, Sandbox 회귀 테스트를 통과했으며 사용자가 완료를 확인했다.
- **표시:** 빌드가 `Idle.png`를 `Sandbox.exe` 옆에 `BoyIdle.png`로 복사한다. Sandbox는 기존 흰 사각형 위에 좌상단 `16×16` 프레임을 그린다. 좌클릭 이동과 휠 줌은 그대로 동작한다.
- **소유권:** `CDirect2DRenderer::LoadSpritePng()`이 시작 시 한 번 WIC `32bppPBGRA`로 변환하고 동일한 Premultiplied Alpha 모드로 Direct2D 비트맵을 만든다. 비트맵은 렌더러 내부에서 소유하며 리사이즈 후에도 재사용한다. 로딩 실패 시 렌더러는 `HRESULT`를 반환하고 Sandbox는 종료 코드 `2`로 종료한다.

- **검증:** 이동·줌·리사이즈 후에도 첫 프레임이 표시되고, 투명 영역을 통해 사각형이 보인다.

#### Phase 2.4 — 스프라이트 시트

- **상태:** 미착수.
- **범위:** 로드한 이미지에서 프레임 영역을 순서대로 선택해 애니메이션을 재생한다. 재생 중에 같은 텍스처를 다시 로드하지 않는다.

### ECS와 공용 이동·충돌

| Phase | 이번에 추가하는 것 | 직접 확인할 것 |
| --- | --- | --- |
| 3.1 — 엔티티 수명 | 엔티티 ID 생성·삭제 | 여러 엔티티를 생성하고 삭제한 ID가 유효하지 않은지 독립 테스트한다. |
| 3.2 — 컴포넌트 저장·순회 | 추가·조회·순회와 엔티티 삭제 시 정리 | 위치 컴포넌트가 있는 엔티티만 조회·순회되고 삭제된 엔티티는 빠진다. |
| 3.3 — ECS 이동 시스템 | Sandbox에 있던 위치·목적지 상태와 클릭 이동을 ECS로 옮긴다. | 기존 클릭 이동·재클릭 동작이 유지된다. 렌더러는 이동 상태를 수정하지 않는다. |
| 3.4 — 사각형 겹침 판정 | ECS나 창에 의존하지 않는 공용 AABB 판정 | 떨어짐·겹침·경계 접촉 케이스를 독립 테스트한다. |
| 3.5 — 이동 중 첫 접촉 계산 | 시작 사각형과 이동량으로 벽에 처음 닿는 위치를 계산 | 정면·모서리, 한 스텝에 벽을 넘을 속도, 접촉 상태에서 벽 반대 방향으로 출발하는 경우를 테스트한다. |
| 3.6 — Sandbox 충돌 연결 | ECS 이동 시스템에서 공용 충돌 함수를 호출 | 벽 뒤를 클릭하면 벽 앞에서 멈추고 빈 곳은 도착한다. 우회나 벽 미끄러짐은 하지 않는다. |
| 3.7 — 렌더링 보간 | 이전·현재 고정 틱 위치를 이용해 표시 위치를 보간 | 표시를 부드럽게 바꿔도 고정 틱의 좌표와 충돌 결과는 같다. |

원형 충돌·필터링·공간 분할·동적 캐릭터 충돌은 기본 동작 검증 후 필요할 때 별도 범위로 정한다.

### 디버그·UI와 v1.0 안정화

| Phase | 이번에 추가하는 것 | 직접 확인할 것 |
| --- | --- | --- |
| 4.1 — 디버그 표시 | FPS·업데이트 시간과 좌표·목적지·충돌 영역을 표시 | 충돌로 멈춘 이유를 화면에서 확인한다. |
| 4.2 — 최소 UI | 텍스트와 버튼 한 개로 UI 입력 확인 | 버튼 클릭은 UI에서 소비하고 캐릭터 목적지를 바꾸지 않는다. |
| 4.3 — 전체화면 전환 | 창 모드와 전체화면 전환 | 반복 전환해도 그리기와 클릭 좌표가 일치한다. |
| 4.4 — 그래픽 자원 복구 | 렌더 타깃·GPU 자원 재생성 및 종료 정리 | 자원 재생성 경로를 검증하고 리사이즈·최소화·복원·종료를 반복한다. |
| 4.5 — v1.0 검증 | 독립 Sandbox 실행과 Release 빌드·자동 테스트 | 서버 없이 스프라이트 클릭 이동·충돌을 확인하고 클라 전용 자동 테스트를 통과한다. |

서버 통합은 별도 단계다. 같은 공용 이동·충돌 함수를 쓰더라도 상태와 입력 적용 틱까지 자동으로 일치하는 것은 아니며, 최종 위치는 서버가 확정한다.

`GameCoreLib`는 추후 양쪽에서 공통으로 실행할 게임 규칙이나 시뮬레이션이 생길 때 `Common/`에 둘 후보 이름이다. 이번에는 추가하지 않으며, 클라 프레임 루프나 서버 틱 정책을 공유하지 않는다.
