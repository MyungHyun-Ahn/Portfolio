# Win32 + Direct2D 2D 게임 개발 라이브러리 계획

## 목표와 작업 범위

서버 개발이 진행되는 동안, 특정 MMO에 묶이지 않고 여러 2D 게임에서 재사용할 C++ 라이브러리 v1.0을 준비한다. 정식 `GameClient` 대신 라이브러리의 실제 사용 예제인 독립 실행형 `Sandbox`를 먼저 만든다. 각 단계는 Sandbox나 독립 테스트에서 확인하고, 사용자 검토 후 다음 단계로 진행한다.

- 작업은 `DevClient`의 별도 작업 폴더에서만 한다. `Server/`, `Tests/Chatting/Server/`, `01~12` 보존 프로젝트, 기존 네트워크·패킷 코드와 기존 솔루션은 변경하지 않는다.
- 공용 코드는 서버가 나중에 같은 구현을 링크할 수 있게 준비하되, 이번에는 서버에 연결하지 않는다. 서버 접속·멀티플레이·스냅샷 동기화, 맵 에디터, 스크립트, 사운드, 자체 셰이더, 복잡한 강체 시뮬레이션은 v1.0 범위에서 제외한다.
- Sandbox 캐릭터의 이동은 **마우스 클릭 이동**으로 유지한다. 키보드 입력은 카메라나 디버그 조작 등으로 검증하며, 캐릭터 이동 방식을 키보드로 바꾸지 않는다.

## 클라이언트 구조 개편 방향

기존 Sandbox를 버리고 다시 만들지 않는다. **Win32 실행 흐름과 `Game → Scene → Actor → Component` 구성을 기준으로 정리하고, 그리기는 현재 Direct2D 백엔드를 재사용한다.** 아래 구조와 작업 순서는 미구현 계획이다. 뒤의 Phase 1~2 기록은 기존 구현과 검증 이력이다.

### 참고 구조에서 확인한 동작과 적용 범위

| 기능 | 확인한 동작 | DevClient 적용 방향 |
| --- | --- | --- |
| 창·게임 루프 | `PeekMessage`로 메시지가 없을 때 `Game::Update()`와 `Render()`를 호출한다. `Update()` 안에서는 시간 → 입력 → 장면 순으로 호출한다. | 호출 구조는 가져오되 현재 메시지 수집과 60Hz 고정 틱을 유지한다. 가변 `deltaTime`과 키 폴링으로 교체하지 않는다. |
| Scene·Actor·Component | 장면 관리자가 현재 장면에 Update/Render를 위임한다. 장면은 레이어 순서로 Actor를, Actor는 자기 Component를 순회한다. UI는 월드 뒤에 그린다. 장면 초기화는 소속 객체의 `BeginPlay()`를 호출한다. | 소유권과 호출 방향을 채택한다. 장면 하나에서 시작하고, 추가·제거·장면 교체는 순회 밖에서 처리한다. 전역 싱글턴과 수동 `delete`는 이식하지 않는다. |
| 입력·플레이어·카메라 | 키 상태와 클라이언트 마우스 좌표를 조회한다. Player는 키로 다음 타일의 이동 가능 여부를 조회하고 상태·방향으로 클립을 고른다. 카메라 컴포넌트는 소유자를 추적한다. | 입력과 게임 상태의 분리를 따른다. Sandbox는 기존 좌클릭 이동과 휠 줌을 유지하고, 카메라는 이동 확정 후 갱신한다. 맵 경계는 실제 맵과 뷰포트 값으로 계산하며 고정 수치를 복사하지 않는다. |
| 이미지·스프라이트·재생 | 리소스를 키로 찾아 재사용한다. Texture는 원본, Sprite는 자를 영역, Flipbook은 재생 정의, Actor는 현재 프레임 및 경과 시간을 갖는다. | 비트맵의 수명과 재생 상태를 분리한다. Direct2D 비트맵은 렌더러가 소유하고 장면·Actor에는 ID만 전달한다. 두 장 제한을 없애고, 경로/ID 공유는 실제 사용처부터 적용한다. |
| 충돌·타일맵 | Collider 쌍의 겹침 시작/종료 판정과 Player의 타일 통과 판정이 별개다. 타일맵은 데이터와 그리는 Actor가 나뉜다. | 작은 정적 맵과 통과 불가 타일부터 검증한다. 연속 클릭 이동에는 타일 셀 검사만 복사하지 않고 이동 중 첫 접촉을 계산한다. 겹침 이벤트, 원형 충돌, 맵 편집기는 선행 조건이 아니다. |
| UI·도구 | Panel이 자식을 순회하고 Button은 마우스 위치와 입력으로 상태를 바꾼다. 별도 편집 장면에 클릭 편집과 파일 입출력 코드가 있다. | UI는 클라이언트 좌표, 월드는 월드 좌표를 사용한다. 버튼 하나부터 시작한다. 편집기·사운드·전투는 이번 계획의 필수 범위가 아니다. |
| 그리기 | `Game`이 GDI 메모리 DC에 장면을 그리고 `BitBlt`로 내보낸다. 스프라이트·타일·UI와 텍스처 로드에도 GDI 호출 또는 타입이 들어 있다. | `Render()` 호출 계층은 유지하되 `HDC`, `HBITMAP`, `BitBlt`, `TransparentBlt`, BMP 색상 키를 그대로 가져오지 않는다. 기존 WIC PNG 및 Premultiplied Alpha와 `BeginFrame → Draw → EndFrame/Present`를 쓴다. |

### 목표 호출 흐름과 소유권

```text
Win32 호스트 / 프레임 루프
  ├─ Input         : 메시지 수집 → 입력 어댑터 → CInputManager에 보관
  ├─ FixedUpdate   : 틱마다 BeginTick → 현재 Scene에 위임 (루프당 0~4회)
  │    └─ UI 입력 소비 → 이동/충돌 → Actor 재생 상태 → 카메라 → 수명 변경 반영
  └─ Render        : BeginFrame → Scene의 맵/Actor → 디버그/UI → EndFrame/Present
```

- 프레임 루프는 **언제 호출할지**, 게임과 Scene은 **무엇을 어떤 순서로 호출할지** 정한다. 구체적인 Sandbox 플레이어를 먼저 분리한 뒤 입력 수집, `FixedUpdate()`, `Render()`의 호출 경계를 정리한다. 공용 루프가 다른 게임을 구동할 때는 이 경계에만 작은 게임 인터페이스를 둔다. 모든 Manager가 세 함수 전부를 구현하거나 등록 순서로 호출 우선순위를 결정하지 않는다.
- `CFixedStepScheduler`는 밀린 틱을 버리지 않는다. 버튼 변화는 첫 처리 틱까지 남고, 따라잡기 틱에서 중복 소비하지 않는다. 최소화 시 업데이트는 계속하고, 닫기와 리사이즈는 Win32 경계에서 처리한다. `Render()`는 이동·애니메이션의 진행 상태를 바꾸지 않는다.
- 게임이 Scene의 수명을, Scene이 Actor와 UI의 수명을, Actor가 개별 Component를 소유한다. 카메라와 애니메이터에는 필요한 상태만 전달한다. GPU 자원은 `ClientRenderLib`에만 두고, 필요할 때만 공용 리소스 조회 계층을 추가한다. Scene 교체 시 이전 장면의 참조나 클릭이 새 장면으로 넘어가지 않게 한다.
- 월드 위치(월드 단위), 화면 목적지(클라이언트 픽셀), 시트 소스(이미지 픽셀)를 분리한다. 클릭과 장면 그리기는 같은 카메라 변환을 쓰고, UI는 카메라 줌을 적용하지 않는다. `HDC`나 Direct2D 포인터를 Actor·Component에 전달하지 않는다. 프레임 시작 및 제출 책임은 한 곳에 둔다.
- `GameFramework.sln`, `Sandbox`, `ClientFrameworkLib`, `ClientRenderLib`를 유지한다. 창/루프 추출만으로 별도 플랫폼 라이브러리를 만들지 않는다. `ClientFrameworkLib`는 클라이언트 전용이다. 충돌의 순수 계산만 추후 `Common/` 후보로 두고 Win32·렌더러·Scene·ECS·서버 코드에 의존시키지 않는다.

### 새 구현 순서와 확인 기준

아래 Phase는 모두 미구현이다. 한 번에 하나만 진행하고, 자동 검증 결과와 사용자 검토를 다음 Phase 전에 확인한다.

#### Phase 3.1 — 플레이어 상태 분리
- **범위:** `Client/Sandbox/Main.cpp`의 이동·방향·Idle/Walk 전환·`CSpriteAnimator` 상태를 Sandbox 전용 `CSandboxPlayer`로 옮긴다. 플레이어는 월드 목적지를 받아 갱신하며 Win32·입력 매니저·Direct2D를 직접 다루지 않는다. 이 Phase에서는 루프 구조와 렌더러 API를 바꾸지 않는다.
- **완료 기준:** 이동 속도와 재생 규칙을 플레이어 코드에서 찾을 수 있다. x64 Debug·Release에서 클릭·재클릭·도착 정지, 방향별 Idle/Walk, 카메라·줌이 기존과 같다.

#### Phase 3.2 — 게임 루프 경계 분리
- **범위:** `Main.cpp` 쪽은 메시지 수집, 고정 틱 수 결정, 창·렌더러 수명을 맡는다. `CSandboxGame`은 클릭의 월드 좌표 변환 → 플레이어 업데이트 → 카메라 추적·줌 순서를 책임지고, `Render()`에서 그릴 내용을 제출한다. 호스트가 프레임 시작과 `Present()`를 한 번만 처리한다. 별도 공용 인터페이스는 도입하지 않는다.
- **완료 기준:** 바깥 루프당 입력 수집 한 번과 고정 틱 0~4회, 밀린 틱과 입력 보존, 같은 틱의 클릭을 변경 전 줌으로 해석하는 규칙을 유지한다. 리사이즈·최소화·복원·종료 동작이 같다.

#### Phase 3.3 — 비트맵 슬롯을 이미지 ID로 교체
- **범위:** `ClientRenderLib`의 고정 두 장 배열을 가변 저장소로 바꾸고, 로드 성공 시 이미지 ID를 돌려준다. Sandbox의 `Idle`·`Walk`와 렌더러 슬롯 번호의 결합을 끊는다. WIC·알파 정책은 그대로 유지하고 범용 매니저는 만들지 않는다.
- **완료 기준:** 세 번째 PNG를 렌더러 용량 코드 수정 없이 로드하고 그릴 수 있다. 새 로드가 실패해도 기존 ID는 유효하다.

#### Phase 3.4 — 두 번째 캐릭터로 공유와 독립 재생 검증
- **범위:** Sandbox에 두 번째 캐릭터를 추가해 이미지 ID와 시트·클립 정의를 공유하고, 위치·방향·재생 위치는 객체마다 따로 유지한다. 마우스 입력은 기존 플레이어에만 연결한다. 공용 Actor 기반 클래스부터 만들지 않는다.
- **완료 기준:** 같은 이미지를 쓰는 두 캐릭터가 서로 다른 프레임과 방향을 표시하며, 두 번째 캐릭터를 붙이는 데 `Main.cpp`의 프레임 루프나 렌더러를 바꾸지 않는다.

#### Phase 3.5 — 단일 Scene으로 객체 소유권 정리
- **범위:** 두 캐릭터에서 확인한 공통 갱신·그리기 흐름을 단일 Sandbox Scene에 모은다. 게임이 Scene을, Scene이 Actor를 소유한다. Actor 추가·제거는 순회가 끝난 뒤 반영한다. 공용 Actor/Component 추출과 장면 전환은 실제 사용처가 생길 때만 진행한다.
- **완료 기준:** `CSandboxGame`이 Scene에 업데이트와 그리기를 위임한다. Scene에서 객체를 추가·제거해도 순회와 플레이어 카메라 추적이 정상이다.

#### Phase 4.1 — 타일맵 표시
- **범위·완료 기준:** 타일 데이터를 그리는 코드에서 분리한다. 작은 정적 맵을 그려 카메라 이동·줌에도 캐릭터와 맵의 위치 관계가 유지되는지 확인한다. 이 Phase에서는 충돌을 적용하지 않는다.

#### Phase 4.2 — 정적 벽 충돌
- **범위·완료 기준:** 플랫폼 독립 AABB 첫 접촉 계산을 적용한다. 벽 뒤를 클릭하거나 한 틱의 이동량이 벽보다 커도 통과하지 않는다. 모서리·접촉 상태에서 벽에서 멀어지는 경우를 독립 테스트한다. 우회·미끄러짐은 제외한다.

#### Phase 4.3 — UI 입력 분리
- **범위·완료 기준:** 클라이언트 좌표로 버튼 하나를 그리고, 버튼에서 소비한 클릭은 월드 이동으로 전달하지 않는다. 카메라를 이동하거나 확대해도 버튼 위치는 고정이다.

#### Phase 4.4 — 디버그 표시와 안정화
- **범위·완료 기준:** FPS/UPS·좌표·콜라이더를 표시한다. 독립 Sandbox에서 맵·이동·충돌·스프라이트·UI와 반복 실행·종료를 확인하고 x64 Debug·Release 회귀 검증을 마친다. 전체화면·디바이스 복구·렌더 보간은 필요할 때 별도 작업으로 둔다.

이 순서는 기존 **ECS 선행 계획을 대체**한다. ECS 엔티티/컴포넌트 저장소와 이동 시스템은 Scene/Actor 기반으로 실제 요구가 확인되면 재검토하며, 타일맵이나 충돌의 선행 조건으로 두지 않는다. 서버 연결과 좌표 동기화는 별도 작업이다.

## 기존 구현 및 검증 이력

**한 번에 Phase 하나만 구현한다.** 시작할 때 이번에 바뀌는 파일과 이유를 설명하고, 끝나면 진입점부터의 호출 흐름, 직접 확인할 방법, 아직 추가하지 않은 기능을 정리한다. 사용자 검토 전에는 다음 Phase로 넘어가지 않는다.

### Win32 기반과 Direct2D 첫 화면

#### Phase 1.1 — 빈 Win32 창 열고 닫기

- **만드는 것:** 클라 전용 솔루션과 `Sandbox` 실행 프로젝트 하나. 진입점에서 창 클래스 등록 → 창 생성·표시 → 메시지 전달 → 종료 흐름만 연결한다.
- **직접 확인:** Sandbox를 빌드해 빈 창을 띄운다. X를 누르면 창이 닫히고 프로세스가 종료된다. 디버거에서 진입점 → `WndProc` → 종료 메시지 흐름을 따라간다.
- **여기서 멈춤:** 별도 라이브러리 프로젝트, Direct2D, 게임 루프, 입력, ECS, 충돌은 추가하지 않는다.
- **완료:** x64 Debug·Release에서 창 표시와 닫기 메시지에 따른 정상 종료를 자동 검증했다. 배경색 등록 수정 후에는 x64 Debug에서 등록값과 창 표시·종료를 재확인했다. 사용자가 창 표시와 코드 흐름을 확인하고 직접 주석을 추가했다.

#### Phase 1.2 — 프레임 루프

- **상태:** 완료. x64 Debug·Release에서 입력 없이 FPS가 표시되고 닫기 메시지로 정상 종료되는 것을 자동 검증했다. 사용자가 검토를 마쳤다.
- **만드는 것:** 메시지 처리와 업데이트가 번갈아 도는 루프. 창 제목에 최근 측정 구간의 초당 루프 횟수를 `FPS`로 표시한다. 아직 렌더링 FPS는 아니다.
- **직접 확인:** 키보드·마우스 입력 없이 창 제목에 FPS가 표시되고 X로 종료된다. 고정 업데이트는 Phase 1.3에서 다룬다.

#### Phase 1.3 — 고정 업데이트

- **상태:** 완료. x64 Debug·Release 자동 검증과 사용자 코드 검토를 마쳤다. 사용자가 검토 후 주석을 수정했다.
- **구현:** `GameFramework.sln`의 `ClientFrameworkLib`가 60Hz 고정 틱을 스케줄링하고 `Sandbox`가 틱마다 `FixedUpdate`를 실행한다. 루프당 최대 4회까지 처리하되, 아직 처리하지 못한 온전한 틱과 한 틱 미만의 시간을 모두 다음 루프로 넘긴다.
- **검증:** 창 없는 테스트로 시간 누적, 1초당 60틱, 실행 상한, 지연 후 남은 틱의 후속 처리와 한 틱 미만의 시간 보존을 확인했다. Sandbox 자동 테스트로 입력 없는 상태의 `FPS`·`UPS` 표시와 정상 종료를 확인했다. `FPS`는 아직 렌더링이 아닌 루프 횟수다.
- **직접 확인:** `Sandbox`를 실행하고 창 제목의 `FPS`와 `UPS`를 비교한다. 디버거로 따라갈 때는 `Advance` 반환값이 재개 직후에도 최대 4인지 확인한다.

#### Phase 1.4 — Direct2D 초기화

- **상태:** 완료. x64 Debug·Release 자동 검증과 사용자 코드 검토를 마쳤다.
- **구현:** `GameFramework.sln`에 `ClientRenderLib`를 추가했다. `CDirect2DRenderer::Initialize()`가 `HWND`에 연결된 DXGI 스왑 체인의 백 버퍼를 Direct2D 그리기 대상으로 지정한다. `Sandbox`는 고정 업데이트를 실행한 뒤 `DrawBackground()`를 호출한다.
- **검증:** Sandbox 창 중앙의 화면 픽셀에서 지정한 배경색을 확인했다. FPS·UPS 표시와 정상 종료도 확인했다.
- **직접 확인:** `Sandbox`를 실행하여 짙은 파란색 배경이 표시되는지 확인한다. `Initialize()`와 `DrawBackground()`를 보면서 초기화, 그리기, `Present()`를 구분한다. 사각형 그리기, 리사이즈 대응, 디바이스 손실 복구는 이 단계에서 추가하지 않는다.

#### Phase 1.5 — 사각형 그리기

- **상태:** 완료. x64 Debug·Release 자동 검증을 마쳤고, 사용자가 완료를 확인했다.
- **구현:** `Sandbox`가 프레임마다 `BeginFrame()` → `FillRectangle()` → `EndFrame()`을 호출한다. 같은 백 버퍼에 파란 배경과 고정 좌표의 흰색 사각형을 그린 뒤 한 번만 `Present()`한다.
- **검증:** 사각형 안쪽과 배경의 화면 픽셀 색을 각각 확인했다. FPS·UPS 표시 및 정상 종료 테스트도 통과했다.
- **직접 확인:** `Sandbox`를 실행해 창 왼쪽 위에 흰 사각형이 보이는지 확인한다. 리사이즈 대응은 Phase 1.6에서 다룬다.

#### Phase 1.6 — 리사이즈·최소화

- **상태:** 완료. x64 Debug·Release 자동 검증 및 사용자 코드 검토를 마쳤다.
- **구현:** `WM_SIZE`에서 창 상태를 기록하고, 프레임 직전에 크기가 바뀐 백 버퍼만 교체해 Direct2D 타깃을 다시 연결한다. 최소화 중에는 렌더링만 건너뛰고 고정 업데이트는 유지한다.
- **검증:** 창을 줄이고 늘린 후 사각형과 배경의 픽셀을 확인했다. 최소화 중 FPS 0·UPS 양수, 복원 후 렌더링 재개와 정상 종료도 확인했다.
- **직접 확인:** 창 크기를 바꿔도 흰 사각형 자체는 늘어나거나 줄어들지 않고, 최소화 후 복원하면 다시 보인다.

#### Phase 1.7 — 클릭 위치 확인

- **상태:** 완료. x64 Debug·Release 자동 검증을 마쳤고, 사용자가 완료를 확인했다.
- **만드는 것:** `ClientFrameworkLib`의 `CInputManager`에서 게임 액션을 키보드 키 또는 마우스 버튼에 매핑한다. `GetActionState()`로 현재 상태(`m_isDown`), 이번 고정 틱의 변화(`m_wasPressed`, `m_wasReleased`), 눌렀을 때의 좌표(`m_pressPosition`, 없으면 비어 있음)를 한 번에 조회한다. 키 설정 UI와 저장은 보류한다.
- **전달 규칙:** 다음 고정 틱까지 변화를 보관한다. 한 틱 사이의 짧은 클릭은 눌림과 떼어짐을 모두 보존하고, 같은 버튼을 여러 번 클릭하면 마지막 눌림 좌표를 사용한다. 누르고 있는 중 들어오는 반복 입력은 새 눌림이 아니다.
- **역할 분리:** `ClientFrameworkLib/Input`의 Win32 입력 어댑터가 `WndProc`에서 받은 입력 메시지를 해석하고, `CInputManager`는 버튼 상태와 액션 매핑을 관리한다. 액션 정의와 기본 바인딩은 `Sandbox`에 둔다.
- **직접 확인:** Sandbox의 `MoveTo` 액션은 좌클릭에 매핑된다. 현재는 Phase 1.8과 연결돼 사각형이 이동하는 동안 목적지 표식이 보인다.

| Phase | 이번에 추가하는 것 | 직접 확인할 것 |
| --- | --- | --- |
| 1.8 — 클릭으로 사각형 이동 | `MoveTo`의 눌림 위치를 목적지로 삼아 사각형의 중심을 고정 틱마다 이동시킨다. 도착 지점을 넘지 않고, 재클릭하면 목적지를 바꾼다. | 사각형 중심이 클릭 지점에 도착하고, 이동 중 다시 클릭하면 새 목적지로 향한다. 벽과 ECS는 아직 없다. |

**Phase 1.8 상태:** 완료. x64 Debug·Release에서 이동 중 재클릭, 새 목적지에서 정지, 창 수명주기 회귀 테스트를 통과했고, 사용자가 완료를 확인했다.

**첫 마일스톤:** Phase 1.8까지 완료. 클릭한 곳으로 사각형이 이동하며 창 크기 변경과 최소화·복원에 대응한다.

**후속 설계(미구현):** `ActionId → ActionFunc` 매핑은 버튼 매핑과 분리한다. 현재 `Sandbox`는 `FixedUpdate()`에서 `GetActionState()`를 직접 조회한다.

### 입력·카메라와 스프라이트

#### Phase 2.1 — 카메라 이동

- **상태:** 완료. 최종 `CCameraManager` 구조에서 x64 Debug·Release 프레임워크 테스트와 Release Sandbox 테스트를 통과했다. 최종 변경 후 Debug Sandbox는 재실행하지 않았다. 사용자가 완료를 확인했다.
- **구현:** `Camera/CCameraManager`는 카메라 한 대의 월드 중심 좌표를 보관하고 `FollowTarget()`으로 추적한다. `Sandbox`는 고정 틱에서 클릭을 월드 목적지로 변환하고, 사각형을 이동시킨 뒤 대상 위치를 매니저에 넘긴다. `Transform/CoordinateTransform2D`는 카메라 타입에 의존하지 않고 월드↔창 내부 좌표를 변환한다.
- **직접 확인:** 사각형은 창 중앙에 있고, 이동하면 월드에 고정된 작은 흰 기준점이 반대 방향으로 흐른다. 카메라가 이동한 후 다시 클릭해도 올바른 월드 지점으로 이동한다. 줌은 Phase 2.2에서 다룬다.

#### Phase 2.2 — 카메라 줌

- **상태:** 완료. 휠 변경 후 x64 Debug·Release 프레임워크 테스트와 Sandbox 테스트를 모두 통과했으며, 사용자가 검토를 마쳤다.
- **범위:** `CCameraManager`가 줌 배율을 보관하고, `Transform`은 배율을 값으로 받아 월드→창 내부 변환에서 곱하고 역변환에서 나눈다. 확대·축소 기준은 창 중앙이며, 사각형의 월드 위치와 이동 속도는 그대로 유지한다.
- **조작:** Sandbox에서 마우스 휠을 위로 굴리면 확대, 아래로 굴리면 축소한다. 배율은 0.5배, 1배(기본), 2배다. 한 칸 미만의 휠 입력은 누적하고, 클릭과 줌 변경이 같은 틱에 들어오면 클릭에는 변경 전 배율을 적용한다.
- **확인 기준:** 줌 전후 화면에서 보이는 위치는 달라도, 같은 월드 기준점을 클릭하면 같은 월드 목적지가 된다.

#### Phase 2.3 — PNG 한 장

- **상태:** 완료. x64 Debug·Release 빌드, 프레임워크 테스트, Sandbox 회귀 테스트를 통과했으며 사용자가 완료를 확인했다.
- **표시:** 빌드가 `Idle.png`를 `Sandbox.exe` 옆에 `BoyIdle.png`로 복사한다. Sandbox는 기존 흰 사각형 위에 좌상단 `16×16` 프레임을 그린다. 좌클릭 이동과 휠 줌은 그대로 동작한다.
- **소유권:** `CDirect2DRenderer::LoadSpritePng()`이 시작 시 한 번 WIC `32bppPBGRA`로 변환하고 동일한 Premultiplied Alpha 모드로 Direct2D 비트맵을 만든다. 비트맵은 렌더러 내부에서 소유하며 리사이즈 후에도 재사용한다. 로딩 실패 시 렌더러는 `HRESULT`를 반환하고 Sandbox는 종료 코드 `2`로 종료한다.

- **검증:** 이동·줌·리사이즈 후에도 첫 프레임이 표시되고, 투명 영역을 통해 사각형이 보인다.

#### Phase 2.4 — 스프라이트 시트

- **상태:** 완료. 구현 및 x64 Debug·Release 자동 검증 후 사용자 확인으로 종료했다. 구현 커밋 `ac70abe`는 `origin/DevClient`에 반영됐다. 다음은 [Phase 3.1 — 플레이어 상태 분리](#phase-31--플레이어-상태-분리)다.
- **재생:** `Idle`은 하·상·좌·우 순서이며, 정지 중에는 마지막으로 바라본 방향의 한 장을 표시한다. `Walk`는 상·하·좌·우 열 중 이동 방향의 열을 고정하고, 위에서 아래로 `16×16` 프레임 네 장을 6틱마다 넘긴다. 걷기 시작 시 첫 프레임으로 돌아가며 이동 중 방향 변경은 재생 위치를 유지한다.
- **소유권:** Sandbox가 이동 방향과 소스 영역을 정하고, `CSpriteAnimator`는 걷기 프레임 번호만 갱신한다. `ClientRenderLib`는 두 PNG를 시작 시 각각 한 번 로드하여 재생과 리사이즈에서 재사용한다.
