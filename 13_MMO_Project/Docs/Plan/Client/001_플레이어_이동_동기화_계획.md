# 플레이어 이동 동기화 1차 계획

## 목표와 범위

**언리얼 클라이언트 2개와 설정으로 지정한 콘솔 더미 N개가 같은 맵에서 서로의 입장·이동·정지·퇴장을 확인한다.** 더미는 언리얼 없이 실행하고, 언리얼과 동일한 `ClientNetworkLib` 및 게임 프로토콜 처리 코드를 사용한다. 초기 지형은 쿼터뷰로 보는 평면 한 장과 고정 장애물 하나다. 로그인/DB, 맵 간 이동, 전투, 광역 AOI, 클라이언트 예측은 1차 구현 범위가 아니다.

현재 있는 것은 IOCP 전송·메일박스, 패킷 생성기와 `FixedMaps` 루프백이다. `FixedMaps`의 `ReqMove`는 목적지 **맵 ID**를 받는 맵 간 이전이다. 구현에서 참고할 것은 맵 소유 워커의 수신·퇴장 처리 경로이며, 같은 맵 안의 보행 패킷이나 월드 상태를 기존 시험에 섞지 않는다. 아래 새 타입·경로·패킷 이름은 설계안이며 아직 구현하지 않았다.

**착수 순서:** [Phase 0 게임 데이터 생성기](../Common/001_게임데이터_생성기_계획.md#phase-0--작은-단위의-선행-작업)의 한 테이블 생성·판독을 먼저 완료한다. 아래 Phase 번호는 유지한다. 테스트용 좌표·기대값을 제외한 실제 이동 속도, 반경, 맵·스폰·장애물 정의와 표시용 수치는 Excel 원본에서 만든 바이너리로 읽고, 필수 데이터가 없으면 상수로 대체하지 않는다.

## 프로젝트·솔루션 등록 규칙

| 구분 | 솔루션 | 프로젝트 |
| --- | --- | --- |
| 클라이언트 | `Client/Client.sln` | `Client/GameClient/GameClient.uproject` (`GameClient`) |
| 서버 | `Server/Server.sln` | `Server/GameServer/GameServer.vcxproj` (`GameServer`) |

- 두 솔루션은 별도로 유지한다. 기존 `Portfolio.sln`과 `Tests/Chatting/Chatting.sln`은 변경하지 않는다. 게임 더미는 추가하는 Phase에서 `Client.sln`에 별도 프로젝트로 등록하며, 언리얼 런타임에 의존하지 않는다.
- `Chatting`과 동일하게 **등록하는 파일의 실제 디렉터리명과 필터명을 일치**시킨다. 예를 들어 `GameServer/Map`의 파일은 `GameServer\Map` 필터에 등록한다. 새 파일을 넣는 Phase에서 프로젝트 항목과 필터를 같이 확인하고, 실제 경로에 없는 분류용 필터는 추가하지 않는다.
- `GameClient`는 UE의 프로젝트 갱신 이후에도 `Client.sln` 이름과 실제 디렉터리 기준 필터 구성이 유지되는지 첫 Phase에서 확인한다. 생성된 프로젝트 파일을 수동으로만 고쳐야 유지되는 구조는 완료로 보지 않는다.

## 코드 공유와 소유권

| 경계 | 소유 상태와 책임 | 금지할 의존성 |
| --- | --- | --- |
| `Common/GameCoreLib` (신규) | 순수 C++20 좌표·이동 값 타입과 한 틱 이동 함수. 위치·목적지·속도·고정 간격의 입력을 받아 이동 후보와 도착을 계산한다. 양쪽에서 같은 규칙이 필요한 정적 지형 검증도 UE 타입 없이 표현한다. | UE, Windows 소켓, 패킷 DTO, `ContentsRuntime`, 실제 시계, 전역 초기화 |
| 게임 서버 맵 (`IContents`) | `ContentsRuntime`이 정한 소유 워커 한 곳에서 엔티티, 세션→엔티티 매핑, 정적 충돌 데이터와 맵 틱을 소유한다. 접수 검증, 이동 확정, 스폰·퇴장·스냅샷을 작성한다. | IOCP 완료 스레드의 월드 쓰기, 엔티티별 락·TLS 풀, UE 전용 타입 |
| 게임 공통 클라이언트 (신규) | 생성 클라이언트 클래스와 `ClientNetworkLib` 위에서 `Req*`/`Handle*`, 입장 상태와 `NetEntityId`별 권위 위치·서버 틱·명령 결과를 관리한다. UE와 더미는 동일한 구현을 사용한다. | UObject, 화면 표시 실패를 프로토콜 오류로 처리, 송수신 코드 복제 |
| UE / 콘솔 더미 | UE 게임 스레드는 클릭→맵 좌표 변환, 게임 상태 소비, Actor 수명·보간·애니메이션을 담당한다. 더미 앱 워커는 스크립트에서 같은 `Req*`를 호출하고 권위 값을 검증한다. 두 앱 모두 자신의 앱 스레드에서 `CClient::Tick()`을 호출한다. | Actor를 권위 상태로 쓰기, IOCP에서 Actor 조작, UE Replication·CMC RPC로 같은 이동을 이중 실행 |

**공유할 것은 `한 스텝의 규칙`이지 `서버 월드 전체`가 아니다.** 1차 클라의 권위 상태는 서버 패킷만 갱신한다. 같은 함수를 서버와 헤드리스 시험에서 먼저 검증하고, 내 캐릭터 예측이 필요할 때 공통 클라이언트가 재사용한다. 같은 소스만으로 동기화가 보장되지는 않는다. 시작 상태·좌표/반올림·속도·충돌 데이터·적용 입력·서버 틱까지 맞아야 하며, 나중에 예측을 넣어도 서버 상태로 보정한다. 전체 월드 락스텝이나 비트 단위 일치는 1차 목표가 아니다.

## ECS 구조 결정

- **ECS의 데이터/시스템 경계는 지금 잡고, 범용 ECS 프레임워크는 만들지 않는다.** 첫 맵은 `EntityId`와 `Transform`, `MoveIntent`, `MoveState` 값 컴포넌트를 가진 고정 조합 엔티티를 `unique_ptr`로 단독 소유한다. 엔티티에 가상 `Update()`나 플레이어 전용 보행을 두지 않는다. 명령 판정과 이동 시스템을 명시적으로 호출한다. 이 형태는 범용 registry나 타입별 고밀도 ECS 저장소를 구현했다는 뜻이 아니다.
- 패킷의 `NetEntityId`는 세션 ID·로컬 저장소 핸들·UE Actor 포인터와 분리한다. 1차는 서버 실행 중 발급한 ID를 재사용하지 않고, 재접속 시 클라이언트의 이전 복제 상태·표시 이력을 초기화한다. UE의 `NetEntityId → Actor`는 표현용 매핑일 뿐이다.
- 플레이어 요청과 다음 단계의 몬스터 AI가 같은 이동 의도를 만든다. 몬스터 단계에 서로 다른 컴포넌트 조합·필터가 실제로 생기면, 현 구조와 `EnTT`를 같은 워크로드에서 비교한다. 맵 틱 p95, 생성·삭제 비용, 캐시/메모리와 코드 복잡성을 비교하고, 채택하더라도 맵 소유권과 네트워크 ID는 유지한다. UE Mass는 나중에 대량 표현 병목이 확인될 때만 검토한다. 서버 ECS와 두 벌로 동기화하지 않는다.

## 이동·복제 계약

1. **입력과 좌표.** 좌클릭 목적지 이동, 재클릭은 목적지 교체, 명시적 정지 요청을 지원한다. 서버 XY 평면과 cm 단위를 정하고, 패킷은 부호 있는 정수 cm, 내부 이동은 소수 좌표를 유지한다. 패킷 경계의 반올림 규칙을 고정한다. 맵 원점과 UE 축·높이 변환은 UE 경계에서만 한다. 클라가 보낸 것은 목적지와 명령 번호뿐이며 현재 위치·속도·시간은 서버가 소유한다.
2. **고정 틱.** 첫 검증 설정의 맵 틱 20 Hz, 주기 스냅샷 10 Hz는 실행 설정에 두고 계측 후 조정한다. `OnFrame()` 한 호출당 고정 스텝 하나를 실행한다. `ContentsRuntime`의 기존 밀린 프레임 처리 방식은 변경하지 않고, 패킷 도착 수나 렌더 프레임 수를 이동 횟수로 쓰지 않는다. 입력은 서버가 선택한 처리 틱에만 적용하며 클라 시각으로 지나간 틱에 소급하지 않는다.
3. **판정과 이동을 분리.** `수신/입장·퇴장 반영 → 제한된 명령 판정 → 엔티티당 이동 한 스텝 → 상태 발행` 순서다. 같은 틱의 여러 명령은 시퀀스 순으로 이동 의도만 바꾼다. 유효한 마지막 명령이 남으며, 거절된 명령은 직전 유효 의도를 훼손하지 않는다. 정지 후 유효한 새 이동 요청이 같은 틱에 오면 새 요청이 우선이다. 처리량·대기열 상한을 정하고, 상한으로 소비하지 않은 요청을 승인으로 집계하거나 무제한 보관하지 않는다. 정체·상한 위반으로 종료할 경우 명시적으로 기록하고 기존 퇴장 경로로 정리한다.
4. **서버 충돌.** 맵 범위와 캐릭터 반경을 적용하고, 끝점만이 아니라 현재 위치부터 목적지까지 전체 직선이 유효한지 본다. 장애물에 가려진 목적지나 잘못된 좌표는 거절하고 기존 유효 이동은 유지한다. 1차는 정적 장애물 하나에 대한 직선 검증이다. 우회 경로, 동적 충돌, UE NavMesh는 이번 서버 판정의 일부가 아니다. 도착은 남은 거리를 넘기지 않으며, 속도는 대각선에서도 동일하다.
5. **프로토콜.** 신규 게임 프로토콜은 기존 생성기와 DTO 규약을 사용하되 `FixedMaps`와 분리한다. 최소 메시지는 입장·준비, 스폰/디스폰, 목적지/정지 요청, 소유자 명령 결과, 위치 스냅샷이다. 1차 스냅샷은 엔티티 하나의 `NetEntityId`, `serverTick`, 위치, 이동/정지 상태를 담고, 미확정 배치 포맷 때문에 생성기를 먼저 확장하지 않는다. 패킷 공급량과 기존 TCP 송신 큐 체류가 늘면 계측하고, 전송 대상과 발행 빈도부터 조정한다. 송신 접수 후 패킷을 폐기·변경할 수 있다고 가정하지 않는다.
6. **결과와 상태를 구별.** 이동과 정지는 연결 내 같은 `cmdSeq` 순서를 사용한다. 소유자 처리 결과에는 `cmdSeq`, 승인/거절 사유 및 판정 틱을 담는다. 처리란 승인뿐 아니라 거절을 확정한 경우도 포함한다. 결과는 좌표를 갱신하지 않는다. 맵은 결과를 명령 순서대로 발행하고, 이동 계산을 끝낸 뒤 그 틱의 최종 상태를 엔티티마다 한 번만 발행한다. 정지가 같은 틱의 유효한 후속 이동으로 대체되지 않았다면 판정 틱에 `Stopped` 상태를 발행한다(이미 멈춘 경우 포함). 도착도 다음 주기를 기다리지 않는다. 정지 승인이 아닌 이 상태를 최종 위치의 근거로 삼는다. 예측 단계에서는 소유자 권위 스냅샷에 처리 완료 입력 경계와 재실행에 필요한 활성 이동 의도를 싣는 계약을 별도로 확정한다.
7. **스폰·표시.** 신규 입장자에게 같은 맵의 기존 캐릭터를 그 틱의 권위 위치에서 보여주고, 최초 목록을 다 받았을 때만 준비 상태로 전환한다. 해당 ID의 위치보다 스폰을 먼저 발행한다. 공통 클라는 이전 틱의 위치나 이미 디스폰된 ID의 갱신을 적용하지 않는다. UE는 원격 Actor를 시간순 권위 표본으로만 보간하고 새 표본이 없으면 마지막 상태를 유지한다. 표시 좌표를 서버나 권위 테이블에 역기록하지 않는다. 첫 검증에서는 내 캐릭터도 권위 위치로 그리며, 입력 반응용 목적지 표시는 시뮬레이션과 분리한다.

## 더미 N개 실행 계약

- 채팅 `CDummyRunner`의 실행 구조를 참고한다. 게임 더미 실행 파일 하나가 설정의 `CLIENT_COUNT`만큼 독립 연결과 클라이언트 상태를 만들고, 하나의 `CClientManager`를 공유한다. `APP_WORKER_COUNT`는 별도 설정이다. 더미마다 스레드를 만들지 않고 각 더미의 `Tick()`과 입력은 배정된 앱 워커만 처리한다. 채팅 전용 시나리오나 패킷 코드는 가져오지 않는다.
- 각 더미는 자신의 입장이 확인되면 다른 더미를 기다리지 않고 스크립트대로 이동·재클릭·정지를 실행한다. 설정 개수, 실제 입장 수, 이동·정지 확인, 접속 실패·퇴장 결과를 구분해 집계한다. 접속 실패를 빼고 통과했다고 처리하지 않는다.
- 더미 2개는 기본 회귀 케이스이고 제품 상한이 아니다. 같은 실행 파일에서 설정만 바꿔 2보다 큰 값(첫 검증 예: 8개)을 여러 앱 워커에 배정한다. 설정한 수만큼 실제 입장하고 각 세션이 이동·정지한 뒤 종료되는지 확인한다. 이 시험은 개수 확장을 검증하는 것이며, 최대 동접이나 여러 물리 호스트 운영을 보장하지 않는다.

## 구현 순서와 완료 기준

한 번에 아래 체크 항목 하나만 작업한다. 각 항목에서 **변경 파일과 읽을 순서, 확인 방법과 결과**를 보여주고 사용자 검토 후 다음으로 넘어간다. 프로젝트 등록과 같은 변경에 필요한 필터 수정은 함께 한다. 다음 항목의 기능이나 리팩터링을 미리 넣지 않는다.

### Phase 1.1 — GameClient 기반과 네트워크 연동

- [ ] **Phase 1.1.1 — 프로젝트 등록:** UE 5.8.4 C++ Top Down으로 `GameClient`를 만들고 `Client.sln`에 등록한다. Win64 `Development Editor`에서 기본 맵을 열고 실행·종료한다. 프로젝트 갱신 뒤 이름과 필터를 확인한다. 네트워크는 연결하지 않는다.
- [ ] **Phase 1.1.2 — 라이브러리 링크:** 기존 `ClientNetworkLib`와 필요한 `NetworkCommonLib`·`MHLib`를 `Build.cs`로 연결한다. 실제 UBT의 MSVC/SDK, CRT/STL ABI, Release `/GL`, PCH/Windows 헤더 경계를 확인한다. 소스 복제나 DLL 래퍼 없이 서버 없는 빌드와 초기화·해제까지만 확인한다.
- [ ] **Phase 1.1.3 — 한 번의 패킷 왕복:** 기존 채팅 시험 서버에 접속해 생성 패킷 하나를 왕복시키고 UE 게임 스레드의 `Tick()`에서 응답을 받는다. 새 게임 패킷은 만들지 않는다.
- [ ] **Phase 1.1.4 — 재실행:** 연결된 상태에서 종료한 뒤 같은 에디터에서 다시 실행해 접속과 왕복을 반복한다. 기존 콘솔 경로도 유지되는지 확인한다.

### Phase 1.2 — GameServer 기반과 고정 틱 이동

- [ ] **Phase 1.2.1 — 서버 프로젝트 등록:** `Server.sln`에 `GameServer`를 등록하고 필터를 맞춘다. 실행 파일의 시작과 정상 종료만 확인한다. 리스너와 맵은 붙이지 않는다.
- [ ] **Phase 1.2.2 — 순수 이동 한 스텝:** 순수 C++ 이동 계산을 작성한다. 소켓 없이 0거리·대각선 속도·목적지 도착과 초과 이동 방지를 확인한다.
- [ ] **Phase 1.2.3 — 맵 한 곳에서 이동:** `GameServer`가 바이너리에서 `PlayerMovement`의 속도와 첫 `Map`의 범위·스폰을 읽고, 맵 하나와 엔티티 하나를 고정 워커에 등록한다. 내부 시험 명령으로 `OnFrame()` 한 번에 한 스텝만 실행되는지, Excel 속도 수정 후 재생성·서버 재시작만으로 이동량이 바뀌는지 확인한다.
- [ ] **Phase 1.2.4 — 재클릭과 정지:** 명령 판정과 이동 연산을 분리한다. 같은 틱의 복수 명령이 이동 거리를 늘리지 않고, 처리 결과와 최종 정지 틱이 구분되는지 확인한다.
- [ ] **Phase 1.2.5 — 장애물 거절:** `Map`에서 읽은 장애물과 `PlayerMovement`의 캐릭터 반경을 적용해 벽을 가로지르는 요청을 거절한다. 거절해도 직전 유효한 이동 의도는 유지되는지 확인한다.
- [ ] **Phase 1.2.6 — 서버 리스너:** `GameServer`에 기존 서버 라이브러리의 리스너를 연결한다. 로컬 접속과 해제만 확인한다. 아직 소켓 세션을 맵에 입장시키지 않는다.

### Phase 1.3 — 콘솔 더미 루프백

- [ ] **Phase 1.3.1 — 한 세션 입장:** 새 게임 프로토콜의 입장 계약과 공통 게임 핸들러를 연결한다. `Client.sln`에 더미 프로젝트를 등록하고, 더미 하나의 입장·준비·종료를 실제 IOCP 루프백에서 확인한다. `FixedMaps` 프로토콜은 그대로 둔다.
- [ ] **Phase 1.3.2 — 두 세션의 이동 복제:** 스폰·디스폰과 이동·정지 메시지를 붙인다. 스폰에는 엔티티의 권위 상태와 함께 표현 데이터를 찾을 이동 프로필 ID를 담되 서버 전용 수치 자체는 보내지 않는다. 더미 둘이 서로의 이동을 받고, 같은 틱의 권위 좌표와 명령 결과를 확인한다.
- [ ] **Phase 1.3.3 — 늦은 입장과 재접속:** 이동 중인 엔티티가 한 번만 스폰되고, 퇴장·재접속 후 이전 상태가 다시 적용되지 않는지 확인한다. 지연을 제어해 큐 체류와 정지 수렴을 따로 관찰한다.
- [ ] **Phase 1.3.4 — 설정 기반 N개:** `CLIENT_COUNT`와 앱 워커 설정을 적용한다. 같은 실행 파일의 2개 기본 회귀와 2보다 큰 설정에서 실제 입장·이동·정지·퇴장 수를 비교한다.

### Phase 1.4 — GameClient·더미 통합

- [ ] **Phase 1.4.1 — Actor 생성과 제거:** `GameClient`에 공통 게임 핸들러를 연결하고, 클라이언트용 바이너리의 표시 설정을 적용한다. 더미의 입장·퇴장이 Actor 생성·삭제로 이어지는지 확인한다. 이때 실제 UE 데이터 경로와 클라이언트 배포 대상도 확인한다.
- [ ] **Phase 1.4.2 — 클릭 이동과 권위 좌표 표시:** UE 클릭을 같은 이동 요청으로 보내고, UE와 더미가 서로의 입력 결과를 권위 좌표로 받는지 확인한다. 예측은 넣지 않는다.
- [ ] **Phase 1.4.3 — 원격 표시 보간:** 권위 상태를 바꾸지 않고 Actor 표시만 보간한다. 마지막 권위 좌표에 표시가 도달하는지 확인한다.
- [ ] **Phase 1.4.4 — UE 2개 + 더미 N개:** N ≥ 2로 접속하여 모든 참가자의 이동·정지·늦은 입장·퇴장을 확인한다. 정지 후 서버와 모든 클라이언트의 **같은 틱의 권위 정수 좌표**가 일치해야 한다.

90% 이상 일치 같은 비율 대신 비교 대상 틱·엔티티·좌표를 로그로 남긴다. 클라이언트 수, 맵 틱 비용, 패킷 건수/바이트 및 송신 대기량의 작은 기준선을 얻되, 이 데모를 MMO 최대 동접 검증이나 Delegate 운영 검증으로 보지 않는다.

## MMO 핵앤슬래시 확장 순서

1. **이동 체감과 지형:** 지연을 측정하고 필요 시 자기 캐릭터만 예측·보정한다. 서버 스냅샷에서 확정 상태를 복원하고 아직 처리되지 않은 입력만 재실행한다. 벽 우회는 별도 계약으로 설계한다.
2. **몬스터와 AOI:** `AIIntent`가 이동 시스템을 공유하도록 몹 한 종류를 추가한다. 근접 엔티티 스폰·디스폰 및 관심 범위 경계를 검증한다. 1차에는 맵 전체 전송 대상으로 시작하되 대상 계산을 발행부에 모아두고, 몹 단계에서 격자 AOI와 패킷 빈도·배치 및 ECS 저장소를 계측 비교한다.
3. **전투:** 처음에는 기본 공격 하나, 몹 HP와 사망까지다. `이동 → 사거리·쿨다운 검증 → 판정 → 피해/사망 이벤트`를 소유 워커에서 실행한다. UE는 선행 애니메이션을 재생할 수 있지만 피해·사망은 서버 확인으로 표시한다. AI·어빌리티·드랍은 UE Actor 상속 계층에 쌓지 않는다.
4. **드랍과 획득:** 서버가 아이템 엔티티를 생성하고, 거리·소유권·중복 획득을 판정한다. 그 뒤에 인벤토리 저장·복구, 맵 확장과 부하 검증을 붙인다.

## 언리얼 MCP와 AI 아트

- [Hermes 공식 `unreal-mcp` 스킬](https://hermes-agent.nousresearch.com/docs/user-guide/skills/optional/creative/creative-unreal-mcp)이 1순위다. 설치된 UE 5.8.4에서 [Epic의 실험 기능](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-mcp-in-unreal-editor?application_version=5.8)인 `ModelContextProtocol`과 `AllToolsets` 파일을 확인했다. 아직 활성화·연결을 시험하지 않았다. 별도 샌드박스 프로젝트에서 로컬 전용으로 도구 목록과 현재 레벨/Actor 조회부터 확인하고, 이후 배치·임포트 자동화에만 쓴다. 이동 규칙·런타임 빌드의 의존성이 아니다.
- [Hermes 공식 `comfyui` 스킬](https://hermes-agent.nousresearch.com/docs/user-guide/skills/optional/creative/creative-comfyui)로 다크 판타지 키아트와 재질 후보를 만들고, [Blender 플러그인/스킬](https://hermes-agent.nousresearch.com/marketplace/blender)은 UV·피벗·스케일 검수와 소품 정리에 사용한다. 기존 `game-sprite-vfx`는 2D 아이콘·VFX 보조 후보로만 둔다. Meshy/Tripo 같은 생성형 3D 도구는 실제 소품 한 개의 품질·비용·사용 조건을 비교할 때 검토한다.
- 첫 아트 결과는 폐허/지하 예배당 콘셉트 1장, 재질 1종, 정적 소품 1개다. 카메라 거리에서 실루엣과 이동 가능 영역이 읽혀야 한다. 원본 출처, 모델·버전, 프롬프트/워크플로와 사용 조건을 기록하고, 캐릭터 리깅이나 대량 제작은 미룬다. 아트 소품의 렌더 메시를 그대로 서버 충돌 데이터로 쓰지 않는다. 이동 검증은 회색 맵과 마네킹으로 진행하며, Blender는 첫 소품의 메시·UV·피벗 등을 실제로 손봐야 할 때만 설치한다.
